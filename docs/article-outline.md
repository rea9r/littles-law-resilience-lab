# 記事の構成（案）

Zenn に 1 本の記事として出す前提の章立て。図は `tools/diagrams/` の HTML から書き出した PNG を使う（Zenn の記事には HTML を埋め込めないため）。目次に出る `##` と `###` で全体像が分かるようにし、実験の中の「予測・実測」は `####` に置く。各節の下の箇条書きは、その節に書くこと・使う図・実測の数字のメモ（数字は 2 周目の値。03a は 4 回分）。

## タイトル案

- 決済 API が遅くなっただけで、なぜ商品一覧まで止まるのか ── リトルの法則で障害の広がり方を予測し、kind で確かめた
- タイムアウトとプールサイズはリトルの法則で決められる ── 障害を再現して確かめた

## 1. はじめに

### 1.1 決済 API が遅くなっただけで、1 秒ほどで商品一覧まで止まる

- 決済 API に 5 秒の遅延を入れると、決済と関係のない /products の成功率が 0.8% まで落ちる、という結果から入る

### 1.2 この記事のゴール

- 自分のサービスで、障害時にどの資源がいつ尽きるかを計算し、被害を広げないために何をどこに入れればよいかを決められるようになる

### 1.3 この記事で扱わないこと

- WebFlux・コルーチン・仮想スレッド（スレッドは尽きにくくなるが、L = λW の制約がコネクションやメモリに移るだけ）
- 待ち行列理論による遅延の予測（リトルの法則は負荷と遅延の関係までは教えてくれない）

## 2. リトルの法則

### 2.1 L = λW

- 式（KaTeX）と直感的な例：60 rps × 0.05 秒 = 常に 3 件を処理中

### 2.2 3 つの向きで使う

- 表：必要な並列数（L = λW）・スループットの上限（λ = L ÷ W）・待ち時間（W = L ÷ λ）

### 2.3 実測で確かめる

- 図：[01b の「実測の L と λ×W」](../scenarios/01b-tx-boundary/results/panels/littles-law.png)
- 平常時は約 3 本、障害中（決済 API がタイムアウトし続ける状態）は約 18 本。状態が変わっても 2 本の線が重なる
- λ×W の計算（`rate(http_server_requests_seconds_sum)` が λ×W に等しい理由）は `:::details` に入れる

### 2.4 この記事で使う前提

- 平均どうしの関係であること（p99 どうしでは成り立たない）
- L と W を同じ箱で測ること（「定常状態が前提」は 5 章で線が離れたところで説明する）

## 3. 障害を L = λW で読む

### 3.1 障害は W の増加から始まる

### 3.2 λW が上限を超えると、共有している資源を通じて広がる

- 本文は [article-draft.md](article-draft.md) の 3.2。防御なし（実験 0 と同じ設定）で考える
- 図：[障害の広がり方](images/failure-spread.ja.png)。平常時と障害時を同じ形で並べ、同時に要る本数（λW）3 本 → 300 本と上限 40 本を比べる。キャプション「スレッドだけを描いた単純化。コネクションについては下の本文」
- λW（上限がない場合に要る数）と L（上限で頭打ちになる実際の数）を呼び分ける
- コネクションも λW ≈ 300 本 > 10 本で、上限が小さいぶんスレッドより先に尽きる。2 つの資源がどちらも上限を超えるので、片方だけ増やしても /products は助からない（6 章への予告）

### 3.3 守り方は 3 つ：W を抑える・L を区切る・λ を絞る

- 表：守り方 × 具体的な手段 × この実験での実装（HTTP クライアントのタイムアウト、トランザクションの範囲、HikariCP、Resilience4j の Bulkhead・Retry・CircuitBreaker）
- 図：[order-api の中の資源](images/order-api-resources.ja.png)。Resilience4j の層がどこに入るかを見せる（3.2 から移した。防御なしの話の直前に置くと「バルクヘッドがあるのに、なぜ埋まるのか」とつまずくため）。作り直すときは、マス目を 10 × 4・使用中を紫にし、failure-spread とそろえる

## 5. 実験0：防御なしで壊す

### 5.1 設定

- タイムアウト 30 秒、決済 API はトランザクションの中で呼ぶ、HikariCP の取得待ちは既定の 30 秒

### 5.2 予測：何秒で、どこまで壊れるか

- 本文は [article-draft.md](article-draft.md) の 5.2
- 図：[障害の直後にスレッドが埋まっていく様子](images/thread-timeline.ja.png)。到着を等間隔にし、スレッドだけを数えた計算（キャプション「計算（実測ではない）」）。縦に切って交わる棒の数が L
- 空いていた 37 本 ÷ 60 件/秒 ≈ 0.6 秒で満杯。棒が「上限の本数 ÷ 到着率」（スレッド 0.67 秒、コネクション 0.17 秒）より長ければ、W によらず同じ時間で埋まる（6.1 のタイムアウトの上限につなぐ）
- λW の 300 本にはすぐにはならない（1.0 秒で 63 本）。頭打ちのあいだ、スレッドに入れる率は平均 40 ÷ 5.05 ≈ 8 件/秒で、L = λW の λ は箱に実際に入る率
- 実験 0 ではコネクションが 0.12 秒で先に尽き、/products もスレッドを握るので、0.12 + 30 ÷ 70 ≈ 0.55 秒と少し早まる

### 5.3 実測：5 秒を待たずに、1 秒ほどで 40 本が埋まる

- 本文は [article-draft.md](article-draft.md) の 5.3。障害の時刻をミリ秒で記録した 2 回の実行を比べる（それより前の 1 回は、時刻が秒単位なので外す）
- 図：[障害の前後 15 秒のスレッド](../scenarios/00-no-defense/results/panels/threads-fault.png)、[同じく HikariCP](../scenarios/00-no-defense/results/panels/hikari-fault.png)。`node tools/capture.mjs <results> --panels threads,hikari --around-fault 15,15 --width 700` で撮る。実測は描き直さず、Grafana の画面で見せる
- 2 回目：0.48 秒で 40 本（10 + 30）。1 回目：0.40 秒で 24 本（10 + 14。コネクションはもう尽きていた）、1.40 秒で 40 本。図の計算（27・32）の前後に散る
- ずれの理由は `:::details` に入れる：時刻の記録の遅れ（API の応答 + プロセスの起動 15〜20 ms で 1〜3 本ぶん）と処理中の本数のぶれ（2 回目が多い）、k6 の VU 不足（1 回目が少ない。/orders に使える空きの VU が 0.15 秒ほどで尽き、そのあとは 1 秒に約 30 しか作り足せない）
- 改善の候補：k6 の preAllocatedVUs を maxVUs にそろえ、障害を入れる前後の時刻を 1 つのプロセスで記録して、全シナリオを回し直す。Grafana の全パネルを幅 700px で撮り直す

### 5.4 決済 API を呼ばない /products まで止まる

- /products の成功率 0.8%、再起動 4 回（灰色の帯。記事の図で紫は /orders に使うので、ダッシュボードの再起動の色を灰色にした）
- 図：[00 の成功率](../scenarios/00-no-defense/results/panels/success.png)、[00 の HikariCP](../scenarios/00-no-defense/results/panels/hikari.png)（10 本が満杯、取得待ち最大 38）
- 実測の L と λ×W の線が離れるのはここ（完了したリクエストしか数えないため）。「定常状態が前提」を説明する
- 40 本のまま約 20 秒続いたあと、約 5 秒ごとに 40 → 28 → 17 → 6 本と下がる。取得待ちは 30 → 18 → 7 → 0、使用中のコネクションは 10 のまま（コネクション 10 本が約 5 秒ごとに入れ替わって、残りを片付けている形に見える。再起動との関係は、イベントの時刻と突き合わせてから書く）。取得待ちの最大 38 は再起動の直後（プールのコネクションがまだ 2 本のとき、2 + 38 = 40）の値で、5.3 の「30 で止まるのはスレッドが 40 本で頭打ちだから」と矛盾しないことを断る。成功率のパネルは、/orders を紫・/products を青緑にしたダッシュボードで撮り直す

## 6. 実験1：W を抑える

### 6.1 タイムアウトの窓を計算する

#### 下限：平常時の p99 に余裕を足す

- 120ms → 約 200ms

#### 上限：割り当てたスレッド数 ÷ ピーク時の rps

- 40 × 0.7 ÷ 60 ≈ 470ms。この間の 300ms にする

### 6.2 タイムアウトを 300ms にする（01a）

#### 予測

- スレッドは 60 × 0.3 = 18 本で収まるが、コネクションは λW = 18 本 > 10 本で尽きる（3.2 の予告どおり）。コネクションの境目 10 ÷ 60 ≈ 0.17 秒は、6.1 の下限 200ms より短く、タイムアウトの窓がない

#### 実測：予告どおりコネクションで尽き、1.6 秒でスレッドも尽きる

- /products の成功率 12.4%、再起動 5 回、コネクションの取得待ち最大 37
- 図：[01a の HikariCP](../scenarios/01a-timeout/results/panels/hikari.png)

### 6.3 もう 1 つの W：コネクションの取得待ち

- トランザクションの中で決済 API を呼ぶと、コネクションも 0.3 秒握る。60 × 0.3 = 18 本 > 10 本
- 取得待ちの既定値 30 秒が新しい W になり、スレッドが尽きる（タイムアウトは 1 か所ではない）

### 6.4 決済 API をトランザクションの外で呼ぶ（01b）

#### 予測

- スレッド 60 × 0.3 + α ≈ 19 本、コネクションはほぼ使わない

#### 実測：スレッドは 20 本で止まり、/products は 100%

- 再起動 0 回、回復まで 6 秒
- 図：[01b のスレッド](../scenarios/01b-tx-boundary/results/panels/threads.png)、[01b の成功率](../scenarios/01b-tx-boundary/results/panels/success.png)

## 8. 実験3：λ を絞る

### 8.1 リトライで、安全だったはずの 300ms が崩れる（03a）

#### 予測

- W = 3 × 0.3 + 2 × 0.5 = 1.9 秒（試行の間の待ちもスレッドを握る）。L = 60 × 1.9 = 114 本

#### 実測：1.3〜1.5 秒で尽き、決済 API のスレッドも上限に張り付く

- 4 回の実行で /products の成功率 5〜9%
- 図：[03a の決済 API のスレッド](../scenarios/03a-retry/results/panels/payment-api-threads.png)

### 8.2 原因を取り除いても戻らない

#### 4 回中 2 回は、遅延を外して 2 分たっても戻らなかった

- 表：[4 回の結果](../scenarios/03a-retry/results/runs.md)（回復まで 42 秒・戻らない・19 秒・戻らない）
- 図：[03a の成功率](../scenarios/03a-retry/results/panels/success.png)（遅延を外したあとも 0% のまま、一瞬戻ってまた落ちる）

#### 何が起きていたか

- order-api が起動するたびに、決済 API への呼び出しが 107 件/秒まで膨らむ（2 回目の実行。毎秒約 36 件がタイムアウト、約 30 件はリトライのすえ成功）
- 両方のスレッドが埋まって liveness probe が失敗し、再起動。Pod のイベントに CrashLoopBackOff が残り、再起動の間隔が延びていく

#### リトルの法則で読むと

- 決済 API の処理能力は λ = L ÷ W = 6 ÷ 0.05 = 120 rps。リトライがこの手前まで呼び出しを増やすと、待ち行列で 300ms を超え、またリトライになる

### 8.3 サーキットブレーカーで流入を止める（03b）

#### 実測：決済 API への呼び出しが 60 件/秒から 5 件/秒に

- /products は 100%、再起動 0 回、回復まで 10 秒
- 図：[03b の Resilience4j](../scenarios/03b-circuit-breaker/results/panels/resilience4j.png)（open と半開を 5 秒ごとに繰り返す）、[03b の決済 API の呼び出し](../scenarios/03b-circuit-breaker/results/panels/payment-calls.png)

### 8.4 ブレーカーが開くまでの穴

- 失敗が 20 件たまるまで開かない。それまでのリクエストはリトライの待ちでスレッドを握り、0.7〜1.4 秒でスレッドが一度尽きる（数秒で空く）
- 図：[03b のスレッド](../scenarios/03b-circuit-breaker/results/panels/threads.png)
- この穴を埋めるのが、9 章のバルクヘッドとの組み合わせ

### A. 他にもこんな場面で使える

### B. この実験環境の限界

- k6 の constant-arrival-rate はリクエストを等間隔に送るので、本番のトラフィックよりばらつき（バースト）を小さく見積もる（7.3 のバルクヘッドの代償が 0 件だった理由）
- 8GB の Mac（Docker に約 4GB）で動かすため、数字を約 1/5 に縮めている。比率が同じなら、尽きるまでの秒数やタイムアウトの窓は変わらない
- メトリクスは 1 秒ごとのサンプルなので、「何秒で尽きたか」には 1 秒の幅がある
- k6 の preAllocatedVUs が少ないので、障害でリクエストが止まると VU を作り足すあいだ到着を捨てる。障害の直後の数秒は、到着が等間隔ではなくなる（5.3）
- 壊れるシナリオの回復時間は、障害が終わるタイミングによって実行ごとにばらつく
