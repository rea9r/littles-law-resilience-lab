Zenn に 1 本の記事として出す前提の章立て。図は `tools/diagrams/` の HTML から書き出した PNG を使う（Zenn の記事には HTML を埋め込めないため）。目次に出る `##` と `###` で全体像が分かるようにし、実験の中の「予測・実測」は `####` に置く。各節の下の箇条書きは、その節に書くこと・使う図・実測の数字のメモ（数字は測り方を直したあとの 3 周目の値。00 は 3 回分、03a は 12 回分）。

## 1. はじめに

### 1.1 決済 API が遅くなっただけで、1 秒ほどで商品一覧まで止まる

- 決済 API に 5 秒の遅延を入れると、決済と関係のない /products の成功率が 1.0% まで落ちる、という結果から入る

### 1.2 この記事のゴール

- 自分のサービスで、障害時にどの資源がいつ尽きるかを計算し、被害を広げないために何をどこに入れればよいかを決められるようになる

### 1.3 この記事で扱わないこと

- WebFlux・コルーチン・仮想スレッド（スレッドは尽きにくくなるが、L = λW の制約がコネクションやメモリに移るだけ）
- 待ち行列理論による遅延の予測（リトルの法則は負荷と遅延の関係までは教えてくれない）

## 2. リトルの法則

### 2.1 L = λW

- 式（KaTeX）と直感的な例：60 rps × 0.05 秒 = 常に 3 件を処理中

### 2.2 3 つの向きで使う

- 表：必要な並列数（L = λW）・スループットの上限（λ = L ÷ W）・待ち時間（W = L ÷ λ）

### 2.3 実測で確かめる

- 図：[01b の「実測の L と λ×W」](../scenarios/01b-tx-boundary/results/panels/littles-law.png)
- 平常時は約 3 本、障害中（決済 API がタイムアウトし続ける状態）は約 18 本。状態が変わっても 2 本の線が重なる
- λ×W の計算（`rate(http_server_requests_seconds_sum)` が λ×W に等しい理由）は `:::details` に入れる

### 2.4 この記事で使う前提

- 平均どうしの関係であること（p99 どうしでは成り立たない）
- L と W を同じ箱で測ること（「定常状態が前提」は 5 章で線が離れたところで説明する）

### 3.2 λW が上限を超えると、共有している資源を通じて広がる

- 本文は [article-draft.md](article-draft.md) の 3.2。防御なし（実験 0 と同じ設定）で考える

## 5. 実験0：防御なしで壊す

### 5.1 設定

- タイムアウト 30 秒、決済 API はトランザクションの中で呼ぶ、HikariCP の取得待ちは既定の 30 秒

### 5.2 予測：何秒で、どこまで壊れるか

- 本文は [article-draft.md](article-draft.md) の 5.2
- 図：[障害の直後にスレッドが埋まっていく様子](images/thread-timeline.ja.png)。到着を等間隔にし、スレッドだけを数えた計算（キャプション「計算（実測ではない）」）。縦に切って交わる棒の数が L
- 空いていた 37 本 ÷ 60 件/秒 ≈ 0.6 秒で満杯。棒が「上限の本数 ÷ 到着率」（スレッド 0.67 秒、コネクション 0.17 秒）より長ければ、W によらず同じ時間で埋まる（6.1 のタイムアウトの上限につなぐ）
- λW の 300 本にはすぐにはならない（1.0 秒で 63 本）。頭打ちのあいだ、スレッドに入れる率は平均 40 ÷ 5.05 ≈ 8 件/秒で、L = λW の λ は箱に実際に入る率
- 実験 0 ではコネクションが 0.12 秒で先に尽き、/products もスレッドを握るので、0.12 + 30 ÷ 70 ≈ 0.55 秒と少し早まる

### 5.3 実測：5 秒を待たずに、1 秒ほどで 40 本が埋まる

- 本文は [article-draft.md](article-draft.md) の 5.3。同じ設定の 3 回の実行を比べる。障害の時刻は、遅延を入れる API を呼ぶ直前と応答を受けた直後の中点（前後の幅は 2〜3 ms）。生の値は [runs.md](../scenarios/00-no-defense/results/runs.md)
- 図：[障害の前後 15 秒のスレッド](../scenarios/00-no-defense/results/panels/threads-fault.png)、[同じく HikariCP](../scenarios/00-no-defense/results/panels/hikari-fault.png)（1 回目の実行）。`node tools/capture.mjs <results> --panels threads,hikari --around-fault 15,15 --width 700` で撮る。実測は描き直さず、Grafana の画面で見せる
- 1 回目：0.34 秒で 27 本（10 + 17。コネクションはもう尽きていた）、1.34 秒で 40 本。3 回目：0.47 秒で 35 本（10 + 25）。2 回目：0.92 秒で 40 本
- コネクションの分を入れた計算（0.34 秒で 26 本、0.47 秒で 34 本、0.55 秒で満杯）より 1 本多いだけ。処理中だった本数のぶれ（障害の前の 1 分間で 1〜5 本）の範囲。スレッドだけの図（23・31 本）より 3〜4 本多いのは、/products がコネクションを待ってスレッドを握るから
- 測り方を直す前は、2 回の実測が計算の前後に散っていた（k6 の VU 不足で障害の直後の到着が減る、障害の時刻の記録が遅れる）。直した経緯は [iteration-log.md](iteration-log.md) に残し、記事には書かない

### 5.4 決済 API を呼ばない /products まで止まる

## 6. 実験1：W を抑える

### 6.1 タイムアウトの窓を計算する

#### 下限：平常時の p99 に余裕を足す

- 120ms → 約 200ms

#### 上限：割り当てたスレッド数 ÷ ピーク時の rps

- 40 × 0.7 ÷ 60 ≈ 470ms。この間の 300ms にする

### 6.2 タイムアウトを 300ms にする（01a）

#### 予測

- スレッドは 60 × 0.3 = 18 本で収まるが、コネクションは λW = 18 本 > 10 本で尽きる（3.2 の予告どおり）。コネクションの境目 10 ÷ 60 ≈ 0.17 秒は、6.1 の下限 200ms より短く、タイムアウトの窓がない

#### 実測：予告どおりコネクションで尽き、1.9 秒でスレッドも尽きる

- /products の成功率 12.3%、再起動 5 回、コネクションの取得待ち最大 31
- 図：[01a の HikariCP](../scenarios/01a-timeout/results/panels/hikari.png)

### 6.3 もう 1 つの W：コネクションの取得待ち

- トランザクションの中で決済 API を呼ぶと、コネクションも 0.3 秒握る。60 × 0.3 = 18 本 > 10 本
- 取得待ちの既定値 30 秒が新しい W になり、スレッドが尽きる（タイムアウトは 1 か所ではない）

### 6.4 決済 API をトランザクションの外で呼ぶ（01b）

#### 予測

- スレッド 60 × 0.3 + α ≈ 19 本、コネクションはほぼ使わない

#### 実測：スレッドは 22 本で止まり、/products は 100%

- 再起動 0 回、回復まで 7 秒
- 図：[01b のスレッド](../scenarios/01b-tx-boundary/results/panels/threads.png)、[01b の成功率](../scenarios/01b-tx-boundary/results/panels/success.png)

## 8. 実験3：λ を絞る

### 8.1 リトライで、安全だったはずの 300ms が崩れる（03a）

#### 予測

- W = 3 × 0.3 + 2 × 0.5 = 1.9 秒（試行の間の待ちもスレッドを握る）。L = 60 × 1.9 = 114 本

#### 実測：1 秒前後で尽き、決済 API のスレッドも上限に張り付く

- 8 回の実行で、スレッドが尽きるまで 0.84〜1.57 秒（1 秒ごとの計測）、/products の成功率 7〜8%
- 図：[03a の決済 API のスレッド](../scenarios/03a-retry/results/panels/payment-api-threads.png)

### 8.2 原因を取り除いても戻らない

#### 12 回中 2 回は、遅延を外して 2 分たっても戻らなかった

- 表：[12 回の結果](../scenarios/03a-retry/results/runs.md)。測り方を直したあとの 8 回はすべて 12〜46 秒で戻り、直す前の 4 回では 2 回が戻らなかった
- 戻らなかったうちの 1 回（直す前の 4 回目）は、直前の実行の再起動の待ち（CrashLoopBackOff）を引き継いでいた。新しい Pod で始めた 11 回に限ると、戻らなかったのは 1 回。「半分は戻らない」ではなく「ときどき戻らない」として書く
- 図：[戻らなかった回の成功率](../scenarios/03a-retry/results/panels/success-not-recovered.png)（直す前の 2 回目。遅延を外したあとも 0% のまま、一瞬戻ってまた落ちる）。戻った回は [03a の成功率](../scenarios/03a-retry/results/panels/success.png)

#### 何が起きていたか

- 12 回のどの実行でも、遅延を外したあと order-api が起動すると、決済 API への呼び出しが 112〜123 件/秒まで膨らみ、payment-api のスレッドが上限の 6 本に 8〜22 秒張り付く。戻るかどうかは、この間に liveness probe が失敗するかどうかで分かれる
- 戻らなかった回（直す前の 2 回目）では、order-api から見て毎秒約 36 件がタイムアウト、約 30 件はリトライのすえ成功していた
- 両方のスレッドが埋まって liveness probe が失敗し、再起動。Pod のイベントに CrashLoopBackOff が残り、再起動の間隔が延びていく

#### リトルの法則で読むと

- 決済 API の処理能力は λ = L ÷ W = 6 ÷ 0.05 = 120 rps。リトライがこの手前まで呼び出しを増やすと、待ち行列で 300ms を超え、またリトライになる

### 8.3 サーキットブレーカーで流入を止める（03b）

#### 実測：決済 API への呼び出しが 60 件/秒から 4 件/秒に

- /products は 100%、再起動 0 回、回復まで 11 秒
- 図：[03b の Resilience4j](../scenarios/03b-circuit-breaker/results/panels/resilience4j.png)（open と半開を 5 秒ごとに繰り返す）、[03b の決済 API の呼び出し](../scenarios/03b-circuit-breaker/results/panels/payment-calls.png)

### B. この実験環境の限界

- k6 の constant-arrival-rate はリクエストを等間隔に送るので、本番のトラフィックよりばらつき（バースト）を小さく見積もる（7.3 のバルクヘッドの代償が 0 件だった理由）
- Docker に約 4GB で動く大きさにするため、数字を約 1/5 に縮めている。比率が同じなら、尽きるまでの秒数やタイムアウトの窓は変わらない
- メトリクスは 1 秒ごとのサンプルなので、「何秒で尽きたか」には 1 秒の幅がある
- HikariCP はプールの統計を 1 秒キャッシュするので、1 秒ごとの計測では、使用中・取得待ちが 1 つ前の計測の値のままのことがある（スレッドの本数と同じ瞬間の値とは限らない。runs.md の 00 の 2 回目）
- 壊れるシナリオの回復時間は、障害が終わるタイミングによって実行ごとにばらつく
