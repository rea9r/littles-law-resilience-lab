### 3.2 λW が上限を超えると、共有している資源を通じて広がる

order-api のスレッド 40 本は /orders・/products・/livez のすべてで、HikariCP のコネクション 10 本は /orders と /products で共有しています。この節では、Resilience4j などの防御をまだ何も入れていない状態（5 章の実験 0 と同じ設定）で考えます。

/orders は、決済 API の応答が返るまでスレッドを 1 本握ったままにします。上限がなければ、同時に握る本数は λW で決まります。/products は DB を読むだけで 1 ミリ秒足らずで返るので、スレッドはほとんど使いません。決済 API の応答が 5.05 秒になると、/orders の λW は 60 件/秒 × 5.05 秒 ≈ 300 本になり、上限の 40 本を大きく超えます（λW は流れが落ち着いたときの本数で、そこに至るまでの動きは 5.2 で追います）。

![障害の広がり方](images/failure-spread.ja.png)
*スレッドだけを描いた単純化。コネクションについては下の本文*

40 本がすべて埋まると、あとから来たリクエストは、どのエンドポイント宛てかに関係なく、Tomcat の中の 1 本の列に並んでスレッドの空きを待ちます。負荷をかける k6 は 5 秒でタイムアウトします（決済 API に入れた遅延の 5 秒とは別の設定です）。そのため、次のことが起きます。

- **/products**：決済 API を呼ばないのに、空きを待つうちに 5 秒を過ぎ、ほぼすべて失敗する
- **/orders**：スレッドを取れても 5 秒以内には返らず、失敗する。クライアントがあきらめたあとも処理は続き、スレッドは握られたまま
- **/livez**：応答できず、Kubernetes が Pod を再起動する（実験 0 では障害中に 3 回。5.4）

コネクションでも同じことが起きます。実験 0 では決済 API をトランザクションの中で呼ぶので、/orders はコネクションも 5.05 秒握ります。コネクションの λW も約 300 本です。上限は 10 本とスレッドより少ないので、スレッドより先に尽きます。コネクションが先に尽きたあとは、スレッドを取れた /products も、コネクションの空きを待ってスレッドを握ります。共有している 2 つの資源がどちらも上限を超えているので、片方だけを増やしても /products は助かりません。6 章では、スレッドとコネクションを握る時間を順に短くします。

遅くなったのは決済 API だけです。それでも、共有している資源を通じて、決済と関係のない API まで止まります。

### 3.3 守り方は 3 つ：W を抑える・L を区切る・λ を絞る

L = λW のどれかを小さくすれば、λW を上限の内側に収められます。W は 1 件が資源を握る・待つ時間です。L と λ は、ここでは決済 API の呼び出しの数で、L は同時に呼んでいる数、λ は 1 秒に呼ぶ数です。/orders 1 件が資源を握る時間の入れ子で見ると、防御が効く場所は次のとおりです（札は、それを入れるシナリオの名前）。

![防御が効く場所](images/defenses.ja.png)
*上の段は 00・01a、下の段は 01b 以降の形。棒の長さは比例していない*

- **W を抑える**：01a のタイムアウトは、決済 API の応答を待つ時間に上限を付けます（上の段）。それでも 00・01a はトランザクションの中で決済 API を呼ぶので、コネクションも同じ時間握り、60 件/秒 × 0.3 秒 = 18 本が上限の 10 本を超えます（6 章）。01b は決済 API をトランザクションの外で呼び、コネクションを握るのをあとの短い書き込みだけにして、取得待ちも打ち切ります（下の段）。スレッドを握る時間は、決済 API の待ちが大半なので、あまり変わりません
- **L を区切る**：02b のバルクヘッドは、決済 API を同時に呼ぶ数を区切ります。あふれた /orders はすぐ断られるので、決済 API を待ってスレッドを握るのは、区切った数までになります
- **λ を絞る**：03b のサーキットブレーカーは、失敗が続くと開き、しばらく決済 API を呼ばずにすぐ失敗を返します
- **リトライ（03a）は逆に働きます**：失敗を取り戻す代わりに、1 件の W と、呼び出しの数 λ を増やします（8 章）

タイムアウト・バルクヘッド・サーキットブレーカーで /orders が早く返れば、スレッドを握る時間も短くなります。リトライが一番外側にあるので、試行のたびにサーキットブレーカーとバルクヘッドを通り直し、それらに断られた呼び出しはリトライしません。実験 0 では、どの防御も入れていません。値は次の表のとおりです。

| 守り方 | 手段 | この実験での値 | 入れるシナリオ |
| --- | --- | --- | --- |
| W を抑える | 決済 API のタイムアウト | 30 秒 → 300ms（02a・02b は 800ms） | 01a 以降 |
| W を抑える | コネクションの取得待ちを打ち切る | 30 秒 → 250ms | 01b 以降 |
| W を抑える | 決済 API をトランザクションの外で呼ぶ | — | 01b 以降 |
| L を区切る | バルクヘッド | 同時に 12 まで。空いていなければ待たずに断る | 02b・04 |
| λ を絞る | サーキットブレーカー | 10 秒の窓で 20 回以上呼び、失敗率 50% 以上で開く。開いたまま 5 秒、半開で 10 回試す | 03b・04 |
| （W と λ が増える） | リトライ | 試行は最大 3 回（初回を含む）・500ms おき（04 は 2 回・100ms おき） | 03a・03b・04 |

### 4.1 全体の構成

![全体の構成](images/architecture.ja.png)

- Prometheus と Grafana は、kind のポートの割り当てで、手元のブラウザから localhost:9090・localhost:3000 で開けます
- 負荷も障害も、クラスタの外から scenarios/run.sh が入れます。シナリオの設定を当てると、設定が変わったアプリの Pod だけが入れ替わります（payment-api の設定が変わるのは 02a・02b の前後だけ）
- k6 は到着率を一定に保って送ります（オープンモデル）。応答が遅れても送る数を減らさないので、障害のときに要求が積み上がる様子をそのまま再現できます。k6 は応答を待つ 1 件に 1 VU を使うので、到着率 × k6 のタイムアウト 5 秒（/orders なら 300）に余裕を足した数の VU を、最初から用意しておきます（これもリトルの法則です。途中で作り足すと、作り足すあいだの到着を捨ててしまいます）
- payment-api は、平均 0.05 秒・p99 0.12 秒の対数正規分布で応答を返すモックです。6 本のスレッドなので、平均 0.05 秒なら 1 秒に約 120 件までさばけます。リトライで呼び出しが増える 03a で、この上限が効いてきます
- order-api のメトリクスは、業務の 40 本とは別のスレッドで 8081 番から返します。40 本が埋まると readiness にも落ち、業務用の Service からは外れます（新しい接続は断られる）。メトリクス用の Service は、readiness に落ちた Pod も返す設定（publishNotReadyAddresses）にしてあるので、そのあいだも Prometheus は取りに行けます
- 手元の kind クラスタで動くよう、到着率やプールの大きさを、よくある本番の規模（Tomcat の既定のスレッド 200 本など）の約 1/5 に縮めています。比率が同じなら、尽きるまでの秒数は変わりません（付録 B）

### 4.2 1 回の実験の流れ

![1 回の実験の流れ](images/scenario-timeline.ja.png)

0 秒の前に、設定の適用と Pod の入れ替え、k6 の起動を待つ時間があり（1 分ほど）、全体では約 7 分かかります。ウォームアップは、JIT のコンパイルや接続プールが落ち着くまで待つ区間で、何も測りません。平常時の区間では、測った L と λW が一致すること（2.3）と、平常時の成功率を確かめます。

### 4.3 被害スコア

図の下の括弧が、どの値をどの区間で測るかです。

- **成功率・使用中のスレッド・取得待ち**：障害中の 120 秒で集計する。成功率はエンドポイントごとに区間全体の割合、使用中のスレッドは平均と最大、コネクションの取得待ちの本数は最大
- **スレッドが尽きるまで**：障害から 15 秒のあいだの生の計測で、初めて 40 本になった時刻。計測は 1 秒ごとなので、実際にはこれより早く尽きていることがある。15 秒のうちに 40 本にならなければ「尽きない」
- **回復までの時間**：遅延を外してから、両方のエンドポイントの成功率（直近 6 秒）が 99% 以上になり、そのまま 15 秒続いた区間の始まりまで。120 秒のうちにそうならなければ「戻らない」
- **再起動の回数**：負荷をかけている間の全体で数える。遅延を外したあとに再起動することもある

### 5.2 予測：何秒で、どこまで壊れるか

3.2 の 300 本は、上限がなかった場合に、流れが落ち着いたあとの値です。障害の直後にスレッドがどう埋まるかは、1 件ずつの動きを追うと分かります。到着を等間隔にし、スレッドだけを数えて計算したのが次の図です。

図の 1 行が 1 本のスレッドです。縦に切ったときに交わる棒の数が、その瞬間に使っているスレッドの数 L になります。障害の前は、0.05 秒の短い棒が上の 3 行を入れ替わりで使っています（/products は 1 ミリ秒足らずで返るので、棒は描いていません）。

![障害の直後にスレッドが埋まっていく様子（計算）](images/thread-timeline.ja.png)
*計算（実測ではない）*

- **埋まるまでの時間は、空いている本数と到着率で決まる。** 障害の時点で処理中だった 3 件も応答が遅れるので、空いているのは 37 本です。終わる棒がないまま 1 秒に 60 本ずつ増えるので、約 0.6 秒で埋まります。棒が十分に長ければ、5 秒でも 30 秒でも同じです（どこまで短くすれば埋まらないかは、6.1 で求めます）
- **上限がなくても、300 本にはすぐにはならない。** 1.0 秒の時点では 63 本です。300 本で落ち着くのは、最初の棒が終わり始め、増える棒と終わる棒が釣り合う 5 秒後からです

**L = λW の λ は、その資源に実際に入る率です。** 2 章では λ を到着率と呼びましたが、上限で頭打ちのあいだ、スレッドに入れる率は到着率よりずっと小さくなります。0.6〜5 秒は 1 件も入れません。5 秒後からは、終わった棒の数だけ入れ替わりに入るので、平均で 40 ÷ 5.05 ≈ 8 件/秒です。落ち着けば、40 本 ≈ 8 件/秒 × 5.05 秒で L = λW が成り立ちます（スレッドだけを数えた値。実験 0 ではコネクション 10 本が先に詰まるので、約 2 件/秒。5.4）。入れなかった残りは列に並び、伸び続けます（図の上の「空きを待つ列」）。上限がなければ入る率は到着率と同じなので、3.2 の 60 件/秒 × 5.05 秒 ≈ 300 本になります。

予測は「障害から約 0.6 秒で 40 本が埋まり、/products は列に並んで 5 秒でタイムアウトする」です。

:::details 実験 0 では、コネクションの分だけ少し早い（約 0.55 秒）
実験 0 では決済 API をトランザクションの中で呼ぶので、コネクション 10 本が先に (10 − 3) ÷ 60 ≈ 0.12 秒で尽きます。このとき使っているスレッドは、コネクションを握った /orders の 10 本です。そのあとは /products もコネクションの空きを待つあいだ（HikariCP の取得待ちの上限は 30 秒）スレッドを握るので、残りの 30 本は 1 秒に 70 本ずつ埋まり、0.12 + 30 ÷ 70 ≈ 0.55 秒で満杯になります。障害中に処理を終えられるのも、コネクションを 5.05 秒ずつ握る /orders が 1 秒に約 2 件（10 ÷ 5.05）だけです（5.4）。
:::

### 5.3 実測：5 秒を待たずに、1 秒ほどで 40 本が埋まる

計測は 1 秒ごとです（業務とは別のポートで受けているので、40 本が埋まっても測れます）。予測の約 0.6 秒は計測の間隔より短いので、障害の直後の 1〜2 点で確かめます。同じ設定で 3 回回しました（障害の時刻は、遅延を入れる API を呼ぶ直前と応答を受けた直後に、ミリ秒まで記録しています）。

![障害の前後 15 秒のスレッド（1 回目の実行）](../scenarios/00-no-defense/results/panels/threads-fault.png)
*1 回目の実行。赤い帯（と下端の赤い線）が障害の区間*

1 回目の実行では、障害の 0.34 秒後の最初の計測で 27 本、次の 1.34 秒後の計測で 40 本すべてが埋まっていました。3 回目は 0.47 秒後に 35 本、2 回目は 0.92 秒後の最初の計測で、もう 40 本でした。コネクションの分を入れた計算（5.2 の折りたたみ）では、0.34 秒で 26 本、0.47 秒で 34 本、0.55 秒で満杯です。途中を測れた 2 回は、どちらも計算より 1 本多いだけでした（障害の時点で処理中だった本数は、障害の前の 1 分間で 1〜5 本とぶれるので、その範囲です）。スレッドだけを数えた図より 3〜4 本多いのは、コネクションが先に尽き、/products もスレッドを握るからです。決済 API の遅れの 5 秒を待たずに、計算の線に沿って埋まっています。3 回の実行の生の値は scenarios/00-no-defense/results/runs.md にあります。

![障害の前後 15 秒の HikariCP（1 回目の実行）](../scenarios/00-no-defense/results/panels/hikari-fault.png)
*1 回目の実行。実線が使用中、点線が取得待ち、薄い破線が上限*

図の 15 秒のあいだは、どの計測でもコネクションは 10 本とも使われていて、握っている 10 本と待っている本数を足すと、スレッドの本数に一致しました（0.34 秒は 10 + 17 = 27、1.34 秒からは 10 + 30 = 40）。0.34 秒の時点で、コネクションはもう尽きていたことになります（計算では 0.12 秒）。取得待ちが 30 で止まっているのは、スレッドが 40 本で頭打ちだからです（コネクションを待てるのは、スレッドを持っているリクエストだけ）。障害の前も約 3 本使っているのは、決済 API をトランザクションの中で呼んでいるからで、60 件/秒 × 0.05 秒と合います。/products がほぼすべて失敗したことは、5.4 の成功率で確かめます（障害中の /products の失敗のうち 91% が、k6 の 5 秒のタイムアウトでした）。
