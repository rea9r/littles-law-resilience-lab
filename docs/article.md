## はじめに

サーバーサイドの開発や運用をしていると、こんな場面に出会うことがあります。

外部の API が1つ遅くなっただけなのに、その API を呼んでいない画面まで開かなくなる。CPU もメモリも余っていて、エラーログにもそれらしいものが出ていない。そのうちヘルスチェックにも答えられなくなって、コンテナが再起動を繰り返す。外部の API が直っても、しばらく戻らない。

遅くなったのは1つの API なのに、なぜほかの画面まで開かなくなるのでしょうか。考えられる原因の1つが、スレッドプールの枯渇です。遅い API の応答を待つ処理がスレッドを握ったまま返さないと、プールが尽きます。そうなると、ほかのリクエストもヘルスチェックも、スレッドの空きを待つことになります。

ここからは、サーバーが呼び出す外部の API や DB を「下流」、サーバーを呼び出す側を「上流」と呼びます。上流のサービスも、応答を待つあいだ自分のスレッドを握るので、上流でも同じことが起こりえます。

スレッドプールの枯渇が起こりうる場合、どうするべきかを考えていきます。下流がどれだけ遅くなったら、何本のスレッドが何秒で尽きるのか。タイムアウトは何秒にすればいいのか。リトライは助けになるのか。

この記事では、これをリトルの法則 L = λW で計算してみます。平常時のピークに耐えられるかだけでなく、下流が遅くなったときにどのプールが何秒で尽きるかまで計算に入れて、タイムアウトや同時実行数の上限を決めます。この記事では、これを障害時のキャパシティプランニングと呼びます。

### やったこと

小さな注文 API（order-api）を作り、kind（Docker の中で動く Kubernetes）で動かしました。注文（POST /orders）は外部の決済 API を呼び、商品一覧（GET /products）は DB を読むだけです。

この決済 API の応答に5秒の遅延を入れて、スレッドとコネクションが何秒で尽きるかを先に計算し、それから実際に確かめます。そのあと、タイムアウトやバルクヘッドなどを1つずつ足していき、それぞれが L・λ・W のどれを変えるのかを見ていきます。

先に結果を見せてしまうと、何も設定していない状態では、決済 API を呼ばない /products まで成功率が1.0%に落ちて、order-api は4回再起動しました。

### 対象とゴール

Tomcat や HikariCP のようなプールを使うサーバーを書いている人、運用している人に向けて書いています。例は Spring Boot（Kotlin）ですが、プールを持つサーバーなら、同じように考えられます。

読み終えたときに、自分のサービスで「下流が遅くなったら、どのプールが何秒で尽きるか」を計算でき、タイムアウト・バルクヘッド・サーキットブレーカー・リトライが L = λW のどこに効くのかを説明できる。これがこの記事のゴールです。タイムアウトとバルクヘッドの値は計算で決め、サーキットブレーカーが開くまでの時間と、リトライを入れたときの W は計算で確かめます。

WebFlux やコルーチン、仮想スレッドの話はしません。ノンブロッキングのクライアントや仮想スレッドで書くと、リクエストを処理するスレッドの数という上限がなくなるかわりに、コネクションの数や、下流を同時に呼ぶ数の上限に先に達します。スレッドの数が下流を同時に呼ぶ数を制限していた分もなくなるので、バルクヘッドのような明示的な上限が要ります。負荷が増えたときに応答時間がどう伸びるかも扱いません。リトルの法則は平均どうしの関係なので、そこまでは教えてくれません。

数字は、とくに断りがなければ1回の実行の値です。計測は1秒ごとなので、「何秒で尽きたか」には1秒ほどの幅があります。細かい条件や補足は、折りたたみと付録にまわしました。

## TL;DR

- 下流の応答を待つあいだスレッドやコネクションを握る（確保したまま返さない）処理は、下流が遅くなると共有のプールを埋める。その下流を呼ばない処理とヘルスチェックも、プールの空きを待つうちにタイムアウトして失敗する
- 「その下流を呼ぶ処理の1台あたりの到着率 λ × 1件が握る時間 W」がプールの大きさを超えると、プールは尽きる。尽きるまでの時間は、遅延の長さではなく「空いている数 ÷ 到着率」で決まる（遅延がこの時間より長いとき）
- 尽きていても CPU は上がらない。見るのは「使用中の数 ÷ プールの大きさ」
- 1件がスレッドを握る時間の合計（（接続のタイムアウト ＋ 応答のタイムアウト）× 試行回数 ＋ リトライの待ち ＋ コネクションの取得待ち）を、「プールの大きさ × 使ってよい割合 ÷ 1台あたりの、ピークの時間帯の到着率」以下にする。使ってよい割合は、ほかの処理が使う本数と、到着のばらつきの分を残した割合
- 応答のタイムアウトの下限は、下流の平常時の応答時間の p99.9（平常時にタイムアウトする呼び出しを0.1%までにする場合）
- 上限はプールごとに計算する。トランザクションの中で下流を呼ぶと、小さいコネクションプールで上限が決まり、下限を下回りやすい。そのときは、下流をトランザクションの外で呼ぶ
- 下限が上限を超えるなら、下流を同時に呼ぶ数に上限を付ける（バルクヘッド）。その数は、平常時に断ってよい率から決める
- 直近の一定時間で失敗率を数えるサーキットブレーカーは、呼ぶ率が変わらなければ、およそ「集計する期間 × 失敗率のしきい値」がたつまで開かない。そのあいだスレッドを握る数は、バルクヘッドで抑える
- liveness probe を業務と同じスレッドプールで受けると、プールが尽きるたびに再起動され、下流が直ったあとの回復も遅れる。業務のスレッドが尽きても再起動させたくないなら、業務のスレッドプールの外で受ける（管理ポートや tcpSocket の probe）

## リトルの法則

### L = λW

$$
L = \lambda W
$$

リトルの法則は、入って出ていくものを数えられるところなら、どこにでも当てはまります。この記事では、主にサーバーのスレッドプールに当てはめます。

- **L**：中にいる数の平均（スレッドプールなら、使用中のスレッドの数）
- **λ**：1秒あたりに入る数（スレッドを取ったリクエストの数）。プールに空きがあれば到着率と同じ
- **W**：1件が入ってから出るまでの時間の平均（1件がスレッドを握っている時間）

たとえば1秒に50件届き、1件が0.2秒で返るなら、平均すると50 × 0.2 = 10本のスレッドが使われています。到着の仕方や処理時間の分布によらず、平均どうしでこの関係が成り立つのが強みです。

3つの値のうち2つが分かれば、残りが決まります。

| 知りたいもの | 式 | 例 |
| --- | --- | --- |
| 同時に要る数 | L = λW | 1秒に100件 × 1件0.2秒 = 20本 |
| さばける率の上限 | λ = L ÷ W | 8本 ÷ 1件0.04秒 = 200件/秒 |
| 1件の平均の時間 | W = L ÷ λ | 平均5本 ÷ 1秒に100件 = 0.05秒 |

### 使うときの注意

注意したいことが3つあります。

1つめは、平均どうしの関係だということです。p99 の W から p99 の L は出ません。この記事の λW も、平均の W を使った値です。

2つめは、L と W を同じものについて測ることです。スレッドの L には、スレッドを握っている時間を W に使います。リクエストがスレッドの空きを待って並んでいる時間は、スレッドの W には入りません。

3つめは、落ち着いた状態でしか成り立たないことです。測る区間が W より十分長く、区間の始めと終わりで中にいる数がほぼ同じなら成り立ちます。プールが埋まっていく途中や、W より短い区間では成り立ちません。プールが埋まったあとは、λ を到着率ではなく、実際にプールに入る率にとると成り立ちます。これは、あとの実験で実際に見ます。

## 障害を L = λW で読む

### 下流が遅くなると、まず W が伸びる

下流が遅くなったとき、まず変わるのは W です。下流の応答を待つあいだスレッドを握る処理では、下流の応答時間がそのまま W に入ります。下流が100倍遅くなれば W もほぼ100倍になり、到着率が同じなら λW も100倍になります。

到着率のほうは、障害中にむしろ上がることがあります。ユーザーが再読み込みをしたり、上流がリトライしたりするからです。レプリカが複数あれば、readiness probe に失敗して Service から外れた Pod に送られていたリクエストが、残りの Pod に送られます。

### λW がプールの大きさを超えると、何が起きるか

スレッドを握ったまま遅い下流を待つ処理 A と、その下流を呼ばない処理 B（DB は使う）が、同じスレッドプールを使っているとします。

下流が遅くなって A の λW がプールの大きさを超えると、プールは A で埋まります。あとから来たリクエストは、A か B かに関係なく、1本の待ち行列に並んで空きを待ちます。B は遅い下流を呼ばないのに、待つ時間がクライアントのタイムアウトを超えると失敗します。A はスレッドを取れても、下流が返らないので失敗します。クライアントがあきらめたあとも処理は続くので、スレッドは握られたままです。

同じプールで liveness probe を受けていれば、probe も答えられず、コンテナが再起動されます。ところが、再起動しても、起動したとたんに同じ λW がまたプールの大きさを超えます。

レプリカを増やせば防げるかというと、少し増やすくらいでは防げません。到着がレプリカに分かれるだけなので、どのレプリカでも1台あたりの λW が同時にプールの大きさを超えます。防ぐには、1台あたりの λW がプールの大きさ（ばらつきの分を残すなら、プールの大きさ × 使ってよい割合。後述）を下回るまで台数を増やす必要があります。必要な台数は W に比例するので、遅延が長いほど現実的ではなくなります。

コネクションプールでも、同じことが起きます。A がトランザクションの中で下流を呼んでいれば、A はコネクションも下流の応答まで握ります。コネクションが先に尽きると、スレッドを取れた B も、コネクションの空きを待ってスレッドを握ります。こうなるとスレッドもコネクションも尽きるので、どちらか一方だけを大きくしても、B は失敗し続けます。

尽きるかどうかは、λW がプールの大きさを超えるかで決まります。どれが先に尽きるかは「空いている数 ÷ そのプールに入る率」で決まり、短いほうが先です。同じリクエストが2つのプールを握るなら、入る率は同じなので、小さいプールが先に尽きます。Tomcat（既定200本）と HikariCP（既定10本）を既定のまま使っていれば、コネクションのほうです。

遅くなったのは下流の1つだけなのに、こうして共有しているプールが尽き、サービス全体が止まります。どれだけの速さで尽きるかは、このあとの実験で計算します。

### それぞれの手段が変えるもの

L = λW は、プールのほかに、下流の呼び出しにも当てはまります。この記事では、次の2つを区別します。

| | スレッドプール（コネクションプールも同じ） | 下流の呼び出し |
| --- | --- | --- |
| L | 使用中のスレッドの数 | 下流を同時に呼んでいる数 |
| λ | スレッドに入るリクエストの率 | 下流を1秒に呼ぶ数 |
| W | 1件がスレッドを握る時間 | 1回の呼び出しを待つ時間 |

タイムアウトは、下流の呼び出しの W に上限を付けます。下流を待つあいだはスレッドも握っているので、スレッドプールの W にも上限が付きます。トランザクションの外で下流を呼ぶと、コネクションプールの W（コネクションを握る時間）から、下流の応答を待つ時間が抜けます。

バルクヘッドは、下流の呼び出しの L、つまり同時に呼ぶ数に上限を付け、上限を超えた分は待たせずにすぐ断ります。下流を待ってスレッドを握るのは同時実行数までになり、断られたリクエストがスレッドを握る時間はほぼ0になります。

サーキットブレーカーは、失敗が続いたら、しばらく下流を呼ばずにすぐ失敗を返します（呼ぶのを止めた状態を「開く」と言います）。下流の呼び出しの λ をほぼ0にし、開いているあいだは、リクエストがスレッドを握る時間もほぼ0になります。

リトライだけは向きが逆です。失敗した呼び出しをもう一度試すので、スレッドプールの W（試行と、その間の待ちの合計）が延び、下流の呼び出しの λ は最大で試行回数倍になります。

## 実験環境

### 構成

![全体の構成](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/architecture.ja.png)

order-api は Spring Boot 4.1（Kotlin、JDK 21、Resilience4j 2.4）で、Tomcat のスレッドは40本、HikariCP のコネクションは10本です。/orders・/products と、liveness probe の /livez・readiness probe の /readyz を、同じスレッドプールで受けます。

決済 API（payment-api）は、平均0.05秒・p99 0.12秒の対数正規分布で応答を返すモックです。スレッドは6本なので、1秒に約120件までさばけます。決済 API の手前には Toxiproxy（通信に遅延などを入れられるプロキシ）を置き、クラスタの外から scenarios/run.sh で遅延を入れたり外したりします。

負荷は k6 で、応答の速さに関係なく一定の率で送ります（オープンモデル）。/orders は1秒に60件、/products は10件で、k6 は5秒でタイムアウトします。k6 は応答を待つ1件に1 VU（仮想ユーザー）を使うので、要る VU の数もリトルの法則で決まります。/orders なら60件/秒 × 5秒 ＝ 300で、これより少し多い数を最初から用意しました。

コードと設定、計測の生の値は [リポジトリ](https://github.com/rea9r/littles-law-resilience-lab) にあります（動かし方は付録）。

:::message
VU の数を固定する負荷試験（クローズドモデル）では、スレッドが尽きる現象は小さく出るか、再現しません。VU は応答を待つあいだ次のリクエストを送らないので、応答が遅くなると到着率が勝手に下がるからです。オープンモデルでも、VU を途中で作り足す設定だと、作り足すあいだの到着を取りこぼします。
:::

:::details 計測のしかけと、規模の縮め方
order-api のメトリクスは、業務の40本とは別のスレッドで8081番から返します。40本が尽きると readiness probe にも失敗して Ready でなくなり、業務用の Service からは外れます。メトリクス用の Service は Ready でない Pod も返す設定（publishNotReadyAddresses）にしてあるので、そのあいだも Prometheus は1秒ごとに取りに行けます。

実験の設定を当てると、設定が変わったアプリの Pod だけが入れ替わります。

小さなクラスタで動くように、到着率やプールの大きさは、本番の規模の例（Tomcat の既定のスレッド200本など）の約1/5に縮めています。比率が同じなら、尽きるまでの秒数やタイムアウトの下限と上限は変わりません。変わるのは、バルクヘッドが断る率と、使ってよい割合です（後述）。
:::

### 1回の実験の手順と、測るもの

![1回の実験の手順](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/scenario-timeline.ja.png)

ウォームアップは、JIT のコンパイルやコネクションプールが落ち着くまで待つ区間で、何も測りません。0秒の前にも、設定の適用と Pod の入れ替えに1分ほどかかり、全体では約7分です。図の下の括弧が、どの値をどの区間で測るかを表しています。

- **平常時**：使用中のスレッドの数と、メトリクスから測った λW（後述）が一致すること、成功率
- **障害中**：成功率（エンドポイントごとに区間全体の割合）、使用中のスレッドの平均と最大、コネクションの取得待ちの数の最大
- **スレッドが尽きるまで**：障害から15秒のあいだの1秒ごとの計測で、初めて40本になった時刻（実際にはこれより早く尽きていることがある）
- **回復までの時間**：遅延を外してから、/orders と /products の成功率がどちらも99%以上に戻るまで（そのあと15秒続いた場合だけ回復とみなす）。120秒のうちに戻らなければ「戻らない」
- **再起動の回数**：負荷をかけているあいだ全体で数える

回復の判定では、戻った時刻のずれを小さくするために、成功率を直近6秒で数えています。そのため、すぐに戻っても6〜7秒と出ます。記事に載せたグラフの成功率は、線を見やすくするために直近10秒で数えています。

## 何も設定せずに、決済 API を遅くする

### 設定

最初は、タイムアウトなどを何も設定しない状態です。

- 決済 API のタイムアウトは30秒
- 決済 API をトランザクションの中で呼ぶ（注文を仮登録 → 決済 API で与信 → 確定、を1つのトランザクションで行う書き方）
- HikariCP の取得待ちのタイムアウト（`connection-timeout`）は、既定の30秒

```kotlin:OrderService.kt
tx.execute {
    val orderId = insertOrder(productId, quantity, "PENDING")
    paymentClient.authorize() // 決済 API を待つあいだも、コネクションを握ったまま
    jdbc.sql("update orders set status = 'CONFIRMED' where id = ?").param(orderId).update()
    orderId
}
```

### 予測

まずは計算してみます。「障害を L = λW で読む」の処理 A がこの実験の /orders、処理 B が /products です。

決済 API の応答が0.05秒から5.05秒になると、/orders が同時に握るスレッドの数は、λW = 60件/秒 × 5.05秒 ≈ 300本です。スレッドは40本しかないので、まったく足りません。

![障害の前後のスレッドプール](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/failure-spread.ja.png)
*計算（実測ではない）。スレッドだけを描いた単純化です。コネクションを含めた計算は、このあとの本文にあります*

では、障害が始まってから何秒で40本が埋まるのでしょうか。到着を等間隔にして、1件ずつスレッドを握っていく様子を計算したのが次の図です。

![障害の直後にスレッドが埋まっていく様子（計算）](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/thread-timeline.ja.png)
*計算（実測ではない）。1行が1本のスレッドで、縦に切ったときに交わる棒の数が、その瞬間の L です*

障害の前は、0.05秒の短い棒が上の3行を入れ替わりで使っています（/products は1ミリ秒足らずで返るので、棒は描いていません）。

障害の時点で処理中だった3件も応答が遅れるので、空いているのは37本です。そこに1秒あたり60件ずつリクエストが入ってきて、5秒たつまで1件も終わらないので、37 ÷ 60 ≈ 0.6秒で尽きます。

ここで大事なのは、この0.6秒が遅延の長さと関係ないことです。1件がスレッドを握る時間が0.6秒より長ければ、遅延が5秒でも30秒でも、同じ0.6秒で尽きます。尽きるまでの時間を決めるのは「空いている数 ÷ 到着率」です。

プールが無限に大きかったとしても、すぐに300本になるわけではありません。1.0秒の時点では63本です。300本で落ち着くのは、最初のリクエストが終わり始めて、増える数と終わる数が釣り合う5秒後からです。

ところで、L = λW の λ を「到着率」と書いてきましたが、正確には「プールに実際に入る率」です。0.6秒から5秒までは空くスレッドがないので、1件も入れません。入る率も出ていく率も0で、L は40のままですが、中の40件はまだ1件も5.05秒を終えていません。W より短い区間なので、ここでは L = λW は成り立ちません。5秒をすぎると、1本のスレッドが5.05秒ごとに空き、空いた分だけ入れ替わりに入ります。スレッドだけで数えると、/orders が入る率は40 ÷ 5.05 ≈ 8件/秒で、ここからは40本 ≈ 8件/秒 × 5.05秒と、L = λW が成り立ちます。入れなかったリクエストは、Tomcat の待ち行列で待ち続けます。

実は、ここまではスレッドだけを数えた単純化です。この実験では決済 API をトランザクションの中で呼ぶので、先にコネクション10本が(10 − 3) ÷ 60 ≈ 0.12秒で尽きます。そのあとは /products もコネクションを待ちながらスレッドを握ります。0.12秒の時点で使用中のスレッドは10本なので、残りの30本が1秒に70本ずつ埋まり、スレッドは0.12 ＋ 30 ÷ 70 ≈ 0.55秒で尽きる計算です。尽きたあとにスレッドに入る率も8件/秒ではなく、コネクションを5.05秒ずつ握る /orders が終わる1秒に約2件（10 ÷ 5.05）になります。

というわけで、予測はこうなります。

- 障害から約0.55秒で、スレッド40本が尽きる
- /products は待ち行列で待つうちに、k6 の5秒のタイムアウトを過ぎて失敗する
- liveness probe も答えられず、再起動が繰り返される
- スレッドは待っているだけなので、CPU は上がらない

:::details 尽きたあと、1件がスレッドを握る時間
スレッドに入る率が1秒に約2件なので、W = L ÷ λ から、落ち着けば1件がスレッドを握る時間は、コネクションの取得待ちを含めて40 ÷ 2 ≈ 20秒まで伸びる計算です。実際には15秒ほどで再起動が始まるのでそこまでは届かず、返った1件の処理時間の平均は9.9秒でした。
:::

### 決済 API を呼ばない /products まで止まり、再起動を繰り返す

障害中の120秒の成功率は、/orders が0.3%、決済 API を呼ばない /products も1.0%でした（はじめにのグラフ）。/products の失敗のうち91%は k6 の5秒のタイムアウトで、スレッドの空きを待つうちに5秒を過ぎています。残りは、再起動のあいだや、readiness probe に失敗して Ready でなかったあいだに、接続を断られた分です。

見落としやすいのは、order-api 側のメトリクス（`http_server_requests`）では、同じ区間の /products がすべてステータス200で、エラーが1件も記録されていなかったことです。k6 があきらめたあとに処理した分も、200として数えられます。サーバー側の成功率だけを見ていたら、この障害は成功率100%に見えていたことになります。

![何も設定しない状態のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/threads.png)
*40本の横ばい → 階段状に下がる → 再起動、を繰り返しています。線が途切れているのは再起動のあいだです*

order-api は障害中に3回再起動し、遅延を外す直前にもう1回止まり始めました（合わせて4回。新しいコンテナが起動したのは、遅延を外して約25秒後）。1回分は、次の順に進みました。

1. 40本が尽きると、/livez も待ち行列に並んで答えられません。liveness probe（5秒ごと、1秒でタイムアウト、3回続けて失敗したら再起動）が失敗し続け、Kubernetes がコンテナを止めにかかります
2. 止めるとき、Spring Boot は新しいリクエストを受け付けず、処理中のものが終わるのを待ちます（graceful shutdown。Spring Boot 3.4 以降の既定）。障害の約15秒後から、スレッドは約5秒ごとに40 → 29 → 17 → 6本と、11本ほどずつ減りました。コネクション10本を5.05秒ずつ握る /orders が10件ずつ終わり、そのたびに、コネクションを取れた /products が1件ほどすぐに終わるからです。予測に書いた「1秒に約2件」が、ここで見えています
3. 新しいコンテナが受け付けを始めると、1秒足らずでまた40本が尽きます

40本が尽きた状態は再起動のたびに途切れ、続いても約20秒でした。liveness probe が「5秒 × 3回」失敗すると、止めにかかるからです。

障害中の再起動では、何も解決しません。起動したとたんに、同じ λW がまたプールの大きさを超えるからです。それどころか、処理中のリクエストを待つ graceful shutdown、JVM の起動、Kubernetes が延ばしていく再起動の間隔のぶんだけ、下流が直ったあとの回復も遅れます。この実験では、遅延を外してから戻るまで38秒かかりました。

### CPU は上がらない

![何も設定しない状態の CPU 使用率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/cpu.png)

障害が始まってから最初の再起動までの約30秒、order-api の CPU 使用率は平均7%で、平常時の20%より下がっていました。スレッドは決済 API とコネクションを待っているだけで、計算をしていないからです。障害中の平均は16%ですが、これには再起動のあとの JVM の起動が入っています。CPU を見ていても気づけませんし、CPU を基準にしたオートスケールも動きません。

### この章でわかったこと

スレッドやコネクションを握ったまま下流を待つ処理があると、下流が遅くなっただけで、同じプールを使うほかの処理やヘルスチェックまで空きを待たされ、タイムアウトしていきます。尽きるまでの時間は遅延の長さではなく「空いている数 ÷ 到着率」で決まるので、到着率が高ければ1秒もかかりません。そのあいだ CPU は上がりません。下流が遅いままなら、再起動しても、起動したとたんにまた同じようにプールが尽き、下流が直ったあとの回復も遅れます。

## タイムアウトとトランザクションの範囲で、W に上限を付ける

### タイムアウトは何秒にすればいいか

W に上限を付けるいちばんの手段は、下流の呼び出しのタイムアウトです。とはいえ、短すぎれば平常時にも失敗しますし、長すぎれば障害時にスレッドが尽きます。そこで、タイムアウトに設定してよい値の下限と上限を、先に計算しておきます。

#### 下限：平常時にタイムアウトさせてよい割合から決める

この記事では、平常時にタイムアウトさせてよいのを0.1%までとし、下限を下流の平常時の p99.9 にとります。この実験の決済 API はモックで、応答時間を平均 50ms・p99 120ms の対数正規分布にしてあります。この分布から計算すると、p99.9 は約 165ms です。実際のサービスでは、平常時の計測から取ります（取り方は点検の章）。

#### 上限：プールの大きさ × 使ってよい割合 ÷ 1台あたりのピーク時の到着率

決済 API が完全に返らなくなると、/orders 1件はタイムアウトまでスレッドを握るので、W はタイムアウトの値そのものになります。λW がスレッドの数に収まるには「タイムアウト ≤ スレッドの数 ÷ 到着率」が条件で、40 ÷ 60 ≈ 0.67秒です。これは1件がスレッドを握ってよい時間の上限で、前の章の0.6秒（尽きるまでの時間）とは別の量です。

ただ、40本ぎりぎりまで使う前提にはできません。ほかの処理が使う本数と、到着のばらつきの分を残しておく必要があります。そこで、プールの大きさに「使ってよい割合」を掛けます。

使ってよい割合は、次のように見積もれます。下流を呼ぶ処理が障害時に同時に握る数の平均を m とします。到着がランダムなら、同時に握る数は平均 m のポアソン分布に近く、標準偏差は √m で、平均 ＋ 3 × 標準偏差を超えるのは0.1%ほどです。そこで「m ＋ 3√m ＋ ほかの処理が使う本数」がプールの大きさに収まる m を求め、m ÷ プールの大きさを割合にします。ほかの処理がほとんど使わないなら、スレッド40本で約0.6、200本で約0.8です。この実験は到着が等間隔でばらつきが小さいので0.7とし、40 × 0.7 ÷ 60 ≈ 0.467秒（467ms）を上限にしました。

到着率には、その下流を呼ぶ処理の、1台（1 Pod）あたりの、ピークの時間帯の到着率（1分ほどの平均）を使います。秒単位のばらつきは、使ってよい割合の3√m で見込んでいます。障害中に到着率が上がりうることも見込みます。なお、ここでは遅くなる下流は1つだけと仮定しています。

![スレッドで見たタイムアウトの下限と上限](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/timeout-range-threads.ja.png)

この図からは、次のことが読み取れます。

- 灰色の帯（0〜165ms）は、下限（決済 API の平常時の p99.9）より短いタイムアウトで、平常時の呼び出しの0.1%より多くがタイムアウトする
- 赤い帯（467ms〜）は、上限（40 × 0.7 ÷ 60）より長いタイムアウトで、障害時にスレッドが尽きる
- 2本の帯のあいだ（165〜467ms）なら、平常時のタイムアウトは0.1%以下で、障害時にもスレッドが尽きない
- この実験では 300ms を設定した（平常時にタイムアウトするのは、計算で0.001%以下）

タイムアウトは、HTTP クライアントの応答のタイムアウトに設定します。

```kotlin:PaymentClient.kt
JdkClientHttpRequestFactory(
    HttpClient.newBuilder().connectTimeout(props.payment.connectTimeout).build(),
).apply { setReadTimeout(props.payment.timeout) } // 応答のタイムアウト（何も設定しない状態は 30 秒、遅い決済 API は 800ms、ほかは 300ms）
```

:::message
上限と比べる値は、ほかにもあります。

上流（クライアント）のタイムアウトもその1つです。1件の W の最大値（タイムアウト × 試行回数 ＋ リトライの待ち）がこれより長いと、誰も待っていない処理にスレッドを使うことになります。何も設定しない状態の障害中、order-api が返した1件の処理時間は平均9.9秒で、k6 は5秒でとうにあきらめていました。

接続のタイムアウトも見落としやすい値です。この実験の接続のタイムアウトは1秒で、上限の 467ms より長い値です。下流が接続を受け付けなくなる障害では、ここが W になります（この実験では接続の障害を起こさないので、1秒のままにしています）。
:::

### タイムアウトを 300ms にしてみる

「タイムアウトだけ」の実験です。決済 API のタイムアウトを 300ms にし、ほかは何も変えません。

#### 予測

スレッドだけを見れば、λW は60件/秒 × 0.3秒 = 18本で、40本に収まります。ところが、決済 API はトランザクションの中で呼んだままです。コネクションも0.3秒握るので、コネクションの λW も18本になり、10本を超えてしまいます。

コネクション10本を0.3秒ずつ握ると、1秒に10 ÷ 0.3 ≈ 33件しか通せず、到着の60件より少なくなります。残りの /orders と /products は、スレッドを握ったままコネクションの空きを待ちます。取得待ちのタイムアウトは HikariCP の既定の30秒と長いので、早めにあきらめて返ることもありません。計算すると、障害から約0.85秒でスレッドも40本が尽きます。

:::details 約0.85秒の計算
- 0〜0.12秒：コネクションが(10 − 3) ÷ 60 ≈ 0.12秒で尽きる。スレッドは約10本
- 0.12〜0.3秒：最初のタイムアウト（0.3秒）まで、終わるリクエストはない。/orders と /products の1秒70件がそのままスレッドを握り、0.3秒で約23本
- 0.3秒〜：コネクションを握った /orders が1秒に約33件終わる。取得待ちには /orders 6件につき /products 1件の割合で並んでいて、/products はコネクションをすぐ返すので、/orders が33件コネクションを取るあいだに /products も約5.5件（33 × 10/60）取って終わる。スレッドは1秒に70 − 33 − 5.5 ≈ 31本ずつ増え、残り17本が約0.55秒で尽きる
:::

#### 結果

![タイムアウトだけの HikariCP](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01a-timeout/results/panels/hikari.png)
*実線が使用中、点線が取得待ちの数、薄い破線がプールの大きさです。障害の直後から10本とも使われ、取得待ちの数が30前後まで増えています。途切れているのは再起動のあいだです*

コネクションは障害の直後から10本とも使われ、取得待ちの数は30前後まで増えました（最大の31は、再起動の直後でコネクションがまだ9本しかなかったときの計測で、40 − 9 = 31です）。スレッドは障害の0.86秒後の最初の計測で39本、1.86秒後に40本で、計算の約0.85秒とほぼ合っています。再起動は5回でした。order-api が受け付けているあいだ、決済 API への呼び出しは1秒に30〜37件で、計算の33件どおりです（再起動で止まっていた約50秒を含めた障害中の平均は17件/秒）。

/products の成功率は12.3%で、何も設定しない状態の1.0%より少しだけ通りました。通ったのは、障害の始まりの約12秒と、再起動の直後の数秒ずつだけです。どちらも、待ち行列がまだ短いあいだです（成功した約140件のうち約半分は、最初の再起動より前）。1秒に33件ほどコネクションを取れるので、待ち行列が短いうちは /products も k6 の5秒以内に順番が来ます。何も設定しない状態では、5.05秒に10件しかコネクションを取れなかったのとは対照的です。ただ、待ち行列が伸びれば、また5秒を超えます。タイムアウトを設定しても、/products の失敗は続きました。

なぜでしょうか。上限は、プールごとに計算する必要があったのです。決済 API をトランザクションの中で呼ぶと、決済 API のタイムアウトはコネクションを握る時間にもなります。コネクション10本で計算し直すと、次のようになります。

![コネクションで見たタイムアウトの下限と上限](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/timeout-range-connections.ja.png)

- コネクションで計算した上限（10 × 0.7 ÷ 60 ≈ 117ms）は、下限（決済 API の平常時の p99.9、165ms）より短い
- 2本の帯が重なるので、どの値にしても、平常時のタイムアウトが0.1%を超えるか、障害時にコネクションが尽きる
- 設定した 300ms は上限より長いので、障害時にコネクションが尽きた
- 到着がランダムなら、コネクション10本の使ってよい割合は約0.4で、上限はさらに短い（約 67ms）

タイムアウトの値をどう変えても解決しません。そこで、決済 API を待つあいだコネクションを握らないようにします。

もう1つ、コネクションの取得待ちのタイムアウトが既定の30秒だったことも、/products がスレッドを握ったまま待ち続けた理由です。スレッドを握ったまま待つ場所（下流の応答、コネクションの取得、リトライの待ち）ごとに、W の上限を確かめる必要があります。

### 決済 API をトランザクションの外で呼ぶ

「トランザクションの外で呼ぶ」実験です。決済 API を先に呼び、コネクションを握るのは DB に書き込む一瞬だけにします。あわせて HikariCP の取得待ちのタイムアウトを 250ms（設定できる最小値）に縮めましたが、この実験ではコネクションの取得待ちが起きない（取得待ちの数は0のまま）ので、結果にはほぼ効いていません。

```kotlin:OrderService.kt
paymentClient.authorize() // 決済 API はトランザクションの外で、先に呼ぶ
tx.execute { insertOrder(productId, quantity, "CONFIRMED") }
```

:::message
本番では、整合性の扱いが別に必要です。タイムアウトした与信は「失敗」ではなく「結果が分からない」状態です。「PENDING を短いトランザクションで書く → トランザクションの外で与信 → 別の短いトランザクションで確定」の形にすれば、コネクションを握らずに、照合のための記録も残せます。リトライするなら、同じ冪等キーで送り直せることが前提です（あとで見るリトライも同じです）。この記事では、スレッドとコネクションを握る時間の違いだけを見ます。
:::

#### 予測

コネクションを握るのは書き込みの数ミリ秒だけになるので、コネクションの λW は1本未満です。スレッドの λW は60 × 0.3 = 18本で、40本に収まります。/orders は0.3秒でタイムアウトして失敗を返し、/products は影響を受けないはずです。

#### 結果

使用中のスレッドの数（L）と、メトリクスから測った λW を同じグラフに描いてみると、L = λW が実際に成り立っているのが分かります。

![実測の L と測った λW](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/littles-law.png)
*緑が使用中のスレッド（実測の L）、黄が測った λW（グラフの凡例では λ×W）です。平常時は約3本、障害中は約18本で重なっています。黄は直近10秒の平均なので、切り替わりの直後は遅れて追いつきます*

:::details λW をメトリクスから測る
Spring Boot（Micrometer）は、リクエストごとの処理時間を `http_server_requests_seconds` に記録し、合計（`_sum`）と件数（`_count`）を出します。合計の増え方 `rate(_sum)` は「1秒に終わった件数 × その平均時間」なので、λW を測った値になります。

```promql
sum by (pod) (rate(http_server_requests_seconds_sum{uri=~"/orders|/products"}[10s]))
```

終わったリクエストしか数えないので、終わらないリクエストが増えていくあいだ（プールが尽きて再起動を繰り返しているときなど）は、使用中のスレッドの数から離れます。平常時の使用中のスレッドの数は、測った λW より、実験によって0.2本少なくも0.4本多くも出ました。整数の本数を1秒ごとに60回測った平均なので、ぶれが入ります。
:::

![トランザクションの外で呼ぶときの成功率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/success.png)
*/orders（紫）は失敗しますが、/products（青緑）は100%のままです。成功率は直近10秒で数えているので、斜めに下がって見えます*

障害中のスレッドは平均18.1本（最大22本）で、計算の18本どおりでした。測った λW も18.1本で、2本の線が重なっています（平常時は使用中のスレッドが3.4本、測った λW が3.1本）。/products の成功率は100%、再起動は0回で、遅延を外してから7秒で戻りました（測り方の下限に近い値です）。/orders は失敗しますが（成功率0.5%）、失敗が0.3秒で返るので、スレッドを使い切ることはありません。

### この章でわかったこと

タイムアウトの下限は、平常時にタイムアウトさせてよい割合から決まります（0.1%までなら p99.9）。上限は「プールの大きさ × 使ってよい割合 ÷ 下流を呼ぶ処理の1台あたりのピーク時の到着率」で、比べるのは、接続のタイムアウトとリトライも足した、1件が握る時間の合計です。上流のタイムアウトより短くすることも必要です。

この上限は、プールごとに計算します。スレッドを握ったまま待つ場所（下流の応答、コネクションの取得、リトライの待ち）のすべてに、上限を付けておきます。下限が上限を超えるプールがあれば、タイムアウトの値をいじるのではなく、そのプールを握らない形に変えます（トランザクションの外で下流を呼ぶ）。

## バルクヘッドで、下流を同時に呼ぶ数に上限を付ける

### タイムアウトでは解決できない下流

「トランザクションの外で呼ぶ」実験で /products が100%のままだったのは、決済 API の p99.9（165ms）が、スレッドで見た上限（467ms）より十分に短かったからです。

では、p99 が長い下流だったらどうでしょうか。下限が上限を超えると、どのタイムアウトにしても、平常時のタイムアウトが0.1%を超えるか、障害時にスレッドが尽きるかのどちらかになります。外部の決済代行のように、p99 が秒単位の下流もあります。たとえば Tomcat の200本で、1台あたり1秒に100件を受けるなら、上限は200 × 0.7 ÷ 100 ＝ 1.4秒です。下流の p99.9 が2秒なら、下限が上限を超えてしまいます。

これを試すのが「遅い決済 API」の実験です。トランザクションの外で呼ぶ形のまま、決済 API を平均 100ms・p99 600ms に遅くし（決済 API のスレッドを6本から12本に増やして、1秒にさばける件数は120件のまま）、タイムアウトを 800ms にしました。どの値でも、平常時にタイムアウトする呼び出しを目標の0.1%までには抑えられません。そこで平常時の失敗を1%まで許すことにし、平常時にタイムアウトする呼び出しが1%を下回る 800ms を選んでいます。

#### 予測

![p99 が長い下流の、タイムアウトの下限と上限](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/timeout-range-slow-downstream.ja.png)

- モックに設定した分布から計算すると、p99.9 は約1.3秒で、これが下限になる。上限（40 × 0.7 ÷ 60 ≈ 467ms）を超えている
- 2本の帯が重なるので、どの値にしても、平常時のタイムアウトが0.1%を超えるか、障害時にスレッドが尽きる
- 設定した 800ms は、平常時のタイムアウトが約0.4%の長さで、上限より長い

障害時の λW は60 × 0.8 = 48本で、40本を超えます。平常時に使っているのは約6本（60 × 0.1）なので、空いている約34本が1秒に60本ずつ埋まり、約0.57秒でスレッドが尽きる計算です。

#### 結果

障害のあとの最初の計測は0.48秒後でした。平常時の使用中のスレッドは6.6本だったので、計算では6.6 ＋ 60 × 0.48 ≈ 35本です。実測は33本で、1.48秒後には40本になりました。障害中の /products の成功率は25.3%、再起動は5回です。

平常時の /orders の成功率は99.4%で、約0.6%がタイムアウトしていました（計算は約0.4%）。

### バルクヘッドを入れる

タイムアウトの値で解決しないなら、W ではなく L に直接上限を付けます。「遅い決済 API ＋ バルクヘッド」の実験です。

Resilience4j の Bulkhead（セマフォで同時実行数を数える型）で、決済 API を同時に呼ぶ数（同時実行数）を12までにし、上限に達していたら待たずに断ります。断られた /orders は、すぐに失敗を返します。

```yaml:application.yml
resilience4j:
  bulkhead:
    instances:
      payment:
        max-concurrent-calls: 12
        max-wait-duration: 0ms # 上限に達していたら待たずに断る
```

この実験では、バルクヘッドだけの効果を見るために、タイムアウトは 800ms のまま変えていません。バルクヘッドでスレッドを握る数を抑えれば、タイムアウトは下限の p99.9 まで延ばせます（点検の章の計算例）。

#### 予測

決済 API を待ってスレッドを握る /orders は、最大12本です。バルクヘッドを通れる率は λ = L ÷ W = 12 ÷ 0.8 = 15件/秒で、残りの約45件/秒はすぐに断られます。スレッドは12本と少しで、40本に収まるはずです。

#### 結果

![遅い決済 API ＋ バルクヘッドの、決済 API の呼び出し](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/02b-bulkhead/results/panels/payment-calls.png)
*緑が成功、黄が失敗（0.8秒のタイムアウト）です。バルクヘッドに断られた分は、決済 API まで届かないので数に入っていません*

障害中に決済 API まで届いた呼び出しは14.9件/秒で、計算の15件/秒どおりでした。スレッドは障害中も12本前後で、最大13本です。/products の成功率は100%、再起動は0回で、遅延を外してから9秒で戻りました。

### 同時実行数はいくつにするか

バルクヘッドの同時実行数は、小さすぎれば平常時にも断り、大きすぎれば障害時にスレッドを多く握ります。最小の目安は平常時の同時実行数とそのばらつき（平均 ＋ 3√平均）で、最大の目安はほかの API の分を残したスレッドの数（40 × 0.7 ＝ 28）です。

12は、平常時の L（60件/秒 × 0.1秒 ＝ 6）の2倍で、最小の目安（6 ＋ 3√6 ≈ 13）より少し小さい値です。この環境で平常時に断った呼び出しは、1分に1件ほど（約3,600件中）でした。ただしこれは、k6 がリクエストを等間隔に送っているからです。

到着がランダム（ポアソン到着）なら、断る率はアーランの B 式で計算できます。同時に使える数が決まっていて、空いていなければ断る仕組みで、断る確率を出す式です。平常時の同時実行数の平均（到着率 × 平均の応答時間）を a、同時実行数を n とすると、B(0) = 1から B(k) = a·B(k−1) ÷ (k ＋ a·B(k−1)) を k = n まで繰り返した B(n) が、断る率になります。a = 6なら、次のとおりです。

| 同時実行数 | 平常時に断る率 |
| --- | --- |
| 12 | 約1.1% |
| 14 | 約0.2% |
| 16 | 約0.03% |

つまり12は、ランダムな到着なら平常時に約1.1%を断る値です。本番なら、断る率を0.2%までにするなら14、0.03%までなら16にします。

「平常時の L の2倍」という倍率は、規模によって意味が変わります。同じ2倍でも、平均30・同時実行数60なら、断るのは100万件に1件以下です。同時実行数は倍率ではなく、断ってよい率から決めます。

### この章でわかったこと

下流の p99 が長く、タイムアウトの下限が上限を超えるなら、タイムアウトではなく、下流を同時に呼ぶ数に上限を付けます。バルクヘッドを通れる率は「同時実行数 ÷ W」で決まり、上限を超えた分は待たせずにすぐ断ります。待たせると、断るまでの時間が新しい W になってしまうからです。同時実行数は、平常時の同時実行数とばらつきをもとに、断ってよい率から決めます。大きくしても、ほかの処理の分を残したスレッドの数までです。

## リトライとサーキットブレーカー

### リトライを足すと、300ms でもスレッドが尽きる

「リトライ」の実験です。トランザクションの外で呼ぶ形（タイムアウト 300ms）に、Resilience4j の Retry を足します。最大3回試行し（初回を含む）、試行の間に 500ms 待ちます（どちらも Retry の既定値）。決済のように副作用のある呼び出しは、冪等キーがない限りリトライしてはいけません（トランザクションの外で呼ぶ実験の注）。ここでは、スレッドと呼び出しの数の動きだけを見ます。

#### 予測

1件の W は、最大3 × 0.3 ＋ 2 × 0.5 ＝ 1.9秒です。試行の間の待ちのあいだも、スレッドは握ったままです。λW は60 × 1.9 = 114本で40本を超え、(40 − 3) ÷ 60 ≈ 0.6秒でスレッドが尽きます。リトライがなければスレッドが尽きなかった 300ms でも、リトライを足すと尽きてしまいます。

1件あたりの試行は最大3回に増えますが、決済 API を呼ぶ率は3倍の180件/秒にはなりません。スレッドが40本を超えられないので、「40本 × 3回 ÷ 1.9秒 ≈ 63件/秒」が上限です。

#### 結果

障害の0.55秒後の最初の計測で37本（計算は36本）、1.55秒後に40本でした。同じ設定で8回回し、障害中の /products の成功率は7.4〜8.3%、再起動はどの回も5回でした。

障害中に決済 API が受けた呼び出しは平均30件/秒で、上限の63件/秒より少なく、リトライのない「トランザクションの外で呼ぶ」実験の60件/秒よりも少なくなりました。再起動のあいだは0になるからです。1件あたりの試行は増えても、スレッドプールの大きさが、決済 API を同時に呼ぶ数の上限として働いたことになります。仮想スレッドや非同期の呼び出しでは、この上限がありません。

### サーキットブレーカーを足す

「リトライ ＋ サーキットブレーカー」の実験です。リトライの形に Resilience4j の CircuitBreaker（以下、ブレーカー）を足します。

直近10秒の呼び出しで失敗率を数え（集計する期間）、呼び出しが20回以上（最低の呼び出し数）あって失敗率が50%以上（失敗率のしきい値）なら開く設定にしました。開いている5秒は決済 API を呼ばずにすぐ失敗を返し、そのあと半開に移ります。半開では試しに10回だけ呼び、成功すれば閉じて元に戻り、失敗が多ければまた開きます。

```yaml:application.yml
resilience4j:
  circuitbreaker:
    instances:
      payment:
        sliding-window-type: TIME_BASED # 直近の一定時間で数える（既定は直近の呼び出し回数で数える COUNT_BASED）
        sliding-window-size: 10 # 秒
        minimum-number-of-calls: 20
        failure-rate-threshold: 50
        wait-duration-in-open-state: 5s
        permitted-number-of-calls-in-half-open-state: 10
        automatic-transition-from-open-to-half-open-enabled: true
  retry:
    instances:
      payment:
        ignore-exceptions: # 断られた呼び出しはリトライしない
          - io.github.resilience4j.bulkhead.BulkheadFullException
          - io.github.resilience4j.circuitbreaker.CallNotPermittedException
```

設定は、インスタンス名（payment）で取り出して、呼び出しを包みます。この記事のコードでは、アノテーションではなく関数で包んでいます。

```kotlin:PaymentClient.kt
private val circuitBreaker = circuitBreakerRegistry.circuitBreaker("payment") // application.yml の payment の設定
...
var call = Supplier { restClient.post().uri("/payments/authorize").retrieve().toBodilessEntity() }
call = Bulkhead.decorateSupplier(bulkhead, call) // バルクヘッドを設定した実験だけ
call = CircuitBreaker.decorateSupplier(circuitBreaker, call)
call = Retry.decorateSupplier(retry, call) // 最後に包んだものが一番外側
call.get()
```

包む順は Retry(CircuitBreaker(Bulkhead(呼び出し))) で、リトライが一番外側です（`@Retry`・`@CircuitBreaker`・`@Bulkhead` のアノテーションを重ねたときの既定の順序と同じ）。試行のたびにブレーカーを通り直し、ブレーカーに断られた呼び出しはリトライしません。

#### 予測（これは外れました）

最初は「失敗が20回たまれば開く」と読んでいました。最初の失敗が返るのはタイムアウトの0.3秒後で、そこから1秒に60件ずつ失敗するので、0.3 ＋ 20 ÷ 60 ≈ 0.63秒で開くはずです。開いているあいだは決済 API への呼び出しがほぼ0になり、/orders はすぐ失敗を返すので、W もほぼ0になります。

#### 結果

ところが、ブレーカーの状態のメトリクスを見ると、障害の3.91秒後の計測ではまだ閉じていて、開いていたのは4.91秒後でした。予測より4秒以上も遅れています。

![リトライ ＋ サーキットブレーカーの、決済 API の呼び出し](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03b-circuit-breaker/results/panels/payment-calls.png)
*緑が成功、黄が失敗（タイムアウト）です。1秒に約60件の失敗が約4.7秒続いても、直近10秒の平均なので30件ほどの山に見えます。開いたあとは、5秒ごとの半開の試しだけが届いています*

開いてからは、予測どおりでした。開いているあいだに決済 API が受けた呼び出しは、半開の10回 ÷ 約5秒で1秒に約2件です。開く前の約5秒を含めた障害中の平均は4.2件/秒で、トランザクションの外で呼ぶだけの形の60件/秒から大きく減りました。/products の成功率は100%、再起動は0回で、遅延を外してから11秒で戻りました。ブレーカーが開いているあいだは決済 API を呼ばないので、遅延が外れても次の半開まで（最大5秒）は戻れません。そのぶん、トランザクションの外で呼ぶだけの形の7秒より少し遅くなっています。

#### なぜ外れたのか

設定値の意味を読み違えていました。20回は、失敗率を計算し始めるのに要る呼び出しの数で、平常時の呼び出しだけですでに満たしています。開く条件は、直近10秒の呼び出しの半分以上が失敗であることです。

![ブレーカーが開く時刻の計算](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/breaker-window.ja.png)
*計算（実測ではない）。障害の直前に集計に残っていた成功の数（メトリクスで約550件）から計算しています*

障害の直前、集計には成功が約550件残っていました。集計は1秒単位の区切りで進むので、実際に残るのは約9秒分で、60件/秒 × 10秒の600件より少なくなります。障害が始まると、成功は1秒に約60件ずつ集計から抜けていきます。一方、失敗は0.3秒後から1秒に約60件ずつ増えます（スレッド40本が1.9秒に3回ずつ呼ぶので、40 × 3 ÷ 1.9 ≈ 63）。

失敗が成功に並ぶのは60 ×（t − 0.3）＝ 550 − 60t のとき、つまり障害から約4.7秒後で、実測と合います。障害中に呼ぶ率が平常時と同じくらいなので、おおよそ「集計する期間 × 失敗率のしきい値」（10秒 × 50%）になっているわけです。

既定の COUNT_BASED（直近の呼び出し回数で数える）なら、開くまでの時間はおよそ「集計する回数 × 失敗率のしきい値 ÷ 1秒あたりの失敗の数」です。既定の100回で、1秒に60件の失敗なら、最初の失敗から約0.8秒、障害からは約1.1秒になります。

### ブレーカーが開くまでの約5秒

![ブレーカーが開くまでのスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03b-circuit-breaker/results/panels/threads-fault.png)
*障害の5秒前から15秒後まで。赤い点線が障害の始まりです。ブレーカーが開くまでの約4秒、40本のままになっています*

開くまでの約5秒は、リトライの実験と同じことが起きています。/orders は1回目の失敗のあと、リトライの待ちのあいだもスレッドを握るので、40本が尽きます。スレッドは障害の0.91秒後から3.91秒後までの計測で40本のまま、4.91秒後に29本、5.91秒後に0本でした。

それでも /products は100%のままでした。待ち行列で待った時間が、k6 で測った最長でも約2.8秒で、k6 の5秒より短かったからです。最初に入った /orders は、3回の試行を終える約1.9秒後から順にスレッドを返すので、そのあいだも待ち行列は進みます。

ブレーカーが開くまでの約5秒にスレッドを握る数は、次の章でバルクヘッドを足して抑えます。

### 予想していなかったこと

遅延を外したあとにも、予想していなかったことが起きていました。order-api が再起動から戻った直後に、決済 API のスレッドが上限の6本になったままの時間が、リトライがあると延びていたのです（再起動のあと30秒のうち、リトライのない実験の5回で4〜6秒、リトライの8回で7〜20秒）。困るのは、そのあいだ下流が、さばける率いっぱいまで呼ばれ続けることです。ただし回数が少なく、遅延を外してから戻るまでの時間には差が出ていません（詳しくは折りたたみ）。

:::details 決済 API のスレッドが上限だった秒数と、起きていたこと
遅延を外したあと、決済 API（payment-api）のスレッドが上限に達していた秒数を数えました。何も設定しない実験は3回、リトライの実験は8回、ほかは1回ずつです。

| 実験 | リトライ | order-api の再起動 | 再起動のあと30秒のうち、上限だった秒数 |
| --- | --- | --- | --- |
| 何も設定しない（3回） | なし | あり | 5秒（3回とも） |
| タイムアウトだけ | なし | あり | 4秒 |
| 遅い決済 API | なし | あり | 6秒（上限は12本） |
| リトライ（8回） | 最大3回 | あり | 7〜20秒 |
| トランザクションの外で呼ぶ | なし | なし | （再起動なし。遅延を外してから120秒のうち1秒） |
| リトライ ＋ サーキットブレーカー | 最大3回 | なし | （再起動なし。遅延を外してから120秒のうち1秒） |

数秒以上続けて上限に達したのは、遅延を外したあとに order-api が受け付けを再開した実験です。再起動した order-api が受け付けを始めると、スレッドはすぐに40本で埋まり、/orders は到着率の60件/秒を超える率で処理されました（スレッドが40本だった区間の平均で、リトライのない実験では1秒に113〜120件、リトライの実験では72〜100件）。起動の直後に処理が遅いあいだ、Tomcat の待ち行列にリクエストが残っていたと考えられます。リトライのない実験では、この率だけで決済 API がさばける120件/秒に届き、数秒だけ上限に達しています。

再起動がなくても、遅延を外した時点で order-api がスレッドを使い切ったまま動いていれば、待ち行列のリクエストが一度に処理されます。何も設定しない実験の2・3回目とリトライの2回目がそうで、再起動の前にも7秒・6秒・5秒、上限に達していました（表には入れていません）。

リトライがあると、上限だった時間が延びました。比べた相手のうち「遅い決済 API」は、トランザクションの外で呼び、再起動もあり、決済 API がさばける率も同じ120件/秒です（応答時間の分布とタイムアウトは違います）。どの実験も回数が少なく、ばらつきが大きいことに注意してください。

![遅延を外したあとの決済 API のスレッド（リトライ）](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03a-retry/results/panels/payment-api-threads-recovery.png)
*リトライあり（1回目の実行）。左端の赤い帯の終わりで遅延を外しました。灰色の縦の帯が order-api の再起動で、そのあと約11秒続けて上限の6本になっています*

リトライがあるときは、次の順に進んでいました。

1. 再起動の直後、/orders が到着率を超える率で処理され、リトライも加わって、決済 API への呼び出しは115〜123件/秒に増え、決済 API がさばける120件/秒に届いた
2. 決済 API の中で待ち行列ができて応答が 300ms を超え、多いときで毎秒27〜40件の呼び出しがタイムアウトし、そのうち25〜35件がリトライのすえ成功していた。タイムアウトした呼び出しがリトライされるあいだは、遅延を取り除いても、決済 API の応答は 300ms を超えたままになる
3. そのあいだ order-api のスレッドも40本で埋まり、/livez も待ち行列に並ぶ。/livez の待ちが liveness probe のタイムアウト（1秒）を3回続けて超えれば、再起動されて1に戻る

遅延を外してから戻るまでの時間は、リトライの8回で12〜46秒でした。リトライがなくスレッドが尽きた「何も設定しない」「タイムアウトだけ」「遅い決済 API」（1回目の値で37〜43秒）より遅いわけではありません。ただ、下流をほかのサービスも使っていれば、そちらも遅くなりますし、3が起きれば再起動の繰り返しに戻ります（負荷のかけ方を直す前の回では、2分たっても戻らなかったことがあります。付録）。

リトルの法則で読むと、決済 API がさばける率は λ = L ÷ W = 6本 ÷ 0.05秒 = 120件/秒で、平常時の60件/秒の2倍しかありません。再起動の直後に /orders が到着率を超える率で処理され、そこに1件あたり最大3回の試行が加わると、さばける率に届きます。さばける率の近くまで呼ぶと、決済 API の中の待ち行列で W が伸び、タイムアウトしてまたリトライになります。
:::

### この章でわかったこと

リトライは、W（試行の間の待ちを含む）と、1件あたりの試行を増やします。入れたら、W の最大値を「試行回数 × タイムアウト ＋ リトライの待ちの合計」で計算し直し、上限と比べます。下流を呼ぶ率は最大で試行回数倍になります。スレッドで呼ぶ構成では「スレッドの数 × 試行回数 ÷ W」を超えませんが、仮想スレッドや非同期の呼び出しでは、この上限がありません。

サービスが戻った直後に、待ち行列で待っていたリクエストがまとめて処理されると、下流への呼び出しがさばける率に届くことがあり、リトライはその時間を延ばしうるようです。回数の少ない観察なので、言えるのはここまでです。リトライは、回数ではなく全体に対する割合（リトライ予算）で絞り、待ちにはジッターを入れるのが定石とされています（付録の参考）。上流もリトライするなら、回数は掛け算になります。

直近の一定時間で失敗率を数えるサーキットブレーカーは、障害中も呼ぶ率が変わらなければ、およそ「集計する期間 × 失敗率のしきい値」がたつまで開きません。開いているあいだは、下流が直っても戻れません。そして、設定値の意味は読み違えやすいものです。最低の呼び出し数を開く条件と読み違えると、開くまでの時間を大きく見誤ります。

## すべてを設定して、もう一度遅くする

最後に「すべて設定する」実験です。タイムアウト 300ms、決済 API はトランザクションの外、取得待ちのタイムアウト 250ms、バルクヘッド12、ブレーカーを設定し、リトライは控えめに最大2回試行・100ms おきにしました。決済 API の速さは、元の平均 50ms・p99 120ms に戻しています。

### 予測

バルクヘッドを通れる率は12 ÷ 0.3 ＝ 1秒に40件で、障害中はどれもタイムアウトします。

スレッドはどうなるでしょうか。1件の W は最大0.3 ＋ 0.1 ＋ 0.3 ＝ 0.7秒なので、バルクヘッドがなければ λW ＝ 60 × 0.7 ＝ 42本となり、40本を超えます。バルクヘッドがあれば、決済 API を待ってスレッドを握るのは12本までです。ただし、リトライの待ち（100ms）にいるあいだはバルクヘッドの外にいます。そこにいるのは、1回目の試行でタイムアウトした呼び出し（多くて1秒に40件）× 0.1秒 ≈ 4本です。合わせて最大16本ほどになるはずです。

ブレーカーが開く時刻も計算しておきます。バルクヘッドに来るのは、新しい呼び出しの1秒60件と、1回目の試行でタイムアウトした呼び出し（最大40件）のリトライで、合わせて1秒に最大100件です。通れる40件はタイムアウトし、残りは断られるので、どれも失敗になります。ブレーカーはバルクヘッドの外側にあるので、バルクヘッドに断られた呼び出しも失敗として数えます（Resilience4j は、既定ではすべての例外を失敗として数えます）。失敗は1秒に80〜100件ずつ増え、リトライ ＋ サーキットブレーカーの実験と同じ計算で、障害から約4秒で開くはずです。

![すべて設定したときのスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/04-all-defenses/results/panels/threads.png)
*ブレーカーが開くまでの数秒も、14本までに収まっています*

スレッドは最大14本で、ブレーカーは障害の3〜4秒後に開きました（リトライ ＋ サーキットブレーカーの実験は4〜5秒後）。開くまでの失敗は、タイムアウトの1秒に約37件に、バルクヘッドに断られた約45〜50件が加わり、1秒に約80〜90件ずつ増えていました。障害中に決済 API が受けた呼び出しは平均3.1件/秒、/products の成功率は100%、再起動は0回で、遅延を外してから9秒で戻りました。

### 8つの実験を並べる

| 実験 | 障害中の /products | スレッドの最大 | 決済 API が受けた呼び出し | 再起動 | 遅延を外してから戻るまで |
| --- | --- | --- | --- | --- | --- |
| 何も設定しない | 1.0% | 40本 | 2件/秒 | 4回 | 38秒 |
| タイムアウトだけ | 12.3% | 40本 | 17件/秒 | 5回 | 43秒 |
| トランザクションの外で呼ぶ | 100% | 22本 | 60件/秒 | 0回 | 7秒 |
| 遅い決済 API | 25.3% | 40本 | 29件/秒 | 5回 | 37秒 |
| 遅い決済 API ＋ バルクヘッド | 100% | 13本 | 15件/秒 | 0回 | 9秒 |
| リトライ | 8.2% | 40本 | 30件/秒 | 5回 | 19秒（8回で12〜46秒） |
| リトライ ＋ サーキットブレーカー | 100% | 40本（約4秒） | 4件/秒 | 0回 | 11秒 |
| すべて設定する | 100% | 14本 | 3件/秒 | 0回 | 9秒 |

どれも1回の実行の値です。回復までの時間は実行ごとのばらつきが大きく、すぐに戻っても6〜7秒と出る測り方です。複数回回した実験のほかの回の値と、残りの列（CPU、平常時の L と測った λW など）はリポジトリにあります（付録）。

並べてみると、/products を100%に保つだけなら、「トランザクションの外で呼ぶ」実験の設定（タイムアウトと、トランザクションの外で呼ぶこと）で足りていました。バルクヘッドが効いたのは、タイムアウトの下限が上限を超える下流と、ブレーカーが開くまでのあいだです。ブレーカーは、決済 API への呼び出しを60件/秒から3〜4件/秒に減らしました。

スレッドが尽きたままになった実験は、どれも4〜5回再起動し、遅延を外してから戻るまで37〜43秒（表の1回の値。リトライは8回で12〜46秒）かかりました。liveness probe を業務と同じスレッドプールで受けているからです（後述）。

CPU も見ておきます。タイムアウトを設定してもスレッドが尽きた実験（タイムアウトだけ・遅い決済 API・リトライ）では、最初の再起動までの CPU は平常時と同じくらい（18〜24%）でした。障害中の平均は42〜45%と平常時の2倍ほどに見えますが、これは再起動のあとの JVM の起動の分で、障害を起こしたのではなく、障害の結果です。

### この章でわかったこと

サーキットブレーカーが開くまでのあいだは、バルクヘッドが、下流を待ってスレッドを握る数を抑えます。

包む順によって振る舞いが変わる点にも注意が要ります。リトライが外側なら、リトライの待ちのあいだ握るスレッドは、バルクヘッドの上限に入りません。ブレーカーがバルクヘッドの外側なら、バルクヘッドに断られた呼び出しも失敗として数えるので、早く開きます。そのぶん、下流が健全でも、平常時の混雑で断る率が失敗率のしきい値に届くほど続けば開きます。数えたくなければ、ブレーカーの ignore-exceptions に BulkheadFullException を入れます。

## 自分のサービスを L = λW で点検する

ここまでの実験をもとに、自分のサービスを点検する手順をまとめます。これが、この記事でいう障害時のキャパシティプランニングです。

### 握ったまま待つプールを書き出す

まず、リクエストが握ったまま待つプールと、その大きさ、使っている処理を書き出します。

- リクエストを処理するスレッド（Tomcat なら `server.tomcat.threads.max`、既定200）。スレッドの空きを待つ待ち行列は `server.tomcat.threads.max-queue-capacity`（既定は事実上無制限）で、受け付ける接続の数の上限は `server.tomcat.max-connections`（既定8192）
- DB のコネクション（HikariCP なら `spring.datasource.hikari.maximum-pool-size`、既定10）
- HTTP クライアントの接続プール（Apache HttpClient 5 の接続プールは、既定で宛先ごとに5本で、空きを待つ時間の既定は3分。ここが一番小さいプールになることがある）
- 非同期処理のスレッドプール、バルクヘッドのような同時実行数の上限
- 仮想スレッドを使っているなら、スレッドの上限はない。下流ごとに同時実行数の上限があるかを確かめる

どこで握っているかが分からなければ、障害中にスレッドダンプ（`jcmd <pid> Thread.print`）を取って、コネクションの取得待ちや、ソケットの読み取りで止まっているスレッドを数えます。HikariCP の `spring.datasource.hikari.leak-detection-threshold` を設定すると、一定時間より長く握られたコネクションについて、取得した場所のスタックがログに出ます。トランザクションの中の外部呼び出しを見つけるのに便利です。

### 障害時の W の最大値を足し算する

次に、下流が返らなくなったとき、1件がスレッドやコネクションを握る最長の時間を、設定から足し算します。

- （接続のタイムアウト ＋ 応答のタイムアウト）× 試行回数 ＋ リトライの待ちの合計。1件のリクエストで同じ下流を順に何回も呼ぶなら（ループの中の呼び出しなど）、その回数も掛ける
- コネクションの取得待ちのタイムアウト（HikariCP の既定は30秒）と、HTTP クライアントの接続プールの取得待ちのタイムアウト（Apache HttpClient 5 の既定は3分）
- トランザクションの中で下流を呼んでいれば、その時間はコネクションの W にも入る。JPA（Hibernate）で Open Session in View（Spring Boot の既定で有効）を使っていると、トランザクションの外で下流を呼んでも、リクエストの終わりまでコネクションを握り続けることがある

HTTP クライアントには、応答のタイムアウトの既定が無制限のものも多くあります。Spring の RestClient や RestTemplate も、タイムアウトを設定しなければ待ち続けます。また「読み取りのタイムアウト」は、バイトが届かない時間の上限で、全体の時間の上限ではないことがあります。Resilience4j の TimeLimiter はブロッキングの呼び出しを打ち切らないので、タイムアウトは HTTP クライアントの側で設定します。最後に、合計が上流のタイムアウトより短いかも確かめておきます。

### λW とプールの大きさを比べる

プールごとに次の表を埋めて、「下流を呼ぶ処理の到着率 × W の最大値」が「プールの大きさ × 使ってよい割合」に収まるかを確かめます。

| 項目 | 例：Tomcat のスレッド |
| --- | --- |
| プールの大きさ | 200 |
| 下流を待つ処理 | 検索 API（外部の在庫 API を呼ぶ） |
| その到着率（1台あたり、ピークの時間帯の1分の rate） | 250件/秒 |
| 障害時の W の最大 | 1.1秒 |
| λW | 275 |
| プールの大きさ × 使ってよい割合（0.7。ほかの処理が約20本使うとして、m ＋ 3√m ＋ 20 ≤ 200から） | 140 |
| 判定 | 超える |

到着率には、1台あたりの、ピークの時間帯の1分の rate を使います。秒単位のばらつきは、使ってよい割合で見込んでいるからです。障害中に上がる分（上流のリトライ、Service から外れた Pod に送られていたリクエスト）も見込んでおきます。

下流が複数あるときは、同時に遅くなりうる組み合わせで λW を足します。下流の呼び出しの一部だけが遅い（下流の1台だけが悪いなど）ときは、λW を平均の W で計算します。トランザクションの中で下流を呼んでいるなら、コネクションプールでも同じ表を埋めます。どちらが先に尽きるかは「空いている数 ÷ そのプールに入る率」で決まります。

表で「超える」になったプールは、下流の障害で尽きます。尽きるまでの時間は「空いている数 ÷ 到着率」なので、1台あたりの到着率が高いほど短くなります。

:::details 通しの計算例（上の表の検索 API）
1. W の最大値1.1秒の内訳は、（接続0.1秒 ＋ 応答0.4秒）× 2回 ＋ リトライの待ち0.1秒
2. 1件が握る時間の上限は200 × 0.7 ÷ 250 ＝ 0.56秒で、1.1秒は超えている
3. リトライを外す（残すなら、（接続 ＋ 応答のタイムアウト）× 試行回数 ＋ 待ちを0.56秒と比べる）。接続の0.1秒を引くと、応答のタイムアウトに使えるのは0.46秒まで
4. 在庫 API の平常時の p99.9 が0.8秒なら、応答のタイムアウトの下限は0.8秒で、上限の0.46秒を超える。どのタイムアウトの値でも、平常時のタイムアウトが0.1%を超えるか、障害時にスレッドが尽きる（いまの0.4秒は、平常時に0.1%以上がタイムアウトする長さ）
5. そこで、在庫 API を同時に呼ぶ数にバルクヘッドで上限を付ける。平常時の同時実行数は250件/秒 × 平常時の平均の応答時間0.05秒 ＝ 12.5。断る率を0.1%以下にするなら、アーランの B 式で同時実行数は25（断る率は約0.06%）
6. 応答のタイムアウトは下限の0.8秒にし、リトライは入れない。障害時に在庫 API を待ってスレッドを握るのは最大25本で、140本に収まる。応答が返らないだけなら、在庫 API まで届くのは25 ÷ 0.8 ≈ 1秒に31件で、残りはすぐに断られる
7. HTTP クライアントの接続プールも、宛先ごとに25本以上にする。Apache HttpClient 5 の既定の宛先ごと5本のままだと、同時に呼べるのは5本で、残りはスレッドを握ったまま接続プールの空きを待つ
:::

:::details 値の取り方（Prometheus と Micrometer の例）
```promql
# 下流を呼ぶ処理の、1台あたりの到着率（1分の rate の、Pod のうちで最大）
max(max_over_time(sum by (pod) (rate(http_server_requests_seconds_count{uri="/search"}[1m]))[1d:1m]))
# 下流ごとの平常時の p99.9（percentiles-histogram を有効にしておく）
histogram_quantile(0.999, sum by (le, client_name) (rate(http_client_requests_seconds_bucket[1h])))
```

1分の rate は、秒単位のピークより低く出ます。秒単位のばらつきは、使ってよい割合の3√m で見込んでいます。

p99.9 には注意が要ります。いまのタイムアウトより長い応答は打ち切られるので、クライアント側のヒストグラムには現れません。上の p99.9 がいまのタイムアウトに近いときは、応答が返らなかった呼び出しの割合を先に見ます。これが0.1%を超えていれば、下限はいまのタイムアウトより長いということです。そのときは、下流側のメトリクスで測るか、一時的にタイムアウトを延ばして測ります。

p99.9 は、直近1時間ほどの呼び出しから計算します（`rate(...[1h])`）。直近5分では、p99.9 より遅い呼び出しが数件しかなく、値がぶれます。ピークの時間帯を含む数日分を見て、下流の障害やデプロイの時間帯を除いた最大を取ります。候補のタイムアウトの前後には、バケットを足しておきます（`management.metrics.distribution.slo.http.client.requests`）。

```promql
# 応答が返らなかった呼び出しの割合（タイムアウトや接続の失敗。ラベルは環境に合わせる）
sum by (client_name) (rate(http_client_requests_seconds_count{outcome="UNKNOWN"}[1h]))
  / sum by (client_name) (rate(http_client_requests_seconds_count[1h]))
```
:::

### どの手段を選ぶか

表で「超える」になったら、状況に合わせて手段を選びます。

| 状況 | 選ぶもの |
| --- | --- |
| タイムアウトの下限が上限より小さい | W に上限を付ける。タイムアウトを、下流の平常時の p99.9 と「プールの大きさ × 使ってよい割合 ÷ 到着率」のあいだの値にする |
| 下流を待つあいだ、小さいプール（コネクションなど）も握っている | そのプールを握らない形に変える。トランザクションの外で下流を呼ぶ |
| タイムアウトの下限が上限を超える | 下流の呼び出しの L に上限を付ける。下流を同時に呼ぶ数に上限を付け、上限を超えた分はすぐ断る |
| 下流に副作用がある（決済・送金・メール送信など） | タイムアウトを短くするほど「結果が分からない」呼び出しが増える。同時実行数の上限で抑えるほうが向くことがある |
| 下流への呼び出しを止めて下流の負荷を下げたい。失敗をすぐ返したい | 下流の呼び出しの λ をほぼ0にする。サーキットブレーカー。開くまでの時間（およそ集計する期間 × 失敗率のしきい値）を計算し、そのあいだ下流を待ってスレッドを握る数（バルクヘッドの同時実行数 ＋ リトライの待ちにいる数）が「プールの大きさ × 使ってよい割合」に収まるかを確かめる。Resilience4j の `slow-call-rate-threshold` を使えば、タイムアウトを待たずに、遅い呼び出しの割合でも開ける |
| スレッドの空きを待つリクエストの数に上限を付けたい | Tomcat の待ち行列の長さに上限を付ける（Spring Boot なら `server.tomcat.threads.max-queue-capacity`）。上限を超えたリクエストは断られる（HTTP のエラーは返らず、接続が閉じられる）。同じポートで受けている probe も断られる |
| 下流を待つだけで CPU を使わず、メモリも足りている | プールや台数を大きくする。大きさを「λW ÷ 使ってよい割合」以上にする（コネクションは、DB 側のコネクション数の上限を超えられない） |
| リトライを入れたい | 冪等であることを確かめる。リトライする例外を、タイムアウト・接続の失敗・5xx に絞る（Resilience4j の Retry は、既定ではすべての例外をリトライする）。回数と待ちを控えめにし、待ちにはジッターを入れ（`enable-exponential-backoff`・`enable-randomized-wait`）、W の最大値を計算し直す |

### liveness probe をどこで受けるか

liveness probe を業務と同じスレッドプールで受けていると、下流の障害でプールが尽きたときに probe も答えられず、コンテナが再起動されます。障害中の再起動では直らないどころか、下流が直ったあとの回復を遅らせます。

とはいえ、別のポートで受ければいいという単純な話でもありません。Spring Boot のドキュメントは、probe を業務と同じポートでも受ける構成（`management.endpoint.health.probes.add-additional-paths`）を勧めています。業務とは別のポートだけで受けると、業務側が接続を受けられなくなっても probe が成功してしまうからです。liveness probe は「プロセスが壊れていて、再起動で直る」ときだけ失敗させるものです。選び方をまとめると、次のようになります。

| 構成 | 得られること | 払うもの |
| --- | --- | --- |
| liveness を業務のポートで受ける（Spring Boot の推奨） | 業務側が接続を受けられなくなったことを検知できる | 下流の障害で再起動を繰り返し、回復が遅れる |
| liveness を管理ポートで、readiness を業務のポートで受ける | 下流の障害で再起動しない | 待ち行列に残ったリクエストを、下流が直ったあとに処理する（表の下） |
| liveness を、業務のポートへの tcpSocket の probe にする | 業務のポートが接続を受け付けなくなったことを検知でき、スレッドが尽きても再起動しない（Tomcat は、スレッドが尽きていても `max-connections` までは接続を受け付ける） | 接続を受け付けている限り、プロセスが応答しなくなっても検知できない |
| 業務のポートのまま、再起動を決めるまでの時間（間隔 × 回数）を長くする | 一時的な下流の障害では再起動しにくく、業務のポートの異常も遅れて検知できる | 本当に壊れたときの再起動も遅れる |

liveness を管理ポートで受ける構成では、再起動しないので、Service から外れる前に届いて、クライアントがすでにあきらめたリクエストが Tomcat の待ち行列に残ります。下流が直ったあと、サービスはまずそれを処理することになります。`max-queue-capacity` で待ち行列に上限を付けて組み合わせるといいでしょう。また、readiness probe がすべてのレプリカで失敗すると、Service に送り先がなくなり、下流を呼ばない処理も含めてすべて断られます。これは、liveness を業務のポートで受ける構成でも同じです。

どの構成でも、業務のスレッドが尽きたことは、再起動ではなく、次の監視で知るようにします。

### 監視とアラート

監視するのは「使用中の数 ÷ プールの大きさ」です。

```promql
# Pod ごとの「使用中の数 ÷ プールの大きさ」（ラベル名は環境に合わせる）
max by (pod) (tomcat_threads_busy_threads / tomcat_threads_config_max_threads)
max by (pod) (hikaricp_connections_active / hikaricp_connections_max)
max by (pod) (hikaricp_connections_pending)
# 下流ごとに、進行中の呼び出しの数（Micrometer の LongTaskTimer）
sum by (pod, client_name) (http_client_requests_active_seconds_gcount)
# バルクヘッドの空き
min by (pod) (resilience4j_bulkhead_available_concurrent_calls)
```

いくつか注意があります。

- `tomcat_threads_*` は、`server.tomcat.mbeanregistry.enabled=true` にしないと出ません
- 進行中の呼び出しの数のメトリクス名は、`percentiles-histogram` を有効にしていると末尾が `_gcount`、していなければ `_count` です（Micrometer 1.13 以降。1.12 以前は `_active_count`）
- メトリクスは業務とは別のポート（`management.server.port`）で出しておけば、業務のスレッドが尽きても測れます。Service 経由で集めているなら、readiness probe に失敗した Pod も集める対象から外れない設定（`publishNotReadyAddresses` など）にします
- 下流ごとの呼び出しの数は、終わった呼び出しから計算する `rate(_sum)` ではなく、進行中の数で見ます。返ってこない呼び出しは、終わるまで `rate(_sum)` に入らないからです

アラートについても考えておきます。尽きるまでの時間は「空いている数 ÷ 到着率」で、到着率が高いと1秒もかかりません。アラートで枯渇そのものを防ぐことはできません。役に立つのは、CPU が上がらず原因を見誤りそうなときに、どのプールが尽き、どの下流で進行中の呼び出しが増えたかを、すぐに示すことです。

アラートの条件は、続いた時間ではなく、直近の数分の最大値やカウンターの増え方にします。プールが尽きると、liveness probe の失敗が「間隔 × 回数」だけ続くたびに再起動され、そのたびに使用中の数は0に戻り、メトリクスも途切れます（5秒ごと・3回で再起動する設定なら、尽きた状態は15〜20秒ほどで途切れます）。「0.8を超えて30秒続く」のような条件は、障害が続いていても満たされないことがあります。

ゲージ（使用中の数など）は、集めた瞬間の値しか残らない点にも注意が要ります。尽きていた時間が集める間隔（Prometheus の既定は1分）より短ければ、`max_over_time` にも現れません。カウンター（コネクションの取得待ちのタイムアウトの回数、コンテナの再起動の回数）と組み合わせておきます。

```promql
# 直近2分のうちに、スレッドプールが尽きたことがある
max by (pod) (max_over_time(tomcat_threads_busy_threads[2m]) / max_over_time(tomcat_threads_config_max_threads[2m])) >= 1
# 直近5分のうちに、コネクションの取得待ちがタイムアウトした
sum by (pod) (increase(hikaricp_connections_timeout_total[5m])) > 0
# 直近2分のうちに、コネクションの取得を100ms 以上待ったリクエストがある
max by (pod) (max_over_time(hikaricp_connections_acquire_seconds_max[2m])) > 0.1
# コンテナが再起動している（kube-state-metrics）
increase(kube_pod_container_status_restarts_total[10m]) > 0
```

エラー率は、上流・Ingress・ロードバランサーの側でも見ておきます。最初の実験で見たとおり、クライアントがタイムアウトしたリクエストは、サーバー側の `http_server_requests` には失敗として記録されず、あとで処理されて200として記録されることもあるからです。

### 遅延を入れて確かめる

計算は、前提が合っていて初めて当たります。予測と合格条件（「障害から2秒以内にスレッドが上限に達する」「遅い下流を呼ばない処理の成功率が99%以上」など）を先に書いてから、下流に遅延を入れ、オープンモデルの負荷をかけて確かめます。負荷試験のツールの VU（同時に待てる数）は、「到着率 × クライアントのタイムアウト」以上を最初から用意しておきます。遅延は、Toxiproxy のようなプロキシや、サービスメッシュの fault injection で入れられます。

予測が外れたら、どの前提が違ったかを調べます。この記事でもサーキットブレーカーの予測が外れ、設定値の読み違いに気づきました。外れた理由を調べること自体が、設定を正しく読めているかの点検になります。

## まとめ

下流の応答を待つあいだスレッドやコネクションを握る処理があると、下流が遅くなっただけで、同じプールを使うほかの処理やヘルスチェックまで空きを待たされ、タイムアウトしていきます。λW がプールの大きさを超えるなら、尽きるまでの時間は遅延の長さによらず「空いている数 ÷ 到着率」で決まります。CPU は上がらないので、見るのは「使用中の数 ÷ プールの大きさ」です。

タイムアウトとトランザクションの範囲は W に、バルクヘッドは下流を同時に呼ぶ数に上限を付け、サーキットブレーカーは下流を呼ぶ率をほぼ0にします。タイムアウトの値の範囲とバルクヘッドの同時実行数は計算で決められ、ブレーカーが開くまでの時間と、リトライを入れたときの W は計算で確かめられます。リトライだけは逆向きに働き、1件がスレッドを握る時間と試行を増やします。また、liveness probe を業務と同じスレッドプールで受けていると、下流の障害で再起動を繰り返し、回復が遅れます。

まず確かめるとしたら、次の2つです。トランザクションの中で外部の API を呼んでいないか。HTTP クライアントの応答のタイムアウトが下流の平常時の p99.9 より長く、リトライの待ちまで含めて1件がスレッドを握る時間の合計が「プールの大きさ × 使ってよい割合 ÷ 1台あたりの到着率」より短いか。

## 付録

### ほかにも使える場面

- **非同期のワーカーやコンシューマーの並列数**：処理したい率 × 1件の処理時間
- **スケールアウトでプールの枯渇を防ぐときの台数**：障害時の λW ÷（1台あたりのプールの大きさ × 使ってよい割合）。プールごとに計算し、大きいほうを取る（何も設定しない状態なら、スレッドでは300 ÷ 28 ≈ 11倍、コネクションでは300 ÷ 7 ≈ 43倍。コネクションは DB 側のコネクション数の上限も超えられない）

### この実験環境の限界

- k6 の constant-arrival-rate はリクエストを等間隔に送るので、本番のトラフィックより、ばらつき（バースト）を小さく見積もっています
- 障害は、応答の遅延だけです。下流がエラーを返す場合や、接続の確立に時間がかかる場合は試していません
- Toxiproxy は応答を遅らせるだけなので、障害中も決済 API 自体は、呼ばれた分を平常どおりの速さで処理していて、過負荷にはなっていません。サーキットブレーカーで下流の負荷を下げる効果は、障害中には確かめられていません
- order-api のレプリカは1つです。複数あるとき、readiness probe に失敗して外れた Pod に送られていたリクエストが残りの Pod に送られる動きや、呼び出し元のサービスでもスレッドが尽きるかは見ていません
- liveness probe の構成は、業務のポートで HTTP の probe を受けるものしか試していません。点検の章の表のほかの構成は、Spring Boot のドキュメントと Tomcat の動きからの推論です
- リトライの利点（一時的な失敗を、もう一度呼んで成功させること）は測っていません。リトライで下流が上限に達する時間が延びる条件も、試したのは1つの組み合わせ（最大3回の試行と、さばける率が平常時の2倍の下流）だけです
- 負荷のかけ方を直す前（k6 が VU を途中で作り足していて、遅延を入れた直後の到着を取りこぼしていたころ）に回したリトライの実験4回のうち1回は、遅延を外して2分たっても戻りませんでした（もう1回戻らなかった回は、直前の実行の再起動の影響が残っていました）。再起動のたびに決済 API が上限に達して liveness probe が失敗し、Kubernetes が再起動の間隔を延ばしていきました（CrashLoopBackOff）。障害の起点を取り除いても、タイムアウトとリトライが下流の負荷を押し上げ続けて戻らなくなる障害は、metastable failure と呼ばれています。この実験の回数では、どれくらいの頻度で起きるかは言えません（12回の値は [runs.md](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/03a-retry/results/runs.md)）
- 「トランザクションの外で呼ぶ」実験では、トランザクションの外で呼ぶことと、取得待ちのタイムアウトを同時に変えています（取得待ちは起きていないので、効いたのは前者です）。タイムアウトの上限の式も、上限の前後でタイムアウトを変えて確かめてはいません
- メトリクスは1秒ごとの計測なので、「何秒で尽きたか」には1秒の幅があります。HikariCP はプールの統計を1秒キャッシュするので、使用中・取得待ちの数が1つ前の計測の値のままのこともあります
- 回復時間は、遅延を外したときに order-api が再起動の途中かどうかで、実行ごとにばらつきます

### 実験ごとの設定値

共通の設定は、Tomcat のスレッド40本、HikariCP のコネクション10本、負荷は /orders 60件/秒・/products 10件/秒（k6 のタイムアウト5秒）、障害は決済 API の応答に5秒の遅延です。サーキットブレーカーは、直近10秒に20回以上呼んで失敗率50%以上で開き、開いたまま5秒、半開で10回試します。リポジトリでは、実験ごとに `scenarios/<ディレクトリ>/` に結果があり、複数回回したものはそこの runs.md に、全体の比較は [SUMMARY.md](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/SUMMARY.md) にあります。

### 動かし方

Docker（コンテナ用に 4GB 以上）、kind、kubectl、JDK 21、Python 3 があれば動きます。Grafana のパネルを PNG に書き出すには、Node.js と Google Chrome も要ります。

```bash
make up                       # クラスタを作り、アプリを作って載せる
make scenario-00-no-defense   # 実験を 1 つ回す（約 7 分）
make scenarios                # 8 つを順に回す（約 1 時間）
make down                     # クラスタを消す
```

結果は `scenarios/<ディレクトリ>/results/score.json` に書き出されます。`cd tools && npm install` をしておくと、Grafana のパネルも `results/panels/` に PNG で残ります。遅延は、Toxiproxy の管理 API（8474番）で入れています（[run.sh](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/run.sh)）。
