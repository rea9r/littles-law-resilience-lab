## TL;DR

- 下流の応答を待つあいだスレッドやコネクションを握る（使ったまま返さない）処理は、下流が遅くなると、1 件が握る時間 W が伸びる。到着率 λ との積 λW がプールの大きさを超えると、そのプールを使うすべての処理が空きを待って並び、遅い下流を呼んでいない処理まで止まる。尽きるまでの時間は「空いている数 ÷ 到着率」で、遅延の長さによらない。CPU は上がらないので、見るべきは「使用中の数 ÷ プールの大きさ」
- タイムアウトには下限と上限がある。下限は「下流の平常時の p99 ＋ 上乗せ」、上限は「プールの大きさ × 使ってよい割合 ÷ 下流を呼ぶ処理の、1 台あたりのピーク時の到着率」。下限が上限を超えるなら、タイムアウトでは守れないので、下流を同時に呼ぶ数に上限を付ける（バルクヘッド）
- スレッドを握ったまま待つ場所（下流の応答、コネクションの取得、リトライの待ち）ごと、プールごとに λW を計算する。トランザクションの中で下流を呼ぶと、コネクションプールが先に尽き、タイムアウトを入れても守れない
- リトライは W と呼び出しの数を両方増やす。下流がさばける率の近くまで呼ぶと、下流の遅延が直っても遅い状態がしばらく続き、再起動が重なると戻らないこともある。サーキットブレーカーは、障害中に呼ぶ率が平常時と同じくらいなら、およそ「集計する期間 × しきい値」がたつまで開かない。そのあいだはバルクヘッドで守る

kind で動かした Spring Boot のサービスで、これらを予測してから壊して確かめました（1.2）。

## 1. はじめに

### 1.1 下流が 1 つ遅くなっただけで、関係のない API まで止まる

外部の API が 1 つ遅くなっただけなのに、その API を呼んでいない画面まで開かなくなる。CPU もメモリも余っていて、ログには遅い API のタイムアウトしか出ていない。こうした障害は、スレッドプールやコネクションプールを持つサーバーなら、どこでも起こりえます。

ふり返りでは「スレッドが枯渇したから」と書かれがちです。しかし、それだけでは次の問いに答えられません。

- 下流がどれだけ遅くなったら、何本のスレッドやコネクションが、何秒で尽きるのか
- なぜ、遅い API を呼んでいない処理まで止まるのか
- タイムアウトは何秒にすればよいのか。バルクヘッドで同時に呼ぶ数はいくつまでにするか。リトライは助けになるのか

この記事では、これらをリトルの法則 L = λW で計算して答えます。キャパシティプランニングというと、平常時のピークに耐える台数やプールの大きさを決めることを指しがちです。この記事では、下流の障害時にどのプールが何秒で尽きるかまで計算に入れて、タイムアウトや同時実行数の上限を決めます。

### 1.2 この記事の進め方

小さな注文 API（order-api）を用意し、kind のクラスタで壊します。注文（POST /orders）は外部の決済 API を呼び、商品一覧（GET /products）は DB を読むだけです。決済 API の応答に 5 秒の遅延を入れ、スレッドとコネクションが何秒で尽きるかを先に計算してから、実際に壊して確かめます。そのうえで、防御を 1 つずつ入れて、それぞれが L = λW のどこに効くか（あるいは逆に働くか）を測ります。

結果を先に見せると、防御がない状態では、決済 API を呼ばない /products の成功率まで 1.0% に落ちました。

### 1.3 対象とゴール

Tomcat や HikariCP のように上限のあるプールで動くサーバーを書いている人、運用している人を想定しています。例は Spring Boot ですが、考え方はプールを持つサーバー全般に当てはまります。読み終えたときに、次のことができるようになるのがゴールです。

- 自分のサービスで、下流の障害時にどのプールがいつ尽きるかを計算できる
- タイムアウト・バルクヘッド・サーキットブレーカー・リトライが L = λW のどこに効くかを説明でき、値を計算で決められる

### 1.4 扱わないこと

- **WebFlux・コルーチン・仮想スレッド**：スレッドの数という上限はなくなりますが、コネクションや下流への同時呼び出しといった別の上限が先に当たるだけです。むしろ暗黙の上限がなくなるぶん、バルクヘッドのような明示的な上限が要ります
- **待ち行列理論による遅延の予測**：リトルの法則は平均どうしの関係で、負荷が増えたときに W がどう伸びるかまでは教えてくれません

## 2. リトルの法則

### 2.1 L = λW

$$
L = \lambda W
$$

L = λW は、入って出ていくものを数えられるところなら、どこにでも当てはまります。この記事では、主にサーバーのスレッドプールに当てはめます。

- **L**：中にいる数の平均（スレッドプールなら、使用中のスレッドの数）
- **λ**：1 秒あたりに入る数（スレッドを取ったリクエストの数）。上限がなければ到着率と同じで、落ち着いた状態では出ていく率とも同じ
- **W**：1 件が入ってから出るまでの時間の平均（1 件がスレッドを握っている時間）

1 秒に 60 件届き、1 件が 0.05 秒で返るなら、平均すると 60 × 0.05 = 3 本のスレッドが使われています。到着の仕方や処理時間の分布によらず、平均どうしでこの関係が成り立つのが強みです。

### 2.2 3 つの向きで使う

3 つの値のうち 2 つが分かれば、残りが決まります。

| 知りたいもの | 式 | 例 |
| --- | --- | --- |
| 同時に要る数 | L = λW | 1 秒に 100 件 × 1 件 0.2 秒 = 20 本 |
| さばける率の上限 | λ = L ÷ W | 8 本 ÷ 1 件 0.04 秒 = 200 件/秒 |
| 1 件の平均の時間 | W = L ÷ λ | 平均 5 本 ÷ 1 秒に 100 件 = 0.05 秒 |

### 2.3 メトリクスで確かめる

L = λW は、メトリクスからも確かめられます。使用中のスレッドの数（L）と、λ と W の積を同じグラフに描けば、流れが落ち着いているあいだ、2 本の線は重なります（実測は 6.3 で見せます）。以下、設定や計算から出す値を λW、メトリクスから測った値を λ×W と書き分けます。

:::details λ×W をどう測るか
Spring Boot（Micrometer）は、リクエストごとの処理時間を `http_server_requests_seconds` に記録し、合計（`_sum`）と件数（`_count`）を出します。合計の増え方 `rate(_sum)` は「1 秒に終わった件数 × その平均時間」なので、λ×W そのものです。

```promql
sum by (pod) (rate(http_server_requests_seconds_sum{uri!~"/actuator.*"}[10s]))
```

L は Tomcat の使用中のスレッド（`tomcat_threads_busy_threads`）です。λ×W は終わったリクエストしか数えないので、終わらないリクエストが溜まると L から離れます（5.3）。直近 10 秒で平均するので、状態が切り替わった直後は遅れて追いつきます。
:::

### 2.4 この記事で使う前提

- **平均どうしの関係です。** p99 の W から p99 の L は出ません。この記事の λW も、平均の W を使った値です
- **L と W は同じものについて測ります。** スレッドの L には、スレッドを握っている時間を W に使います。リクエストがスレッドの空きを待って並ぶ時間は、スレッドの W には入りません
- **上限で頭打ちのあいだは、λ を「実際にプールに入る率」にとります。** 到着率のままでは成り立ちません（5.2）。入ったまま終わらないリクエストが溜まっているあいだは、測った λ×W が L から離れます（5.3）

## 3. 障害を L = λW で読む

### 3.1 障害は W の増加から始まる

下流が遅くなったとき、まず変わるのは W です。到着率は、クライアントが送り続ける限り変わりません。下流の応答を待つあいだスレッドを握る処理では、下流の応答時間がそのまま W に入ります。下流が 100 倍遅くなれば W もほぼ 100 倍になり、到着率が同じなら λW も 100 倍になります。

### 3.2 λW がプールの大きさを超えると、プールを共有する処理まで止まる

スレッドを握ったまま下流を待つ処理 A と、下流を呼ばない処理 B が、同じスレッドプールを使っているとします。上限がなければ、A が同時に握る本数は λW で決まります。下流が遅くなって A の λW がプールの大きさを超えると、プールは A で埋まります。あとから来たリクエストは、A か B かに関係なく、1 本の待ち行列に並んで空きを待ちます。

- **B**：下流を呼ばないのに、空きを待つうちにクライアントのタイムアウトを過ぎて失敗する
- **A**：スレッドを取れても下流が返らないので失敗する。クライアントがあきらめたあとも処理は続き、スレッドは握られたまま
- **同じプールで受けている liveness probe**：答えられず、コンテナが再起動される

同じことは、A と B が使うコネクションプールでも起きます。A がトランザクションの中で下流を呼んでいれば、A はコネクションも下流の応答まで握ります。コネクションが先に尽きると、スレッドを取れた B も、コネクションの空きを待ってスレッドを握ります。2 つのプールがどちらも尽きるので、片方だけを大きくしても B は助かりません。

どのプールから尽きるかは「λW ÷ プールの大きさ」で決まり、大きいプールから先に尽きます。同じリクエストが 2 つのプールを同じだけ握るなら、小さいプールが先です。

遅くなったのは下流の 1 つだけです。それでも、共有しているプールを通じて、関係のない処理まで止まります。どれだけの速さで尽きるかは、5.2 で計算します。

### 3.3 守り方は 3 つ：W を抑える・L に上限を付ける・λ を絞る

L = λW は、下流の呼び出しにも当てはまります。下流の呼び出しの L（同時に呼んでいる数）・λ（1 秒に呼ぶ数）・W（1 回の呼び出しを待つ時間）のどれかに上限を付ければ、下流を待ってスレッドを握る数にも上限が付きます。

- **W を抑える**：下流の応答を待つ時間に上限を付ける（タイムアウト）。トランザクションの外で下流を呼べば、下流を待つあいだはコネクションを握らない
- **L に上限を付ける**：下流を同時に呼ぶ数に上限を付け、上限を超えた分は待たせずにすぐ断る（バルクヘッド）。下流の応答を待ってスレッドを握るのは、上限の数までになる
- **λ を絞る**：失敗が続いたら、しばらく下流を呼ばずにすぐ失敗を返す（サーキットブレーカー）
- **リトライは逆に働く**：失敗を取り戻す代わりに、1 件の W と、下流を呼ぶ数を増やす

## 4. 実験環境

### 4.1 全体の構成

![全体の構成](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/architecture.ja.png)

- order-api は Spring Boot（Tomcat のスレッド 40 本、HikariCP のコネクション 10 本）で、/orders・/products・/livez を同じスレッドで受けます
- 決済 API（payment-api）は、平均 0.05 秒・p99 0.12 秒の対数正規分布で応答を返すモックです。6 本のスレッドなので、1 秒に約 120 件までさばけます
- 決済 API の手前に Toxiproxy を置き、クラスタの外から scenarios/run.sh が遅延を入れたり外したりします
- 負荷は k6 で、応答の速さに関係なく一定の率で送ります（オープンモデル）。/orders は 1 秒に 60 件、/products は 10 件で、k6 は 5 秒でタイムアウトします。k6 は応答を待つ 1 件に 1 VU（仮想ユーザー）を使うので、要る VU の数もリトルの法則で決まります。/orders なら 60 件/秒 × 5 秒 ＝ 300 で、これより少し多い数を最初から用意しています
- コードと設定、計測の生の値は [リポジトリ](https://github.com/rea9r/littles-law-resilience-lab) にあります（動かし方は付録 E）

:::message
VU の数を固定する負荷試験（クローズドモデル）では、この壊れ方は小さく出るか、再現しません。VU は応答を待つあいだ次のリクエストを送らないので、応答が遅くなると到着率が勝手に下がるからです（ただし、クライアントがあきらめたあともサーバーが処理を続けると、VU が次を送るぶん、VU の数より多くのスレッドが握られます）。
:::

:::details 計測のしかけと、規模の縮め方
- order-api のメトリクスは、業務の 40 本とは別のスレッドで 8081 番から返します。40 本が埋まると readiness にも落ち、業務用の Service からは外れます。メトリクス用の Service は、readiness に落ちた Pod も返す設定（publishNotReadyAddresses）にしてあるので、そのあいだも Prometheus は 1 秒ごとに取りに行けます
- シナリオの設定を当てると、設定が変わったアプリの Pod だけが入れ替わります
- コンテナ用に約 4GB で動くよう、到着率やプールの大きさを、よくある本番の規模（Tomcat の既定のスレッド 200 本など）の約 1/5 に縮めています。比率が同じなら、尽きるまでの秒数やタイムアウトの下限と上限は変わりません
:::

### 4.3 1 回の実験の流れと、被害の測り方

![1 回の実験の流れ](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/scenario-timeline.ja.png)

ウォームアップは、JIT のコンパイルや接続プールが落ち着くまで待つ区間で、何も測りません（0 秒の前にも、設定の適用と Pod の入れ替えに 1 分ほどかかり、全体は約 7 分です）。図の下の括弧が、どの値をどの区間で測るかです。

- **成功率・使用中のスレッド・取得待ちの数**：障害中の 120 秒で集計する。成功率はエンドポイントごとに区間全体の割合、使用中のスレッドは平均と最大、コネクションの取得待ちの数は最大
- **スレッドが尽きるまで**：障害から 15 秒のあいだの 1 秒ごとの計測で、初めて 40 本になった時刻。実際にはこれより早く尽きていることがある
- **回復までの時間**：遅延を外してから、両方のエンドポイントの成功率（直近 6 秒）が 99% 以上になり、そのまま 15 秒続いた区間の始まりまで。直近 6 秒で数えるので、すぐに戻っても 6〜7 秒と出る。120 秒のうちにそうならなければ「戻らない」
- **再起動の回数**：負荷をかけている間の全体で数える

## 5. 防御なしで壊す（00）

### 5.1 設定

- 決済 API のタイムアウトは 30 秒
- 決済 API をトランザクションの中で呼ぶ（注文を仮登録 → 決済 API で与信 → 確定、を 1 つのトランザクションで行う、よくある書き方）
- HikariCP の取得待ちの上限は、既定の 30 秒

```kotlin:OrderService.kt（00・01a）
tx.execute {
    val orderId = insertOrder(productId, quantity, "PENDING")
    paymentClient.authorize() // 決済 API を待つあいだも、コネクションを握ったまま
    jdbc.sql("update orders set status = 'CONFIRMED' where id = ?").param(orderId).update()
    orderId
}
```

### 5.2 何秒で、どこまで壊れるか

#### 予測

3.2 をこの実験に当てはめます。下流を待つ処理 A は決済 API を呼ぶ /orders、呼ばない処理 B は /products です。決済 API の応答が 0.05 秒から 5.05 秒（遅延の 5 秒を足した値）になると、/orders の λW は 60 件/秒 × 5.05 秒 ≈ 300 本になり、40 本を大きく超えます。

![障害の広がり方](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/failure-spread.ja.png)
*スレッドだけを描いた単純化。コネクションについては下の折りたたみ*

300 本は、上限がなかった場合に、流れが落ち着いたあとの値です。障害の直後にスレッドがどう埋まるかは、1 件ずつの動きを追うと分かります。到着を等間隔にし、スレッドだけを数えて計算したのが次の図です。

![障害の直後にスレッドが埋まっていく様子（計算）](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/thread-timeline.ja.png)
*計算（実測ではない）。1 行が 1 本のスレッドで、縦に切ったときに交わる棒の数が、その瞬間の L*

障害の前は、0.05 秒の短い棒が上の 3 行を入れ替わりで使っています（/products は 1 ミリ秒足らずで返るので、棒は描いていません）。

- **尽きるまでの時間は、空いている数と到着率で決まる。** 障害の時点で処理中だった 3 件も応答が遅れるので、空いているのは 37 本です。処理を終えるリクエストがないまま、使用中のスレッドが 1 秒に 60 本ずつ増えるので、約 0.6 秒で尽きます。1 件がスレッドを握る時間が 0.6 秒より長ければ、5 秒でも 30 秒でも同じです（どこまで短くすれば尽きないかは、6.1 で求めます）
- **上限がなくても、300 本にはすぐにはならない。** 1.0 秒の時点では 63 本です。300 本で落ち着くのは、最初のリクエストが終わり始め、増える数と終わる数が釣り合う 5 秒後からです

**L = λW の λ は、そのプールに実際に入る率です。** 上限で頭打ちのあいだは、到着率とは一致しません。

- 0.6〜5 秒：空くスレッドがないので、1 件も入れない
- 5 秒以降：終わったリクエストの数だけ、入れ替わりに入る。平均 40 ÷ 5.05 ≈ 8 件/秒で、40 本 ≈ 8 件/秒 × 5.05 秒と L = λW が成り立つ（スレッドだけを考えた場合。00 ではコネクションが先に尽きるので、実際は 1 秒に約 2 件。下の折りたたみ）

入れなかったリクエストは、図の上の「空きを待つ列」に並び続けます。上限がなければ入る率は到着率の 60 件/秒のままなので、300 本になります。

予測は「障害から約 0.6 秒で 40 本が尽き、/products は待ち行列に並んで k6 の 5 秒でタイムアウトする」です。

:::details コネクションの分だけ少し早い（約 0.55 秒）
00 では決済 API をトランザクションの中で呼ぶので、コネクション 10 本が先に (10 − 3) ÷ 60 ≈ 0.12 秒で尽きます。このとき使っているスレッドは、コネクションを握った /orders の 10 本です。そのあとは /products もコネクションの空きを待つあいだ（HikariCP の取得待ちの上限は 30 秒）スレッドを握るので、残りの 30 本は 1 秒に 70 本ずつ埋まり、0.12 + 30 ÷ 70 ≈ 0.55 秒で尽きます。

頭打ちのあいだに処理を終えられるのも、コネクションを 5.05 秒ずつ握る /orders の 1 秒に約 2 件（10 ÷ 5.05）だけです。
:::

#### 実測：計算どおり、1 秒足らずで 40 本が尽きる

計測は 1 秒ごとなので、障害の直後の 1〜2 点で、コネクションの分を入れた計算と比べます。障害から t 秒後のスレッドは、計算では 3 ＋ 60t ＋ 10 ×（t − 0.117）本です。同じ設定で 3 回回しました（表は、障害からの時間の順）。

| 実行 | 障害からの時間 | 実測のスレッド | 計算 |
| --- | --- | --- | --- |
| 1 回目 | 0.344 秒 | 27 本 | 26 本 |
| 3 回目 | 0.466 秒 | 35 本 | 34 本 |
| 2 回目 | 0.919 秒 | 40 本 | 40 本（0.55 秒で尽きる） |

途中を測れた 2 回は、計算との差が 1 本でした（障害の時点で処理中だった本数が、障害の前の 1 分間で 1〜5 本とぶれるので、その範囲です）。決済 API の遅れの 5 秒を待たずに、計算どおり 1 秒足らずで尽きています。

計測は業務とは別のポートで受けているので、40 本が尽きても取れます。障害の時刻は、遅延を入れる API を呼ぶ直前と応答を受けた直後に、ミリ秒まで記録しています。3 回の生の値は [runs.md](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/00-no-defense/results/runs.md) にあります。

### 5.3 決済 API を呼ばない /products まで止まり、再起動を繰り返す

障害中の 120 秒の成功率は、/orders が 0.3%、決済 API を呼ばない /products も 1.0% でした（1.2 のグラフ）。/products の失敗のうち 91% が k6 の 5 秒のタイムアウトで、スレッドの空きを待つ待ち行列で 5 秒を過ぎています（残りは接続を断られた分）。

![00 のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/threads.png)
*40 本の横ばい → 階段状に下がる → 再起動、を繰り返す。線が途切れているのは再起動のあいだ*

order-api は障害中に 3 回再起動し、4 回目は遅延を外す直前に止まり始めました（新しいコンテナが起動したのは、遅延を外して約 25 秒後）。1 回分の流れは次のとおりです。

1. 40 本が尽きると、/livez も待ち行列に並んで答えられません。liveness probe（5 秒ごと、1 秒でタイムアウト、3 回続けて失敗したら再起動）が失敗し続け、Kubernetes がコンテナを止めにかかります
2. 止めるとき、Spring Boot は新しいリクエストを受け付けず、処理中のものが終わるのを待ちます（graceful shutdown。Spring Boot 3.4 以降の既定）。障害の約 15 秒後から、スレッドは約 5 秒ごとに 40 → 29 → 17 → 6 本と、11 本ほどずつ減りました。コネクション 10 本を 5.05 秒ずつ握る /orders が 10 件ずつ終わり、そのたびに、コネクションを取れた /products が 1 件ほどすぐに終わるからです。5.2 の折りたたみの「1 秒に約 2 件」が、ここで見えています
3. 新しいコンテナが起動すると、待っていた到着がすぐに入り、1 秒足らずでまた 40 本が尽きます

障害中の再起動は、何も解決しません。起動したとたんに、同じ λW が同じプールの大きさに当たるからです。

:::details 実測の L と λ×W が離れる
障害中の L は平均 28.3 本、λ×W は 19.8 本と、落ち着いているときは重なる 2 本の線が離れました。理由は 2 つあります。

- L の平均は、計測できた秒だけの平均です。再起動で計測が途切れた約 16 秒を含みません（途切れた秒を 0 本として 121 秒で割ると 24.5 本）
- λ×W は終わったリクエストしか数えません。遅延を外した時点で、まだ 30 本が処理中でした。再起動の直前に終わったリクエストも、計測が取りに行く前にプロセスが止まると数に入りません

L = λW は、入ったものがいずれ出ていく、流れが落ち着いた状態の関係です。入ったまま終わらないリクエストがあるあいだは、そのままでは成り立ちません。
:::

### 5.4 CPU は上がらない

![00 の CPU 使用率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/cpu.png)
*突き出ているのは、再起動したあとの JVM の起動*

障害が始まってから最初の再起動までの約 30 秒、order-api の CPU 使用率は平均 7% で、平常時の 20% より下がりました（障害中の平均の 16% には、再起動のあとの JVM の起動が入っています）。スレッドは決済 API とコネクションを待っているだけで、計算をしていないからです。タイムアウトの短い 01a・02a・03a でも、最初の再起動までの CPU は平常時と同じくらい（18〜23%）でした。どちらにしても CPU は上がらないので、CPU を見ていても、CPU を基準にしたオートスケールでも、この障害には気づけません。

### 5.5 学び

- スレッドやコネクションを握ったまま下流を待つ処理は、下流の遅れを、そのプールを共有するすべての処理に広げる
- プールが尽きるほどの遅延なら、尽きるまでの時間は遅延の長さによらず「空いている数 ÷ 到着率」で決まる
- 尽きているあいだも CPU は上がらない。再起動しても、同じ λW が同じプールの大きさに当たるだけ

## 6. W を抑える：タイムアウトとトランザクションの範囲（01a・01b）

### 6.1 タイムアウトの下限と上限を計算する

W を抑える一番の手段は、下流の呼び出しのタイムアウトです。短すぎれば平常時にも失敗し、長すぎれば障害時にスレッドが尽きます。そこで、下限と上限を先に計算します。

![タイムアウトの下限と上限](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/timeout-window.ja.png)
*上の段が 01a・01b の決済 API とスレッド。下の 2 段は 6.2 と 7.1 で使う*

#### 下限：平常時の p99 に上乗せする

決済 API の平常時の p99 は 120ms です。タイムアウトをこれより短くすると、平常時にも 1% 以上の呼び出しがタイムアウトします。どれだけ上乗せするかは、平常時の分布の裾（p99.9 や、混む時間帯の p99）を見て決めます。ここでは約 200ms にします。

#### 上限：プールの大きさ × 使ってよい割合 ÷ 1 台あたりのピーク時の到着率

決済 API が完全に返らなくなると、/orders 1 件はタイムアウトまでスレッドを握るので、W はタイムアウトの値そのものになります。λW がスレッドの数に収まるには「タイムアウト ≤ スレッドの数 ÷ 到着率」が条件で、40 ÷ 60 ≈ 0.67 秒です。5.2 で見たとおり、W がこれより長いと、W がいくつでも同じ速さで尽きます。

ここから、ほかの API の分と到着のばらつきの分を残します。この記事では使ってよい割合を 0.7 として、40 × 0.7 ÷ 60 ≈ 467ms を上限にします。0.7 は計算から出る値ではなく、設計で選ぶ割合です。到着率には、その下流を呼ぶ処理の、1 台あたりの、秒単位のピークを使います。また、この上限は、遅くなる下流が 1 つで、ほかの下流は同時には遅くならないことを前提にしています。

この 200〜467ms のあいだから、300ms を選びます。HTTP クライアントの応答のタイムアウトで掛けます。

```kotlin:PaymentClient.kt
JdkClientHttpRequestFactory(
    HttpClient.newBuilder().connectTimeout(props.payment.connectTimeout).build(),
).apply { setReadTimeout(props.payment.timeout) } // 応答のタイムアウト（01a 以降は 300ms）
```

:::message
上限は、ほかにもあります。
- **上流（クライアント）のタイムアウト**：1 件の W の最大値（タイムアウト × 試行回数 ＋ 待ち）がこれより長いと、誰も待っていない処理にスレッドを使います。00 の障害中、order-api が返した 1 件の処理時間は平均 9.9 秒で、k6 は 5 秒でとうにあきらめていました
- **接続のタイムアウト**：この実験の接続のタイムアウトは 1 秒で、上限の 467ms より長い値です。下流が接続を受け付けなくなる障害では、ここが W になります（この実験では試していません）
:::

### 6.2 タイムアウトを 300ms にしても、コネクションが先に尽きる（01a）

#### 予測

スレッドだけを見れば、λW は 60 件/秒 × 0.3 秒 = 18 本で、40 本に収まります。ところが 01a は、決済 API をトランザクションの中で呼んだままです。コネクションも 0.3 秒握るので、コネクションの λW も 18 本になり、10 本を超えます。

コネクション 10 本でさばけるのは、10 ÷ 0.3 ≈ 1 秒に 33 件で、到着の 60 件より少なくなります。残りの /orders と /products は、スレッドを握ったままコネクションの空きを待ちます。取得待ちの上限は HikariCP の既定の 30 秒と長いので、早めにあきらめて返ることもありません。計算すると、障害から約 0.85 秒でスレッドも 40 本が尽きます。

:::details 約 0.85 秒の計算
- 0〜0.12 秒：コネクションが (10 − 3) ÷ 60 ≈ 0.12 秒で尽きる。スレッドは約 10 本
- 0.12〜0.3 秒：最初のタイムアウト（0.3 秒）まで、終わるリクエストはない。/orders と /products の 1 秒 70 件がそのままスレッドを握り、0.3 秒で約 23 本
- 0.3 秒〜：コネクションを握った /orders が 1 秒に約 33 件終わり、取得待ちの中で /orders のあいだに並んだ /products も 1 秒に約 5.5 件（33 × 10/60）流れる。スレッドは 1 秒に 70 − 33 − 5.5 ≈ 31 本ずつ増え、残り 17 本が約 0.55 秒で尽きる
:::

#### 実測：0.86 秒で 39 本、/products は 12%

![01a の HikariCP](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01a-timeout/results/panels/hikari.png)
*実線が使用中、点線が取得待ちの数、薄い破線がプールの大きさ。障害の直後から 10 本とも使われ、取得待ちの数が 30 前後まで積み上がる。途切れているのは再起動のあいだ*

コネクションは障害の直後から 10 本とも使われ、取得待ちの数は 30 前後まで積み上がりました（最大 31）。スレッドは、障害の 0.86 秒後の最初の計測で 39 本、1.86 秒後に 40 本でした（計算は約 0.85 秒で尽きる）。再起動は 5 回で、障害中に決済 API が受けた呼び出しは平均 17 件/秒でした。再起動で止まっていた約 45 秒を含めた平均で、動いているあいだは計算どおり 1 秒に約 33 件です。

/products の成功率は 12.3% で、00 の 1.0% より少しだけ通りました。通ったのは、再起動した直後の数秒だけです。コネクションが 0.3 秒ずつで回るので、待ち行列がまだ短いうちは、/products も k6 の 5 秒以内に順番が来ます（00 では 5.05 秒に 10 件しか回らない）。待ち行列が伸びれば、また 5 秒を超えます。タイムアウトを入れても、/products は守れていません。

タイムアウトは 1 か所ではありません。スレッドを握ったまま待つ場所（下流の応答、コネクションの取得、リトライの待ち）ごとに、W の上限を確かめる必要があります。コネクションの数で上限を計算し直すと 10 × 0.7 ÷ 60 ≈ 117ms で、下限の 200ms より短くなります（6.1 の図の 2 段目）。下限が上限を超えるので、タイムアウトの値では守れません。そこで、決済 API を待つあいだコネクションを握らないようにします。

### 6.3 決済 API をトランザクションの外で呼ぶと守れる（01b）

決済 API を先に呼び、コネクションを握るのは DB に書き込む一瞬だけにします。あわせて HikariCP の取得待ちの上限を 250ms（設定できる最小値）に縮めますが、01b ではコネクションの取得待ちが起きない（取得待ちの数は 0 のまま）ので、結果にはほぼ効いていません。

```kotlin:OrderService.kt（01b 以降）
paymentClient.authorize() // 決済 API はトランザクションの外で、先に呼ぶ
tx.execute { insertOrder(productId, quantity, "CONFIRMED") }
```

:::message
本番では、整合性の扱いが別に必要です。タイムアウトした与信は「失敗」ではなく「結果が分からない」状態です。「PENDING を短いトランザクションで書く → トランザクションの外で与信 → 別の短いトランザクションで確定」の形にすれば、コネクションを握らずに、照合のための記録も残せます。リトライするなら、同じ冪等キーで送り直せることが前提です（8 章と 9 章のリトライも同じです）。この記事では、スレッドとコネクションを握る時間の違いだけを見ます。
:::

#### 予測

コネクションを握るのは書き込みの数ミリ秒だけになり、コネクションの λW は 1 本未満です。スレッドの λW は 60 × 0.3 = 18 本で、40 本に収まります。/orders は 0.3 秒でタイムアウトして失敗を返し、/products は影響を受けないはずです。

#### 実測：スレッドは 18 本で横ばい、/products は 100%

![01b の実測の L と λ×W](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/littles-law.png)
*緑が使用中のスレッド（実測の L）、黄が λ×W。平常時は約 3 本、障害中は約 18 本で重なる*

![01b の成功率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/success.png)
*/orders（紫）は失敗するが、/products（青緑）は 100% のまま。成功率は直近 10 秒で数えているので、斜めに下がって見える*

障害中のスレッドは平均 18.1 本（最大 22 本）で、計算の 18 本どおりでした。λ×W も 18.1 本で、2.3 のとおり 2 本の線が重なっています（平常時は L が 3.4 本、λ×W が 3.1 本）。/products の成功率は 100%、再起動は 0 回で、遅延を外してから 7 秒で戻りました（測り方の下限に近い値）。/orders は失敗しますが（成功率 0.5%）、失敗が 0.3 秒で返るので、スレッドを使い切りません。

### 6.4 学び

- タイムアウトは「下流の平常時の p99 ＋ 上乗せ」と「プールの大きさ × 使ってよい割合 ÷ 下流を呼ぶ処理の 1 台あたりのピーク時の到着率」のあいだに置く。上流のタイムアウトより短くし、接続のタイムアウトも同じ上限に照らす
- スレッドを握ったまま待つ場所は 1 つではない。下流の応答、コネクションの取得、リトライの待ちのすべてに上限を付け、プールごとに λW を計算する
- 下限が上限を超えるプールは、タイムアウトの値ではなく、そのプールを握らない形に変える（トランザクションの外で下流を呼ぶ）

## 7. L に上限を付ける：バルクヘッド（02a・02b）

### 7.1 p99 が長い下流では、タイムアウトの下限が上限を超える（02a）

01b でうまくいったのは、決済 API の p99（120ms）が、スレッドから見た上限（467ms）より十分に短かったからです。p99 が長い下流では、下限が上限を超えて、両方を満たす値がありません。外部の決済代行のように p99 が秒単位の下流も珍しくなく、たとえば Tomcat の 200 本で 1 台あたり 1 秒に 100 件を受けるなら、上限は 200 × 0.7 ÷ 100 ＝ 1.4 秒です。p99 が 2 秒なら、下限が上限を超えます。

02a では、決済 API を平均 100ms・p99 600ms に遅くし（スレッドは 12 本に増やして、さばける率は 120 件/秒のまま）、タイムアウトを p99 に上乗せした 800ms にします。決済 API はトランザクションの外で呼びます（01b と同じ）。

#### 予測

6.1 の図の 3 段目のとおり、下限の約 800ms が上限の 467ms を超えていて、両方を満たす値がありません。障害中の λW は 60 × 0.8 = 48 本で 40 本を超えます。平常時の L は実測で約 6.6 本（計算の 60 × 0.1 = 6 に、2.3 と同じ L と λ×W のずれが約 0.4 本乗る）なので、空いている約 33 本が 1 秒に 60 本ずつ埋まり、約 0.55 秒でスレッドが尽きます。

#### 実測：1 秒ほどで尽き、/products は 25%

障害の 0.48 秒後の最初の計測で 33 本（計算は 35 本）、1.48 秒後に 40 本でした。障害中の /products の成功率は 25.3%、再起動は 5 回です。

平常時の /orders の成功率は 99.4% でした。タイムアウトを p99 ＋ 上乗せにしても、p99 より遅い 1% のうち一部（ここでは 0.6%）はタイムアウトします。下限ちょうどにタイムアウトを置いても、平常時にこれだけは払うことになります。

### 7.2 バルクヘッドで、決済 API を同時に呼ぶ数に上限を付ける（02b）

タイムアウトで守れないなら、W ではなく L に直接上限を付けます。Resilience4j の Bulkhead で、決済 API を同時に呼ぶ数（同時実行数）を 12 までにし、上限に達していたら待たずに断ります。

```yaml:application.yml
resilience4j:
  bulkhead:
    instances:
      payment:
        max-concurrent-calls: 12
        max-wait-duration: 0ms # 上限に達していたら待たずに断る
```

#### 予測

決済 API を待ってスレッドを握る /orders は、最大 12 本です。バルクヘッドを通れる率は λ = L ÷ W = 12 ÷ 0.8 = 15 件/秒で、残りの約 45 件/秒はすぐに断られます。スレッドは 12 本と少しで、40 本に収まります。

#### 実測：決済 API に届いたのは 14.9 件/秒、スレッドは最大 13 本、/products は 100%

![02b の決済 API の呼び出し](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/02b-bulkhead/results/panels/payment-calls.png)
*緑が成功、黄が失敗（0.8 秒のタイムアウト）。バルクヘッドに断られた分は、決済 API まで届かないので数に入らない*

障害中に決済 API まで届いた呼び出しは 14.9 件/秒で、計算の 15 件/秒どおりでした。スレッドは障害中も 12 本前後で、最大 13 本です。/products の成功率は 100%、再起動は 0 回で、遅延を外してから 9 秒で戻りました。

### 7.3 同時実行数は、断ってよい率から決める

バルクヘッドの同時実行数は、小さすぎれば平常時にも断り、大きすぎれば障害時にスレッドを多く握ります。目安の下限は平常時の同時実行数とそのばらつき、上限はほかの API の分を残したスレッドの数（40 × 0.7 ＝ 28）です。12 は、平常時の L（60 件/秒 × 0.1 秒 = 6）の 2 倍で、下限に近い値です。

この環境で平常時に断った呼び出しは、1 分に 1 件ほど（約 3,600 件中）でした。ただしこれは、k6 がリクエストを等間隔に送っているからです。到着がランダム（ポアソン到着）なら、断る率はアーランの B 式（同時に使える数が決まっていて、空いていなければ断る仕組みで、断る確率を出す式）で計算できます。平均 6 なら、次のとおりです。

| 同時実行数 | 平常時に断る率 |
| --- | --- |
| 12 | 約 1.1% |
| 14 | 約 0.2% |
| 16 | 約 0.03% |

「平常時の L の 2 倍」という倍率は、規模で意味が変わります。同じ 2 倍でも、平均 30・同時実行数 60 なら、断るのは 100 万件に 1 件以下です。同時実行数は倍率ではなく、断ってよい率から決めます。

### 7.4 学び

- 下流の p99 が長く、タイムアウトの下限が上限を超えるなら、タイムアウトではなく、下流を同時に呼ぶ数に上限を付ける
- バルクヘッドを通れる率は「同時実行数 ÷ W」で決まる。上限を超えた分は待たせずにすぐ断る。待たせると、断るまでの時間が新しい W になる
- 同時実行数は、平常時の同時実行数とばらつきから、断ってよい率で決める。大きくても、ほかの処理の分を残したスレッド数まで

## 8. リトライは λ を増やし、サーキットブレーカーは λ を絞る（03a・03b）

### 8.1 リトライで、300ms でもスレッドが尽きる（03a）

01b（タイムアウト 300ms、決済 API はトランザクションの外）に、Resilience4j の Retry を足します。最大 3 回試行し、試行の間に 500ms 待ちます（どちらも Retry の既定値）。決済のように副作用のある呼び出しは、冪等キーがない限りリトライしてはいけません（6.3 の注）。ここではスレッドと呼び出しの数の動きだけを見ます。

#### 予測

1 件の W は、最大 3 × 0.3 + 2 × 0.5 = 1.9 秒です。試行の間の待ちも、スレッドを握ったままです。λW は 60 × 1.9 = 114 本で 40 本を超え、(40 − 3) ÷ 60 ≈ 0.6 秒でスレッドが尽きます。01b では安全だった 300ms が、リトライによって安全でなくなります。決済 API への呼び出しも、最大 3 倍に増えます。

#### 実測：1 秒ほどで尽き、/products は 7〜8%

障害の 0.55 秒後の最初の計測で 37 本（計算は 36 本）、1.55 秒後に 40 本でした。同じ設定で 8 回回し、障害中の /products の成功率は 7.4〜8.3%、再起動はどの回も 5 回でした。

### 8.2 遅延を外しても、すぐには戻らない

遅延を外してから戻るまでの時間は、8 回で 12〜46 秒でした。リトライのない 00（38 秒）・01a（43 秒）・02a（37 秒）と比べて遅いわけではありません。違うのは、遅延を外したあとの決済 API です。payment-api のスレッドが上限の 6 本に張り付いた時間は、リトライのない 00・01a では 5〜6 秒、03a では 8〜22 秒でした。

この 8 回はすべて戻りました。ただ、k6 が VU を途中で作り足していたころ（負荷のかけ方を直す前）に回した 4 回では、1 回が 2 分たっても戻りませんでした（このほかにも 1 回戻らなかったが、直前の実行の再起動の影響が残っていた）。次のグラフはその回です。12 回の値は [runs.md](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/03a-retry/results/runs.md) にあります。

![戻らなかった回の成功率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03a-retry/results/panels/success-not-recovered.png)
*負荷のかけ方を直す前の回。遅延を外したあと（赤い帯の右）、一度は 100% まで戻ってから、また 0% に落ちる*

#### 何が起きていたか

どの回でも、遅延を外したあとに再起動した order-api が受け付けを始めると、/orders は、スレッドが 40 本に張り付いていたあいだの平均で 1 秒に約 70〜100 件と、到着率の 60 件/秒を超えて処理されました（起動を待つあいだに溜まっていた分が重なったと考えられます）。リトライも加わって、決済 API への呼び出しは 112〜123 件/秒まで増え、payment-api のスレッドは上限の 6 本に張り付きました。そのあいだ payment-api の中で待ち行列ができて応答が 300ms を超え、タイムアウトしたものがリトライされて、呼び出しがまた増えます。戻らなかった回では、多いときで毎秒約 38 件の呼び出しがタイムアウトし、約 30 件がリトライのすえ成功していました。

payment-api が上限に張り付いているあいだ、order-api のスレッドも 40 本で埋まり、/livez も待ち行列に並びます。待ち時間が liveness probe のタイムアウト（1 秒）を超える状態が 3 回続けば再起動され、起動のたびに同じことを繰り返します。Kubernetes は再起動の間隔を延ばしていきます（CrashLoopBackOff）。戻った 8 回でも、再起動のあと 8〜21 秒はスレッドが 40 本のままでした。21 秒続いても再起動されなかった回がある一方で、戻らなかった回は 12 秒で再起動されています。分かれ目は 40 本でいた時間ではなく、/livez の待ちが probe の 1 秒を超えたかどうかです。

#### リトルの法則で読むと

payment-api がさばける率は λ = L ÷ W = 6 本 ÷ 0.05 秒 = 120 件/秒で、平常時の 60 件/秒に対して、処理能力の余力は 2 倍しかありません。最大 3 回のリトライは呼び出しを最大 3 倍にするので、この余力を超えます。さばける率の近くまで呼ぶと、待ち行列ができて W が伸び、タイムアウトしてまたリトライになります。そのうえ再起動のたびに溜まった分が一度に流れ込むので、遅延を取り除いても、遅い状態がしばらく続きます。このように、原因が取り除かれても続く障害は、metastable failure と呼ばれています。

### 8.3 サーキットブレーカーで、決済 API への呼び出しを止める（03b）

03a に Resilience4j の CircuitBreaker を足します。直近 10 秒の呼び出しが 20 回以上あり、その失敗率が 50% 以上なら開きます。開いている 5 秒は決済 API を呼ばずにすぐ失敗を返し、そのあと半開（試しに 10 回だけ呼び、成功すれば閉じて元に戻り、失敗が多ければまた開く状態）に移ります。

包む順は Retry(CircuitBreaker(Bulkhead(呼び出し))) で、リトライが一番外側です。試行のたびにブレーカーを通り直し、ブレーカーに断られた呼び出しはリトライしないよう、例外を除外しています。

```yaml:application.yml
resilience4j:
  retry:
    instances:
      payment:
        ignore-exceptions: # 断られた呼び出しはリトライしない
          - io.github.resilience4j.bulkhead.BulkheadFullException
          - io.github.resilience4j.circuitbreaker.CallNotPermittedException
```

#### 予測

開いているあいだ、決済 API への呼び出しはほぼ 0 になり、/orders はすぐ失敗を返すので、W もほぼ 0 になります。

最初は「20 回の失敗がたまれば開く」と読んで、0.6〜0.7 秒で開くと予測しましたが、外れました。20 回は失敗率を計算し始めるのに要る呼び出しの数で、平常時の流れですでに満たしています。開く条件は、直近 10 秒の呼び出しの半分以上が失敗であることです。

計測から導き直すと、次のようになります。障害の直前の 10 秒に成功した約 550 件が集計に残っていて（集計は 1 秒ごとに区切って進むので、60 件/秒 × 10 秒より少し少ない）、成功は 1 秒に約 60 件ずつ集計から抜けます。失敗は 0.3 秒後から、1 秒に約 60 件ずつ増えます（スレッド 40 本が、1.9 秒に 3 回ずつ呼ぶので 40 × 3 ÷ 1.9 ≈ 63）。60 ×（t − 0.3）＝ 550 − 60t から、開くのは障害から約 4.7 秒後です。障害中に呼ぶ率が平常時と同じくらいなので、おおよそ「集計する期間 × しきい値」になっています。

#### 実測：開いたのは約 4〜5 秒後、決済 API への呼び出しは平均 4 件/秒に

ブレーカーの状態のメトリクスでは、障害の 3.91 秒後の計測ではまだ閉じていて、4.91 秒後には開いていました。

![03b の決済 API の呼び出し](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03b-circuit-breaker/results/panels/payment-calls.png)
*緑が成功、黄が失敗。直近 10 秒で平均しているので、開く前の失敗の山は低く出る。開いたあとは、5 秒ごとの半開の試しだけが届く*

障害中に決済 API が受けた呼び出しは平均 4.2 件/秒で、01b の 60 件/秒から大きく減りました。/products の成功率は 100%、再起動は 0 回で、遅延を外してから 11 秒で戻りました。ブレーカーが開いているあいだは決済 API を呼ばないので、遅延が外れても次の半開まで（最大 5 秒）は戻れず、01b の 7 秒より少し遅くなります。

### 8.4 ブレーカーが開くまでの約 5 秒

![03b のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03b-circuit-breaker/results/panels/threads.png)
*障害の直後の約 4 秒、40 本に張り付く（ブレーカーが開くまで）。そのあとの細い山は、5 秒ごとの半開の試し*

開くまでの約 5 秒は、03a と同じことが起きます。/orders は 1 回目の失敗のあとリトライの待ちに入り、スレッドを握ったままです。スレッドは障害の 0.91 秒後から 3.91 秒後までの計測で 40 本のまま、4.91 秒後に 29 本、5.91 秒後に 0 本でした。

/products が 100% のままだったのは、待ち行列で待った時間が最長でも約 2.8 秒で、k6 のタイムアウトの 5 秒より短かったからです（障害中の /products 1,210 件のうち、2 秒を超えたのは 16 件）。スレッドは約 4 秒 40 本のままでしたが、最初に入った /orders は 3 回の試行を終える約 1.9 秒後から順にスレッドを返すので、そのあいだも待ち行列は進みます。上流のタイムアウトが 2 秒なら、十数件が失敗していたはずです。そのあと 5 秒ごとに立ち上がる 10 本ほどの山は、半開で試した 10 件が、タイムアウトとリトライの待ちでスレッドを握る分です。

このあいだを、9 章でバルクヘッドと組み合わせて守ります。

### 8.5 学び

- リトライは、W（試行の間の待ちを含む）と下流を呼ぶ数の両方を増やす。入れたら、W の上限を「試行回数 × タイムアウト ＋ 待ちの合計」で計算し直す
- 試行回数が下流の処理能力の余力（さばける率 ÷ 平常時の率）を超えると、下流の遅延が直っても遅い状態がしばらく続きうる。そのあいだに liveness probe が失敗し続けると、再起動を繰り返して戻らないこともある。リトライは回数ではなく全体に対する割合（リトライ予算）で絞り、待ちにはジッターを入れる。上流もリトライするなら、回数は掛け算になる
- 直近の一定時間で失敗率を数えるサーキットブレーカーは、障害中に呼ぶ率が平常時と同じくらいなら、およそ「集計する期間 × しきい値」がたつまで開かない。開いているあいだは、下流が直っても戻れない
- 設定値の意味は読み違えやすい。「最低の呼び出し数」を開く条件と読み違えると、開くまでの時間を一桁見誤る

## 9. すべての防御を入れて、もう一度壊す（04）

04 では、タイムアウト 300ms、決済 API はトランザクションの外、取得待ちの上限 250ms、バルクヘッド 12、サーキットブレーカーを入れ、リトライは控えめに最大 2 回試行・100ms おきにします。

### 9.1 ブレーカーが開くまでのあいだを、バルクヘッドが守る

#### 予測

リトライを控えめにしても、1 件の W は最大 0.3 + 0.1 + 0.3 = 0.7 秒で、バルクヘッドがなければ λW = 60 × 0.7 = 42 本となり、40 本を超えます。バルクヘッドがあれば、決済 API を待ってスレッドを握るのは 12 本までです。ただし、リトライの待ち（100ms）にいるあいだはバルクヘッドの外なので、スレッドは「12 本 ＋ リトライの待ちにいる分」になります。

#### 実測：スレッドは最大 14 本、ブレーカーは 3〜4 秒後に開いた

![04 のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/04-all-defenses/results/panels/threads.png)
*ブレーカーが開くまでの数秒も、14 本まで*

スレッドは最大 14 本に収まりました。ブレーカーは障害の 3〜4 秒後に開き、03b の約 4.7 秒より早くなりました。包む順が Retry(CircuitBreaker(Bulkhead(呼び出し))) なので、バルクヘッドに断られた呼び出しも、ブレーカーは失敗として数えます（Resilience4j は、既定ではすべての例外を失敗として数える）。タイムアウトの約 37 件/秒に、断られた約 45〜50 件/秒が加わり、失敗は 1 秒に約 85 件ずつ増えました。障害中に決済 API が受けた呼び出しは平均 3.1 件/秒、/products の成功率は 100%、再起動は 0 回で、遅延を外してから 9 秒で戻りました。

### 9.2 8 つのシナリオの比較

| シナリオ | 入れたもの | 障害中の /products | スレッドの最大 | 決済 API が受けた呼び出し | 再起動 | 遅延を外してから戻るまで |
| --- | --- | --- | --- | --- | --- | --- |
| 00 | なし | 1.0% | 40 本 | 2 件/秒 | 4 回 | 38 秒 |
| 01a | タイムアウト 300ms | 12.3% | 40 本 | 17 件/秒 | 5 回 | 43 秒 |
| 01b | 01a ＋ トランザクションの外 | 100% | 22 本 | 60 件/秒 | 0 回 | 7 秒 |
| 02a | 01b で、決済 API の p99 が 600ms | 25.3% | 40 本 | 29 件/秒 | 5 回 | 37 秒 |
| 02b | 02a ＋ バルクヘッド | 100% | 13 本 | 15 件/秒 | 0 回 | 9 秒 |
| 03a | 01b ＋ リトライ | 8.2% | 40 本 | 30 件/秒 | 5 回 | 19 秒（8 回で 12〜46 秒） |
| 03b | 03a ＋ サーキットブレーカー | 100% | 40 本（約 4 秒） | 4 件/秒 | 0 回 | 11 秒 |
| 04 | すべて | 100% | 14 本 | 3 件/秒 | 0 回 | 9 秒 |

どれも 1 回の実行の値です。回復までの時間は実行ごとのばらつきが大きく、すぐに戻っても 6〜7 秒と出る測り方です。00 と 03a のほかの回の値は各シナリオの runs.md に、残りの列（CPU、平常時の L と λ×W など）は [SUMMARY.md](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/SUMMARY.md) にあります。

- /products を守るだけなら、01b（タイムアウトと、トランザクションの外で呼ぶこと）でも足りています。バルクヘッドはタイムアウトの下限が上限を超える下流（02b）と、ブレーカーが開くまでのあいだ（04）で、ブレーカーは決済 API への呼び出しを 60 件/秒から 3〜4 件/秒に減らすことで効いています
- スレッドが尽きたままになったシナリオ（00・01a・02a・03a）は、どれも 4〜5 回再起動しました。liveness probe を業務と同じスレッドで受けているからです（10.5）

### 9.3 学び

- サーキットブレーカーが開くまでのあいだは、バルクヘッドが、下流を待ってスレッドを握る数を抑える
- 包む順で振る舞いが変わる。リトライが外側なら、リトライの待ちのあいだ握るスレッドはバルクヘッドの上限に入らない。ブレーカーがバルクヘッドの外側なら、バルクヘッドに断られた呼び出しも失敗として数え、早く開く

## 10. 障害時のキャパシティプランニング：自分のサービスを L = λW で点検する

### 10.1 プールと上限を書き出す

リクエストが握ったまま待つプールと、その大きさ、使っている処理を書き出します。

- リクエストを処理するスレッド（Tomcat なら `server.tomcat.threads.max`、既定 200）
- DB のコネクション（HikariCP なら `maximum-pool-size`、既定 10）
- HTTP クライアントの接続プール（Apache HttpClient 5 の接続プールは、既定で宛先ごとに 5 本。ここが一番小さいプールになることがある）
- 非同期処理のスレッドプール、バルクヘッドのような同時実行数の上限
- 仮想スレッドを使っているなら、スレッドの上限はありません。下流ごとに同時実行数の上限があるかを確かめます

### 10.2 障害時の W の最大値を足し算する

下流が返らなくなったとき、1 件がスレッドやコネクションを握る最長の時間を、設定から足し算します。

- （接続のタイムアウト ＋ 応答のタイムアウト）× 試行回数 ＋ リトライの待ちの合計
- コネクションの取得待ちの上限（HikariCP の既定は 30 秒）と、HTTP クライアントの接続プールの取得待ちの上限
- トランザクションの中で下流を呼んでいれば、その時間はコネクションの W にも入る。JPA（Hibernate）で Open Session in View（Spring Boot の既定で有効）を使っていると、トランザクションの外で下流を呼んでも、リクエストの終わりまでコネクションを握り続けることがある

HTTP クライアントには、応答のタイムアウトの既定が無制限のものも多くあります。また「読み取りのタイムアウト」は、バイトが届かない時間の上限で、全体の時間の上限ではないことがあります。最後に、合計が上流のタイムアウトより短いかを確かめます。

### 10.3 λW とプールの大きさを比べる

プールごとに次の表を埋め、「下流を呼ぶ処理の到着率 × W の最大値」が「プールの大きさ × 使ってよい割合」に収まるかを確かめます。下流が複数あるときは、同時に遅くなりうる組み合わせで λW を足します。

| プール | 大きさ | 下流を待つ処理 | その到着率（1 台あたり、秒単位のピーク） | 障害時の W の最大 | λW | 大きさ × 0.7 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 例：Tomcat | 200 | 検索 API（外部の在庫 API を呼ぶ） | 250 件/秒 | 1.1 秒 | 275 | 140 | 超える |

超えていれば、そのプールは下流の障害で尽きます。尽きるまでの時間は「空いている数 ÷ 到着率」で、1 台あたりの到着率が高いほど短くなります。

:::details 値の取り方（Prometheus と Micrometer の例）
```promql
# 下流を呼ぶ処理の、1 台あたりの到着率（1 分の rate の最大）
max_over_time(max by (pod) (rate(http_server_requests_seconds_count{uri="/search"}[1m]))[1d:1m])
# 下流ごとの平常時の p99（percentiles-histogram を有効にしておく）
histogram_quantile(0.99, sum by (le, client_name) (rate(http_client_requests_seconds_bucket[5m])))
```

1 分の rate は秒単位のピークより低く出ます。到着がランダムなら、1 秒あたりの件数は平均 λ に対しておおよそ λ ＋ 3√λ まで振れます。
:::

### 10.4 守り方を選ぶ

| 状況 | 守り方 |
| --- | --- |
| タイムアウトの下限が上限より小さい | W を抑える。タイムアウトを下限と上限のあいだに置く |
| 下流を待つあいだ、小さいプール（コネクションなど）も握っている | そのプールを握らない形に変える。トランザクションの外で下流を呼ぶ |
| タイムアウトの下限が上限を超える | L に上限を付ける。下流を同時に呼ぶ数に上限を付け、上限を超えた分はすぐ断る |
| 下流を守りたい、早く失敗させたい | λ を絞る。サーキットブレーカー（開くまでのあいだはバルクヘッドで守る） |
| 下流を待つだけで CPU を使わず、メモリにも余裕がある | プールや台数を大きくする。大きさを「λW ÷ 使ってよい割合」以上にする（コネクションは DB の接続数の上限に当たる） |
| リトライを入れたい | 冪等であることを確かめ、回数と待ちを控えめにして、W の最大値を計算し直す |

### 10.5 liveness probe を業務と同じスレッドで受けていないか

liveness probe を業務と同じスレッドプールで受けていると、下流の障害でプールが尽きたときに probe も答えられず、コンテナが再起動されます。再起動しても、起動したとたんに同じ λW が同じプールの大きさに当たるので、回復が遅れるだけです（9.2）。

一方で、Spring Boot のドキュメントは、probe を業務と同じポートでも受ける構成（`management.endpoint.health.probes.add-additional-paths`）を勧めています。業務とは別のポートだけで受けると、業務側が接続を受けられなくなっても probe が成功してしまうからです。liveness probe は「プロセスが壊れていて、再起動で直る」ときだけ失敗させるものです。選び方は次のとおりです。

| 構成 | 得られること | 払うもの |
| --- | --- | --- |
| liveness を業務のポートで受ける（Spring Boot の推奨） | 業務側が接続を受けられなくなったことを検知できる | 下流の障害で再起動を繰り返す |
| liveness を管理ポートで、readiness を業務のポートで受ける | 下流の障害で再起動しない | readiness がすべてのレプリカで落ちると、Service に送り先がなくなり、下流を呼ばない処理も含めてすべて断られる |
| 業務のポートのまま、再起動を決めるまでの時間（間隔 × 回数）を長くする | その中間 | 本当に壊れたときの再起動も遅れる |

どの構成でも、業務のスレッドが尽きたことは、再起動ではなく 10.6 の監視で知ります。

### 10.6 「使用中の数 ÷ プールの大きさ」を監視する

```promql
# Pod ごとの「使用中の数 ÷ プールの大きさ」（ラベル名は環境に合わせる）
max by (pod) (tomcat_threads_busy_threads / tomcat_threads_config_max_threads)
max by (pod) (hikaricp_connections_active / hikaricp_connections_max)
max by (pod) (hikaricp_connections_pending)
# 下流ごとに、進行中の呼び出しの数（Micrometer の active。ヒストグラムを有効にしていれば _gcount）
sum by (pod, client_name) (http_client_requests_active_seconds_active_count)
# バルクヘッドの空き
min by (pod) (resilience4j_bulkhead_available_concurrent_calls)
```

- `tomcat_threads_*` は、`server.tomcat.mbeanregistry.enabled=true` にしないと出ません
- メトリクスは業務とは別のポート（`management.server.port`）で出しておけば、業務のスレッドが尽きても測れます
- 下流ごとの呼び出しの数は、終わった呼び出しから計算する `rate(_sum)` ではなく、進行中の数で見ます。返ってこない呼び出しは、終わるまで `rate(_sum)` に入らないからです
- 尽きるまでの時間は短い（この実験では 1 秒足らず）ので、アラートで防ぐことはできません。役に立つのは、CPU が上がらず原因を見誤りそうなときに、どのプールが尽き、どの下流の呼び出しが溜まったかをすぐ示すことです

### 10.7 遅延を注入して確かめる

計算は、前提が合っていて初めて当たります。予測と合格条件（「障害から 2 秒以内にスレッドが上限に達する」「下流を呼ばない処理の成功率が 99% 以上」など）を先に書いてから、下流に遅延を入れ、オープンモデルの負荷をかけて確かめます。遅延は、Toxiproxy のようなプロキシや、サービスメッシュの fault injection で入れられます（この記事の入れ方は [run.sh](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/run.sh)）。予測が外れたら、どの前提が違ったかを調べます。それ自体が、設定を正しく読めているかの点検になります。

## 11. まとめ

- スレッドやコネクションを握ったまま下流を待つ処理があると、下流の遅れは、そのプールを共有するすべての処理に広がる。プールが尽きるほどの遅延なら、尽きるまでの時間は遅延の長さによらず「空いている数 ÷ 到着率」で決まる
- 守り方は、W・L・λ のどれを小さくするかで決まる。タイムアウトの下限と上限、トランザクションの範囲、同時実行数、サーキットブレーカーが開くまでの時間を、それぞれ計算で決められる
- リトライは逆向きに働き、下流がさばける率の近くまで呼ぶと、下流の遅延が直っても遅い状態がしばらく続きうる
- CPU は上がらないので、見るのは「使用中の数 ÷ プールの大きさ」

まず確かめるなら、次の 2 つです。トランザクションの中で外部の API を呼んでいないか。HTTP クライアントに、下限と上限のあいだのタイムアウトが設定されているか。

## 付録

### A. 他にもこんな場面で使える

- **コネクションプールの大きさ**：ピーク時の到着率 × 1 件がコネクションを握る平均時間を、使ってよい割合で割る
- **非同期のワーカーやコンシューマーの並列数**：処理したい率 × 1 件の処理時間
- **スケールアウトで守るときの台数**：障害時の λW ÷ 1 台あたりのプールの大きさ。プールごとに計算し、大きいほうを取る（00 なら、スレッドでは 300 ÷ 40 ≈ 8 倍、コネクションでは 300 ÷ 10 ＝ 30 倍で、DB の接続数の上限にも当たる）

### B. この実験環境の限界

- k6 の constant-arrival-rate はリクエストを等間隔に送るので、本番のトラフィックより、ばらつき（バースト）を小さく見積もります
- 障害は、応答の遅延だけです。下流がエラーを返す場合や、接続の確立に時間がかかる場合は試していません
- Toxiproxy は応答を遅らせるだけなので、障害中の payment-api 自体はほぼ暇です。サーキットブレーカーが下流を守る効果は、障害中には確かめられていません
- order-api のレプリカは 1 つです。複数あるとき、readiness で外れた Pod の分が残りの Pod に寄る動きは見ていません
- リトライの利点（一時的な失敗を吸収すること）は測っていません。リトライで戻らなくなる頻度も、この実験の回数では言えません
- メトリクスは 1 秒ごとの計測なので、「何秒で尽きたか」には 1 秒の幅があります。HikariCP はプールの統計を 1 秒キャッシュするので、使用中・取得待ちの数が 1 つ前の計測の値のままのこともあります
- 回復時間は、遅延を外したときに order-api が再起動の途中かどうかで、実行ごとにばらつきます
