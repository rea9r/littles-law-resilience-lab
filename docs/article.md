## TL;DR

- 決済 API の応答に 5 秒の遅延を入れると、注文 API（order-api）の 40 本のスレッドが 1 秒ほどで埋まり、決済 API を呼ばない商品一覧（/products）の成功率まで 1.0% に落ちた
- 埋まり方は、リトルの法則 L = λW で前もって計算できる。同時に要るスレッドは λW = 60 件/秒 × 5.05 秒 ≈ 300 本で、上限の 40 本を大きく超える。埋まるまでの時間は「空いている本数 ÷ 到着率」≈ 0.6 秒で、実測と合った
- 守り方は、L = λW のどれを小さくするかで 3 つに分かれる。W を抑える（タイムアウト、決済 API をトランザクションの外で呼ぶ）、L を区切る（バルクヘッド）、λ を絞る（サーキットブレーカー）。リトライは逆に W と λ を増やす
- タイムアウトは「平常時の p99 ＋ 余裕」から「資源の上限 × 0.7 ÷ ピーク時の到着率」のあいだに置く。この窓がなければ、タイムアウトの値では守れない
- 全部を入れると、/orders だけが失敗し、/products は 100% のまま、再起動は 0 回、遅延を外して 9 秒で戻った

| | 防御なし（00） | すべての防御（04） |
| --- | --- | --- |
| 障害中の /products の成功率 | 1.0% | 100% |
| 使用中のスレッドの最大 | 40 / 40 本 | 14 / 40 本 |
| order-api の再起動 | 4 回 | 0 回 |
| 遅延を外してから戻るまで | 38 秒 | 9 秒 |

## 1. はじめに

### 1.1 決済 API が遅くなっただけで、1 秒ほどで商品一覧まで止まる

注文 API（order-api）は、注文（POST /orders）のたびに外部の決済 API を呼び、商品一覧（GET /products）では DB を読むだけです。この決済 API の応答に 5 秒の遅延を入れると、決済 API を呼ばない /products の成功率まで 1.0% に落ちました。order-api の CPU 使用率は 16% と、平常時より低いままでした。

よくある説明は「スレッドが枯渇したから」です。この記事では一歩進めて、何本のスレッドが、何秒で、なぜ尽きるのかを、リトルの法則 L = λW で障害の前に計算し、kind のクラスタで再現して確かめます。そのうえで、タイムアウト・バルクヘッド・サーキットブレーカー・リトライを 1 つずつ入れ、それぞれが L = λW のどこに効くのか（あるいは逆に働くのか）を測ります。

### 1.2 この記事のゴール

- 自分のサービスで、障害時にどの資源がいつ尽きるかを計算できる
- タイムアウト・バルクヘッド・サーキットブレーカー・リトライが L = λW のどこに効くかを説明でき、値を計算で決められる

### 1.3 この記事で扱わないこと

- WebFlux・コルーチン・仮想スレッド。スレッドは尽きにくくなりますが、L = λW の上限が、コネクションやメモリなど別の資源に移るだけです
- 待ち行列理論による遅延の予測。リトルの法則は平均どうしの関係で、負荷が増えたときに W がどう伸びるかまでは教えてくれません

## 2. リトルの法則

### 2.1 L = λW

$$
L = \lambda W
$$

- **L**：箱の中にいる数の平均（同時に処理中のリクエスト、使用中のスレッドなど）
- **λ**：箱に入る率（1 秒あたりの到着数）
- **W**：1 件が箱の中にいる時間の平均

ここで「箱」は、スレッドプールやコネクションプールのように、出入りを数えられる範囲のことです。1 秒に 60 件届き、1 件が 0.05 秒で返るなら、平均して常に 60 × 0.05 = 3 件を処理しています。到着の仕方や処理時間の分布によらず、平均どうしでこの関係が成り立つのが強みです。

### 2.2 3 つの向きで使う

3 つの値のうち 2 つが分かれば、残りが決まります。この記事では、次の 3 つの向きで使います。

| 知りたいもの | 式 | この記事での例 |
| --- | --- | --- |
| 同時に要る数 | L = λW | 障害中の /orders：60 件/秒 × 5.05 秒 ≈ 300 本 |
| さばける率の上限 | λ = L ÷ W | payment-api：6 本 ÷ 0.05 秒 = 120 件/秒 |
| 1 件の平均の時間 | W = L ÷ λ | 平常時の order-api の実測：3.1 本 ÷ 70 件/秒 ≈ 0.045 秒 |

### 2.3 実測で確かめる

order-api の使用中のスレッド（L）と、λ × W を同じグラフに描くと、2 本の線は重なります。次は 6 章の実験 01b のグラフです。

![01b の実測の L と λ×W](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/littles-law.png)
*緑が使用中のスレッド（実測の L）、黄が λ×W。赤い帯が障害の区間*

平常時は L が 3.4 本、λW が 3.2 本です。障害中（決済 API の呼び出しが毎回 0.3 秒でタイムアウトする状態）は、どちらも 18.1 本で、60 件/秒 × 0.3 秒 = 18 本と合います。状態が変わっても、2 本の線は重なったままです。

:::details λ×W をどう測っているか
Spring Boot（Micrometer）は、リクエストごとの処理時間を `http_server_requests_seconds` に記録し、合計（`_sum`）と件数（`_count`）を出します。合計の増え方 `rate(_sum)` は「1 秒に終わった件数 × その平均時間」なので、λ × W そのものです。

```promql
sum(rate(http_server_requests_seconds_sum{job="order-api", uri=~"/orders|/products"}[10s]))
```

L は Tomcat の使用中のスレッド（`tomcat_threads_busy_threads`）です。λ × W は終わったリクエストしか数えないので、終わらないリクエストが溜まると L から離れます（5.4）。
:::

### 2.4 この記事で使う前提

- **平均どうしの関係です。** p99 の W から p99 の L は出ません。この記事の λW も、平均の W を使った値です
- **L と W は同じ箱で測ります。** スレッドの L には、スレッドを握っている時間を W に使います。リクエストがスレッドの空きを待って列に並ぶ時間は、スレッドの W には入りません
- **流れが落ち着いた状態の関係です。** 立ち上がりの途中や、上限で頭打ちのあいだは、そのままでは成り立ちません（5.2、5.4）

## 3. 障害を L = λW で読む

### 3.1 障害は W の増加から始まる

下流が遅くなったとき、まず変わるのは W です。λ（届く数）は、クライアントが送り続ける限り変わりません。order-api の /orders は、決済 API の応答を待つあいだスレッドを握ります。決済 API の応答が 0.05 秒から 5.05 秒になれば、/orders がスレッドを握る W も約 100 倍になり、λ が同じなら λW も約 100 倍になります。

### 3.2 λW が上限を超えると、共有している資源を通じて広がる

order-api のスレッド 40 本は /orders・/products・/livez のすべてで、HikariCP のコネクション 10 本は /orders と /products で共有しています。この節では、Resilience4j などの防御をまだ何も入れていない状態（5 章の実験 0 と同じ設定）で考えます。

/orders は、決済 API の応答が返るまでスレッドを 1 本握ったままにします。上限がなければ、同時に握る本数は λW で決まります。/products は DB を読むだけで 1 ミリ秒足らずで返るので、スレッドはほとんど使いません。決済 API の応答が 5.05 秒になると、/orders の λW は 60 件/秒 × 5.05 秒 ≈ 300 本になり、上限の 40 本を大きく超えます（λW は流れが落ち着いたときの本数で、そこに至るまでの動きは 5.2 で追います）。

![障害の広がり方](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/failure-spread.ja.png)
*スレッドだけを描いた単純化。コネクションについては下の本文*

40 本がすべて埋まると、あとから来たリクエストは、どのエンドポイント宛てかに関係なく、Tomcat の中の 1 本の列に並んでスレッドの空きを待ちます。負荷をかける k6 は 5 秒でタイムアウトします（決済 API に入れた遅延の 5 秒とは別の設定です）。そのため、次のことが起きます。

- **/products**：決済 API を呼ばないのに、空きを待つうちに 5 秒を過ぎ、ほぼすべて失敗する
- **/orders**：スレッドを取れても 5 秒以内には返らず、失敗する。クライアントがあきらめたあとも処理は続き、スレッドは握られたまま
- **/livez**：応答できず、Kubernetes が Pod を再起動する（実験 0 では障害中に 3 回。5.4）

コネクションでも同じことが起きます。実験 0 では決済 API をトランザクションの中で呼ぶので、/orders はコネクションも 5.05 秒握ります。コネクションの λW も約 300 本です。上限は 10 本とスレッドより少ないので、スレッドより先に尽きます。コネクションが先に尽きたあとは、スレッドを取れた /products も、コネクションの空きを待ってスレッドを握ります。共有している 2 つの資源がどちらも上限を超えているので、片方だけを増やしても /products は助かりません。6 章では、スレッドとコネクションを握る時間を順に短くします。

遅くなったのは決済 API だけです。それでも、共有している資源を通じて、決済と関係のない API まで止まります。

### 3.3 守り方は 3 つ：W を抑える・L を区切る・λ を絞る

L = λW のどれかを小さくすれば、λW を上限の内側に収められます。W は 1 件が資源を握る・待つ時間です。L と λ は、ここでは決済 API の呼び出しの数で、L は同時に呼んでいる数、λ は 1 秒に呼ぶ数です。/orders 1 件が資源を握る時間の入れ子で見ると、防御が効く場所は次のとおりです（札は、それを入れるシナリオの名前）。

![防御が効く場所](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/defenses.ja.png)
*上の段は 00・01a、下の段は 01b 以降の形。棒の長さは比例していない*

- **W を抑える**：01a のタイムアウトは、決済 API の応答を待つ時間に上限を付けます（上の段）。それでも 00・01a はトランザクションの中で決済 API を呼ぶので、コネクションも同じ時間握り、60 件/秒 × 0.3 秒 = 18 本が上限の 10 本を超えます（6 章）。01b は決済 API をトランザクションの外で呼び、コネクションを握るのをあとの短い書き込みだけにして、取得待ちも打ち切ります（下の段）。スレッドを握る時間は、決済 API の待ちが大半なので、あまり変わりません
- **L を区切る**：02b のバルクヘッドは、決済 API を同時に呼ぶ数を区切ります。あふれた /orders はすぐ断られるので、決済 API を待ってスレッドを握るのは、区切った数までになります
- **λ を絞る**：03b のサーキットブレーカーは、失敗が続くと開き、しばらく決済 API を呼ばずにすぐ失敗を返します
- **リトライ（03a）は逆に働きます**：失敗を取り戻す代わりに、1 件の W と、呼び出しの数 λ を増やします（8 章）

タイムアウト・バルクヘッド・サーキットブレーカーで /orders が早く返れば、スレッドを握る時間も短くなります。リトライが一番外側にあるので、試行のたびにサーキットブレーカーとバルクヘッドを通り直し、それらに断られた呼び出しはリトライしません。実験 0 では、どの防御も入れていません。値は次の表のとおりです。

| 守り方 | 手段 | この実験での値 | 入れるシナリオ |
| --- | --- | --- | --- |
| W を抑える | 決済 API のタイムアウト | 30 秒 → 300ms（02a・02b は 800ms） | 01a 以降 |
| W を抑える | コネクションの取得待ちを打ち切る | 30 秒 → 250ms | 01b 以降 |
| W を抑える | 決済 API をトランザクションの外で呼ぶ | — | 01b 以降 |
| L を区切る | バルクヘッド | 同時に 12 まで。空いていなければ待たずに断る | 02b・04 |
| λ を絞る | サーキットブレーカー | 10 秒の窓で 20 回以上呼び、失敗率 50% 以上で開く。開いたまま 5 秒、半開で 10 回試す | 03b・04 |
| （W と λ が増える） | リトライ | 試行は最大 3 回（初回を含む）・500ms おき（04 は 2 回・100ms おき） | 03a・03b・04 |

## 4. 実験環境

### 4.1 全体の構成

![全体の構成](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/architecture.ja.png)

- Prometheus と Grafana は、kind のポートの割り当てで、手元のブラウザから localhost:9090・localhost:3000 で開けます
- 負荷も障害も、クラスタの外から scenarios/run.sh が入れます。シナリオの設定を当てると、設定が変わったアプリの Pod だけが入れ替わります（payment-api の設定が変わるのは 02a・02b の前後だけ）
- k6 は到着率を一定に保って送ります（オープンモデル）。応答が遅れても送る数を減らさないので、障害のときに要求が積み上がる様子をそのまま再現できます。k6 は応答を待つ 1 件に 1 VU を使うので、到着率 × k6 のタイムアウト 5 秒（/orders なら 300）に余裕を足した数の VU を、最初から用意しておきます（これもリトルの法則です。途中で作り足すと、作り足すあいだの到着を捨ててしまいます）
- payment-api は、平均 0.05 秒・p99 0.12 秒の対数正規分布で応答を返すモックです。6 本のスレッドなので、平均 0.05 秒なら 1 秒に約 120 件までさばけます。リトライで呼び出しが増える 03a で、この上限が効いてきます
- order-api のメトリクスは、業務の 40 本とは別のスレッドで 8081 番から返します。40 本が埋まると readiness にも落ち、業務用の Service からは外れます（新しい接続は断られる）。メトリクス用の Service は、readiness に落ちた Pod も返す設定（publishNotReadyAddresses）にしてあるので、そのあいだも Prometheus は取りに行けます
- 手元の kind クラスタで動くよう、到着率やプールの大きさを、よくある本番の規模（Tomcat の既定のスレッド 200 本など）の約 1/5 に縮めています。比率が同じなら、尽きるまでの秒数は変わりません（付録 B）

### 4.2 1 回の実験の流れ

![1 回の実験の流れ](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/scenario-timeline.ja.png)

0 秒の前に、設定の適用と Pod の入れ替え、k6 の起動を待つ時間があり（1 分ほど）、全体では約 7 分かかります。ウォームアップは、JIT のコンパイルや接続プールが落ち着くまで待つ区間で、何も測りません。平常時の区間では、測った L と λW が一致すること（2.3）と、平常時の成功率を確かめます。

### 4.3 被害スコア

図の下の括弧が、どの値をどの区間で測るかです。

- **成功率・使用中のスレッド・取得待ち**：障害中の 120 秒で集計する。成功率はエンドポイントごとに区間全体の割合、使用中のスレッドは平均と最大、コネクションの取得待ちの本数は最大
- **スレッドが尽きるまで**：障害から 15 秒のあいだの生の計測で、初めて 40 本になった時刻。計測は 1 秒ごとなので、実際にはこれより早く尽きていることがある。15 秒のうちに 40 本にならなければ「尽きない」
- **回復までの時間**：遅延を外してから、両方のエンドポイントの成功率（直近 6 秒）が 99% 以上になり、そのまま 15 秒続いた区間の始まりまで。120 秒のうちにそうならなければ「戻らない」
- **再起動の回数**：負荷をかけている間の全体で数える。遅延を外したあとに再起動することもある

## 5. 実験0：防御なしで壊す

### 5.1 設定

- Tomcat のスレッドは 40 本、HikariCP のコネクションは 10 本
- 決済 API のタイムアウトは 30 秒
- 決済 API をトランザクションの中で呼ぶ（注文を仮登録 → 決済 API で与信 → 確定、を 1 つのトランザクションで行う、よくある書き方）
- HikariCP の取得待ちの上限は、既定の 30 秒

```kotlin:OrderService.kt（実験 0・01a）
tx.execute {
    val orderId = insertOrder(productId, quantity, "PENDING")
    paymentClient.authorize() // 決済 API を待つあいだも、コネクションを握ったまま
    jdbc.sql("update orders set status = 'CONFIRMED' where id = ?").param(orderId).update()
    orderId
}
```

### 5.2 予測：何秒で、どこまで壊れるか

3.2 の 300 本は、上限がなかった場合に、流れが落ち着いたあとの値です。障害の直後にスレッドがどう埋まるかは、1 件ずつの動きを追うと分かります。到着を等間隔にし、スレッドだけを数えて計算したのが次の図です。

図の 1 行が 1 本のスレッドです。縦に切ったときに交わる棒の数が、その瞬間に使っているスレッドの数 L になります。障害の前は、0.05 秒の短い棒が上の 3 行を入れ替わりで使っています（/products は 1 ミリ秒足らずで返るので、棒は描いていません）。

![障害の直後にスレッドが埋まっていく様子（計算）](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/thread-timeline.ja.png)
*計算（実測ではない）*

- **埋まるまでの時間は、空いている本数と到着率で決まる。** 障害の時点で処理中だった 3 件も応答が遅れるので、空いているのは 37 本です。終わる棒がないまま 1 秒に 60 本ずつ増えるので、約 0.6 秒で埋まります。棒が十分に長ければ、5 秒でも 30 秒でも同じです（どこまで短くすれば埋まらないかは、6.1 で求めます）
- **上限がなくても、300 本にはすぐにはならない。** 1.0 秒の時点では 63 本です。300 本で落ち着くのは、最初の棒が終わり始め、増える棒と終わる棒が釣り合う 5 秒後からです

**L = λW の λ は、その資源に実際に入る率です。** 2 章では λ を到着率と呼びましたが、上限で頭打ちのあいだ、スレッドに入れる率は到着率よりずっと小さくなります。0.6〜5 秒は 1 件も入れません。5 秒後からは、終わった棒の数だけ入れ替わりに入るので、平均で 40 ÷ 5.05 ≈ 8 件/秒です。落ち着けば、40 本 ≈ 8 件/秒 × 5.05 秒で L = λW が成り立ちます（スレッドだけを数えた値。実験 0 ではコネクション 10 本が先に詰まるので、約 2 件/秒。5.4）。入れなかった残りは列に並び、伸び続けます（図の上の「空きを待つ列」）。上限がなければ入る率は到着率と同じなので、3.2 の 60 件/秒 × 5.05 秒 ≈ 300 本になります。

予測は「障害から約 0.6 秒で 40 本が埋まり、/products は列に並んで 5 秒でタイムアウトする」です。

:::details 実験 0 では、コネクションの分だけ少し早い（約 0.55 秒）
実験 0 では決済 API をトランザクションの中で呼ぶので、コネクション 10 本が先に (10 − 3) ÷ 60 ≈ 0.12 秒で尽きます。このとき使っているスレッドは、コネクションを握った /orders の 10 本です。そのあとは /products もコネクションの空きを待つあいだ（HikariCP の取得待ちの上限は 30 秒）スレッドを握るので、残りの 30 本は 1 秒に 70 本ずつ埋まり、0.12 + 30 ÷ 70 ≈ 0.55 秒で満杯になります。障害中に処理を終えられるのも、コネクションを 5.05 秒ずつ握る /orders が 1 秒に約 2 件（10 ÷ 5.05）だけです（5.4）。
:::

### 5.3 実測：5 秒を待たずに、1 秒ほどで 40 本が埋まる

計測は 1 秒ごとです（業務とは別のポートで受けているので、40 本が埋まっても測れます）。予測の約 0.6 秒は計測の間隔より短いので、障害の直後の 1〜2 点で確かめます。同じ設定で 3 回回しました（障害の時刻は、遅延を入れる API を呼ぶ直前と応答を受けた直後に、ミリ秒まで記録しています）。

![障害の前後 15 秒のスレッド（1 回目の実行）](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/threads-fault.png)
*1 回目の実行。赤い帯（と下端の赤い線）が障害の区間*

1 回目の実行では、障害の 0.34 秒後の最初の計測で 27 本、次の 1.34 秒後の計測で 40 本すべてが埋まっていました。3 回目は 0.47 秒後に 35 本、2 回目は 0.92 秒後の最初の計測で、もう 40 本でした。コネクションの分を入れた計算（5.2 の折りたたみ）では、0.34 秒で 26 本、0.47 秒で 34 本、0.55 秒で満杯です。途中を測れた 2 回は、どちらも計算より 1 本多いだけでした（障害の時点で処理中だった本数は、障害の前の 1 分間で 1〜5 本とぶれるので、その範囲です）。スレッドだけを数えた図より 3〜4 本多いのは、コネクションが先に尽き、/products もスレッドを握るからです。決済 API の遅れの 5 秒を待たずに、計算の線に沿って埋まっています。3 回の実行の生の値は [runs.md](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/00-no-defense/results/runs.md) にあります。

![障害の前後 15 秒の HikariCP（1 回目の実行）](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/hikari-fault.png)
*1 回目の実行。実線が使用中、点線が取得待ち、薄い破線が上限*

図の 15 秒のあいだは、どの計測でもコネクションは 10 本とも使われていて、握っている 10 本と待っている本数を足すと、スレッドの本数に一致しました（0.34 秒は 10 + 17 = 27、1.34 秒からは 10 + 30 = 40）。0.34 秒の時点で、コネクションはもう尽きていたことになります（計算では 0.12 秒）。取得待ちが 30 で止まっているのは、スレッドが 40 本で頭打ちだからです（コネクションを待てるのは、スレッドを持っているリクエストだけ）。障害の前も約 3 本使っているのは、決済 API をトランザクションの中で呼んでいるからで、60 件/秒 × 0.05 秒と合います。

### 5.4 決済 API を呼ばない /products まで止まる

![実験 0 の成功率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/success.png)
*紫が /orders、青緑が /products（ほぼ重なっている）。灰色の縦の帯は order-api の再起動*

障害中の 120 秒の成功率は、/orders が 0.3%、決済 API を呼ばない /products も 1.0% でした。/products の失敗のうち 91% が k6 の 5 秒のタイムアウトで、スレッドの空きを待つ列で 5 秒を過ぎています（3.2 のとおり）。

![実験 0 のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/threads.png)
*40 本の横ばい → 階段状に下がる → 再起動、を繰り返す*

order-api は障害中に 3 回、遅延を外したあとにもう 1 回再起動しました。1 回分の流れは次のとおりです。

1. 40 本が埋まると、/livez も列に並んで応答できません。liveness probe（5 秒ごと、1 秒でタイムアウト、3 回続けて失敗したら再起動）が失敗し続け、Kubernetes がコンテナを止めにかかります
2. 止めるとき、Spring Boot は新しいリクエストを受け付けず、処理中のものが終わるのを待ちます（graceful shutdown）。障害の約 15 秒後から、スレッドは約 5 秒ごとに 40 → 29 → 17 → 6 本と、11 本ほどずつ減りました。コネクション 10 本を 5.05 秒ずつ握る /orders が、10 件ずつ終わるからです。5.2 の折りたたみの「1 秒に約 2 件」が、ここで見えています
3. 新しいコンテナが起動すると、待っていた到着がすぐに入り、1 秒足らずでまた 40 本が埋まります

障害中の再起動は、何も解決しません。起動したとたんに、同じ λW が同じ上限に当たるからです。

:::details 実測の L と λ×W が離れる
障害中の L は平均 28.3 本、λ × W は 19.8 本と、2.3 では重なっていた 2 本の線が離れました。λ × W は終わったリクエストしか数えないので、終わる前に再起動で失われたリクエストが入らないからです。L = λW は、入ったものがいずれ出ていく、流れが落ち着いた状態の関係です。入ったまま終わらないリクエストがあるあいだは、そのままでは成り立ちません。

なお、被害スコアの取得待ちの最大は 37 で、5.3 の「30 で止まる」より多くなっています。これは再起動の直後、プールのコネクションがまだ 2 本しかないときの値です（2 + 37 で、ほぼ 40 本）。
:::

### 5.5 CPU は低いまま

![実験 0 の CPU 使用率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/cpu.png)
*突き出ているのは、再起動したあとの JVM の起動*

障害中の CPU 使用率の平均は 16% で、平常時（20%）より低くなりました。スレッドは決済 API とコネクションを待っているだけで、計算はしていないからです。CPU を見ていても、この障害の始まりには気づけません（10.6）。

:::message
VU（仮想ユーザー）の数を固定する負荷試験（クローズドモデル）では、この壊れ方は再現しません。VU は応答を待つあいだ次のリクエストを送らないので、応答が遅くなると到着率が勝手に下がるからです。障害を再現するには、応答に関係なく一定の率で送る（オープンモデル。k6 なら constant-arrival-rate）必要があります。
:::

### 5.6 学び

- 下流の W が伸びて λW が上限を超えると、共有している資源を通じて、関係のない API まで止まる
- 埋まるまでの時間は「空いている本数 ÷ 到着率」で、W が十分に長ければ W によらない。この実験では約 0.55 秒の計算に対して、実測は 1 本の差で合った
- 障害中の再起動は役に立たない。CPU は低いままなので、見るべきはスレッドとコネクションの「使用中 ÷ 上限」

## 6. 実験1：W を抑える

### 6.1 タイムアウトの窓を計算する

W を抑える一番の手段は、決済 API のタイムアウトです。短すぎれば平常時にも失敗し、長すぎれば障害時に資源が尽きます。そこで、置ける範囲（窓）を先に計算します。

![タイムアウトの窓](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/timeout-window.ja.png)
*上の段が 01a・01b の決済 API とスレッド。下の 2 段は 6.3 と 7.1 で使う*

#### 下限：平常時の p99 に余裕を足す

決済 API の平常時の p99 は 120ms です。タイムアウトをこれより短くすると、平常時にも 1% 以上の呼び出しがタイムアウトします。ばらつきの余裕を足して、下限は約 200ms にします。

#### 上限：資源の上限 × 0.7 ÷ ピーク時の到着率

決済 API が返らなくなると、/orders 1 件はタイムアウトまでスレッドを握るので、W はタイムアウトの値そのものになります。λW がスレッドの上限に収まるには「タイムアウト ≤ スレッド数 ÷ ピーク時の到着率」が条件で、40 ÷ 60 ≈ 0.67 秒です。5.2 で見たとおり、W がこれより長いと、W がいくつでも同じ速さで埋まります。/products や /livez の分と到着のばらつきの分として 3 割を残すと、40 × 0.7 ÷ 60 ≈ 0.47 秒（467ms）が上限です。

この 200〜467ms の窓の中から、300ms を選びます。

### 6.2 タイムアウトを 300ms にする（01a）

#### 予測

スレッドだけを見れば、λW は 60 件/秒 × 0.3 秒 = 18 本で、40 本に収まります。ところが 01a は、決済 API をトランザクションの中で呼んだままです。コネクションも 0.3 秒握るので、コネクションの λW も 18 本になり、上限の 10 本を超えます（6.1 の図の 2 段目）。

コネクション 10 本でさばけるのは 10 ÷ 0.3 ≈ 33 件/秒です。残りの /orders と /products は、スレッドを握ったままコネクションを待ちます。待つ上限は HikariCP の既定の 30 秒で、これがスレッドにとっての新しい W になります。計算すると、障害から約 0.85 秒でスレッドも 40 本が埋まります。

:::details 約 0.85 秒の計算
- 0〜0.12 秒：コネクションが (10 − 3) ÷ 60 ≈ 0.12 秒で尽きる。スレッドは約 10 本
- 0.12〜0.3 秒：最初のタイムアウト（0.3 秒）まで、終わるリクエストはない。/orders と /products の 1 秒 70 件がそのままスレッドを握り、0.3 秒で約 23 本
- 0.3 秒〜：コネクションを握った /orders が 1 秒に約 33 件終わり、列の中で /orders に挟まれた /products も 1 秒に約 5.5 件（33 × 10/60）流れる。スレッドは 1 秒に 70 − 33 − 5.5 ≈ 31 本ずつ増え、残り 17 本が約 0.55 秒で埋まる
:::

#### 実測：予告どおりコネクションで尽き、1 秒足らずでスレッドも埋まる

![01a の HikariCP](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01a-timeout/results/panels/hikari.png)
*実線が使用中、点線が取得待ち、薄い破線が上限*

コネクションは障害の直後から 10 本とも使われ、取得待ちが 30 前後まで積み上がりました（最大 31）。スレッドは、障害の 0.86 秒後の最初の計測で 39 本、1.86 秒後に 40 本でした（計算は約 0.85 秒で満杯）。障害中の /products の成功率は 12.3%、再起動は 5 回で、タイムアウトを入れても /products は守れていません。

### 6.3 もう 1 つの W：コネクションの取得待ち

01a で先に尽きたのはコネクションでした。決済 API をトランザクションの中で呼ぶと、コネクションを握る時間に決済 API の待ちが入ります。そして、コネクションを待つ時間にも上限（HikariCP の connection-timeout、既定 30 秒）があり、それがスレッドにとっての新しい W になりました。

タイムアウトは 1 か所ではありません。スレッドを握ったまま待つ場所（HTTP の応答、コネクションの取得、リトライの待ち）ごとに、W の上限を確かめる必要があります。

6.1 の図の 2 段目のとおり、トランザクションの中で呼ぶ限り、コネクションには窓がありません（上限 10 × 0.7 ÷ 60 ≈ 117ms は、下限の 200ms より短い）。そこで、タイムアウトの値ではなく、コネクションを握る範囲を変えます。

### 6.4 決済 API をトランザクションの外で呼ぶ（01b）

決済 API を先に呼び、コネクションを握るのは DB に書き込む一瞬だけにします。あわせて、HikariCP の取得待ちを 250ms（設定できる最小値）に縮めます。

```kotlin:OrderService.kt（01b 以降）
paymentClient.authorize() // 決済 API はトランザクションの外で、先に呼ぶ
tx.execute { insertOrder(productId, quantity, "CONFIRMED") }
```

:::message
本番では、与信が通ったあとに書き込みが失敗したときの取り消しなど、整合性の扱い（補償の処理や冪等キー）が別に必要です。この記事では、資源を握る時間の違いだけを見ます。
:::

#### 予測

コネクションを握るのは書き込みの数ミリ秒だけになり、コネクションの λW は 1 本未満です。スレッドの λW は 60 × 0.3 = 18 本で、上限の 40 本に収まります。/orders は 0.3 秒でタイムアウトして失敗を返し、/products は影響を受けないはずです。

#### 実測：スレッドは 18 本で横ばい、/products は 100%

![01b のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/threads.png)
*障害中も 18 本前後で横ばい（上限は 40 本）*

![01b の成功率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/success.png)
*/orders（紫）は失敗するが、/products（青緑）は 100% のまま*

障害中のスレッドは平均 18.1 本（最大 22 本）で、計算の 18 本どおりでした。/products の成功率は 100%、再起動は 0 回で、遅延を外してから 7 秒で戻りました。/orders は失敗しますが（成功率 0.5%）、失敗が 0.3 秒で返るので、資源を巻き込みません。

### 6.5 学び

- タイムアウトは「平常時の p99 ＋ 余裕」と「資源の上限 × 0.7 ÷ ピーク時の到着率」のあいだに置く
- スレッドを握ったまま待つ場所は 1 つではない。HTTP の応答、コネクションの取得、リトライの待ちのすべてに上限を付け、資源ごとに λW を計算する
- 窓がない資源は、値ではなく構造を変える（決済 API をトランザクションの外で呼ぶ）

## 7. 実験2：L を区切る

### 7.1 窓が存在しない下流（02a）

01b がうまくいったのは、決済 API の p99（120ms）が、スレッドから見た上限（467ms）より十分に短かったからです。p99 が長い下流では、そもそも窓がありません。

02a では、payment-api を平均 100ms・p99 600ms に遅くし（スレッドは 12 本に増やして、さばける率は 120 件/秒のまま）、タイムアウトを p99 に余裕を足した 800ms にします。決済 API はトランザクションの外で呼びます（01b と同じ）。

#### 予測

6.1 の図の 3 段目のとおり、下限の約 800ms が上限の 467ms を超えていて、窓がありません。障害中の λW は 60 × 0.8 = 48 本で 40 本を超えます。平常時の L は約 6.6 本なので、空いている約 33 本が 1 秒に 60 本ずつ埋まり、約 0.55 秒でスレッドが尽きます。平常時でも、800ms を超える遅い応答はタイムアウトします。

#### 実測：1 秒ほどで尽き、/products は 25%

![02a のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/02a-no-window/results/panels/threads.png)
*障害の直後に 40 本が埋まり、再起動を繰り返す*

障害の 0.48 秒後の最初の計測で 33 本（計算は 35 本）、1.48 秒後に 40 本でした。障害中の /products の成功率は 25.3%、再起動は 5 回です。平常時の /orders の成功率は 99.4% で、約 0.6% がタイムアウトしていました。タイムアウトを p99 の外側に置いた代償です。

### 7.2 バルクヘッドで同時実行数に上限を付ける（02b）

窓がないなら、W ではなく L を直接区切ります。Resilience4j の Bulkhead で、決済 API を同時に呼ぶ数を 12 までにし、空いていなければ待たずに断ります。

```yaml:application.yml
resilience4j:
  bulkhead:
    instances:
      payment:
        max-concurrent-calls: 12
        max-wait-duration: 0ms # 枠が空いていなければ待たずに断る
```

#### 予測

決済 API を待ってスレッドを握る /orders は、最大 12 本です。そこを通れる率は λ = L ÷ W = 12 ÷ 0.8 = 15 件/秒で、残りの約 45 件/秒はすぐに断られます。スレッドは 12 本と少しで、40 本に収まります。

#### 実測：決済 API に届いたのは 14.9 件/秒、スレッドは最大 13 本、/products は 100%

![02b のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/02b-bulkhead/results/panels/threads.png)
*障害中も 12 本前後で横ばい*

![02b の決済 API の呼び出し](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/02b-bulkhead/results/panels/payment-calls.png)
*緑が成功、黄が失敗（0.8 秒のタイムアウト）。バルクヘッドに断られた分は、決済 API まで届かないので数に入らない*

障害中に決済 API まで届いた呼び出しは 14.9 件/秒で、計算の 15 件/秒どおりでした。/products の成功率は 100%、再起動は 0 回で、遅延を外してから 9 秒で戻りました。

### 7.3 枠の大きさとばらつき

枠の 12 は、平常時の L（60 件/秒 × 0.1 秒 = 6）の 2 倍です。小さくすれば平常時にも断る呼び出しが増え、大きくすれば障害時に握るスレッドが増えます。

この環境で平常時に断った呼び出しは、1 分に 1 件ほど（約 3,600 件中）でした。ただしこれは、k6 がリクエストを等間隔に送っているからです。到着がランダム（ポアソン到着）なら、平常時でも約 1% を断る計算になります（アーランの B 式、同時に 12 まで・平均 6）。枠は、平常時の L とそのばらつきから決めます（付録 B）。

### 7.4 学び

- 下流の p99 が長くて窓がないなら、タイムアウトではなく同時実行数で区切る
- 通過量は λ = L ÷ W で決まる（12 ÷ 0.8 = 15 件/秒）。枠の外は待たせずにすぐ断る。待たせると、断るまでの時間が新しい W になる
- 枠は、平常時の L とばらつきから決める

## 8. 実験3：λ を絞る

### 8.1 リトライで、安全だったはずの 300ms が崩れる（03a）

01b（タイムアウト 300ms、決済 API はトランザクションの外）に、Resilience4j の Retry を足します。最大 3 回試行し、試行の間に 500ms 待ちます（どちらも Retry の既定値）。

#### 予測

1 件の W は、最大 3 × 0.3 + 2 × 0.5 = 1.9 秒です。試行の間の待ちも、スレッドを握ったままです。λW は 60 × 1.9 = 114 本で 40 本を超え、(40 − 3) ÷ 60 ≈ 0.6 秒でスレッドが尽きます。01b では安全だった 300ms が、リトライによって安全でなくなります。決済 API への呼び出しも、最大 3 倍に増えます。

#### 実測：1 秒ほどで尽き、/products は 8%

![03a のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03a-retry/results/panels/threads.png)
*障害の直後に 40 本が埋まり、再起動を繰り返す*

障害の 0.55 秒後の最初の計測で 37 本（計算は 36 本）、1.55 秒後に 40 本でした。同じ設定で 8 回回し、障害中の /products の成功率は 7〜8%、再起動はどの回も 5 回でした。

### 8.2 原因を取り除いても戻らない

#### ときどき、遅延を外して 2 分たっても戻らない

今の設定での 8 回は、どれも遅延を外してから 12〜46 秒で戻りました。一方、k6 が VU を途中で作り足していたころ（4.1）の 4 回では、2 回が 2 分たっても戻りませんでした。そのうち 1 回は、直前の実行の再起動の待ち（後述の CrashLoopBackOff）を引き継いでいたので、新しい Pod で始めた 11 回に限ると、戻らなかったのは 1 回です。

![戻らなかった回の成功率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03a-retry/results/panels/success-not-recovered.png)
*戻らなかった回。遅延を外したあと（赤い帯の右）、一度は 100% まで戻ってから、また 0% に落ちる*

#### 何が起きていたか

どの実行でも、遅延を外したあとに order-api が起動すると、リトライで決済 API への呼び出しが 112〜123 件/秒まで膨らみ、payment-api のスレッドが上限の 6 本に 8〜22 秒張り付きました。

![03a の payment-api のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03a-retry/results/panels/payment-api-threads.png)
*戻った回の payment-api。緑が使用中、黄が上限の 6 本。遅延を外したあとも、しばらく上限に届く*

戻らなかった回では、order-api から見て、多いときで毎秒約 38 件の呼び出しがタイムアウトし、約 30 件がリトライのすえ成功していました。その間に order-api のスレッドがまた埋まり、liveness probe が失敗して再起動します。再起動のたびに同じことが起き、Kubernetes は再起動の間隔を延ばしていきます（CrashLoopBackOff）。戻るかどうかは、遅延を外した直後のこの数十秒に、liveness probe が失敗するかどうかで分かれていました。

#### リトルの法則で読むと

payment-api がさばける率は λ = L ÷ W = 6 本 ÷ 0.05 秒 = 120 件/秒です。リトライで呼び出しがこの近くまで増えると、payment-api の中で列ができ、応答が 300ms を超えます。するとまたタイムアウトしてリトライになり、呼び出しが減りません。きっかけ（遅延）を取り除いても、リトライが作った負荷で、遅い状態が自分を保ってしまいます。このように、きっかけが去っても続く障害は、metastable failure と呼ばれています。

### 8.3 サーキットブレーカーで流入を止める（03b）

03a に Resilience4j の CircuitBreaker を足します。10 秒の窓で 20 回以上呼び、失敗率が 50% 以上なら開きます。開いている 5 秒は決済 API を呼ばずにすぐ失敗を返し、そのあと半開で 10 回だけ試します。ブレーカーに断られた呼び出しは、リトライしません。

#### 予測

開いているあいだ、決済 API への λ はほぼ 0 になり、/orders はすぐ失敗を返すので、W もほぼ 0 になります。ただし、開くには失敗が 20 件たまる必要があります。最初の失敗が返るのはタイムアウトの 0.3 秒後なので、開くのは障害から約 0.65 秒後（0.3 ＋ 20 ÷ 60）です。

#### 実測：決済 API への呼び出しが 60 件/秒から 4 件/秒に

![03b の決済 API の呼び出し](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03b-circuit-breaker/results/panels/payment-calls.png)
*緑が成功、黄が失敗。開いたあとは、5 秒ごとの半開の試しだけが届く*

障害中に決済 API が受けた呼び出しは平均 4.2 件/秒で、01b の 60 件/秒から大きく減りました。/products の成功率は 100%、再起動は 0 回で、遅延を外してから 11 秒で戻りました。

### 8.4 ブレーカーが開くまでの穴

![03b のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03b-circuit-breaker/results/panels/threads.png)
*障害の直後に一度だけ 40 本に届く。そのあとの細い山は、5 秒ごとの半開の試し*

開くまでの約 0.65 秒に届いた /orders は、1 回目の失敗のあとリトライの待ち（500ms）に入り、スレッドを握ったままです。約 40 件がそれぞれ 0.8 秒ほどスレッドを握るので、障害の 0.91 秒後の計測で、スレッドが一度 40 本に届きました。数秒で空いたので、その間に届いた /products も k6 の 5 秒には掛からず、成功率は 100% のままでした。そのあと 5 秒ごとに立ち上がる 10 本ほどの山は、半開で試した 10 件が、タイムアウトとリトライの待ちでスレッドを握る分です。

穴で握られる本数は「開くまでの時間 × 到着率」なので、到着率が高いほど穴は深くなります。この穴を、9 章でバルクヘッドと組み合わせて埋めます。

### 8.5 学び

- リトライは、W（試行の間の待ちを含む）と λ（呼び出しの数）の両方を増やす。入れたら、W の上限を「試行回数 × タイムアウト ＋ 待ちの合計」で計算し直す
- 下流がさばける率（λ = L ÷ W）の近くまでリトライで呼ぶと、きっかけが去っても戻らないことがある
- サーキットブレーカーは λ を絞るが、開くまでに穴がある

## 10. 自分のサービスを L = λW で点検する

### 10.1 資源を洗い出す

リクエストが握ったまま待つ資源と、その上限、共有している API を書き出します。

- リクエストを処理するスレッド（Tomcat なら `server.tomcat.threads.max`、既定 200）
- DB のコネクション（HikariCP なら `maximum-pool-size`、既定 10）
- HTTP クライアントの接続プール、非同期処理のスレッドプール、バルクヘッドのような同時実行の枠

### 10.2 障害時の W の最大値を確かめる

下流が返らなくなったとき、1 件がその資源を握る最長の時間を、設定から足し算します。

- HTTP の応答のタイムアウト × 試行回数 ＋ リトライの待ちの合計
- コネクションの取得待ちの上限（HikariCP の既定は 30 秒）
- トランザクションの中で外部を呼んでいれば、その時間がコネクションの W に入る

HTTP クライアントには、応答のタイムアウトの既定が無制限のものも多いので、明示的に設定されているかも確かめます。

### 10.3 λ × W と上限を比べる

資源ごとに「ピーク時の到着率 × W の最大値 ≤ 上限 × 0.7」かを確かめます。超えていれば、その資源は下流の障害で尽きます。尽きるまでの時間は、5.2 のとおり「空いている数 ÷ 到着率」で、多くの場合 1 秒もかかりません。

### 10.4 3 つの守り方を当てはめる

- 窓があるなら、W を抑える（タイムアウトを窓の中に置く）
- 外部の待ちが、コネクションのような小さい資源を巻き込んでいるなら、握る範囲を変える
- 窓がないなら、L を区切る（バルクヘッド。枠の外はすぐ断る）
- 下流を守り、早く失敗させたいなら、λ を絞る（サーキットブレーカー。開くまでの穴はバルクヘッドで埋める）
- リトライは W と λ を増やす。入れるなら回数と待ちを控えめにし、W の最大値を計算し直す

### 10.5 ヘルスチェックを業務と同じスレッドプールで受けていないか

この実験の order-api は、/livez と /readyz を業務と同じ 8080 番（同じ 40 本）で受けています（Spring Boot の `management.endpoint.health.probes.add-additional-paths` を使う、よくある構成です）。そのため、スレッドが尽きた 00・01a・02a・03a では、liveness probe が失敗して再起動を繰り返し、遅延を外してから戻るまで 37〜43 秒（03a は 12〜46 秒で、ときどき戻らない）かかりました。スレッドが尽きなかった 01b・02b・04 は、7〜9 秒で戻っています。

下流を待ってスレッドが埋まった状態は、再起動では直りません。liveness probe は「プロセスが壊れていて、再起動で直る」ときだけ失敗させるのが原則です。一方で、業務と別のスレッドで受ければ、本当にリクエストを受けられなくなったときにも成功してしまいます。readiness と liveness の役割を分け、liveness の失敗までの時間（この実験では 5 秒 × 3 回）を、下流の障害が数十秒続いても再起動しない長さにするなど、何を検知したいかから決めます。

### 10.6 「L ÷ 上限」を監視する

使用中 ÷ 上限を、資源ごとに監視します。

```promql
max(tomcat_threads_busy_threads) / max(tomcat_threads_config_max_threads)
max(hikaricp_connections_active) / max(hikaricp_connections_max)
max(hikaricp_connections_pending)
```

実験 0 では、障害から 1 秒足らずでスレッドが上限に届いた一方、CPU は 16% と平常時より低いままでした（5.5）。メトリクスは、業務とは別のポートで出しておきます（Spring Boot なら `management.server.port`）。業務のスレッドが尽きても測れます。

### 10.7 遅延を注入して確かめる

計算は、前提が合っていて初めて当たります。下流に遅延を入れ、オープンモデルの負荷をかけて、埋まるまでの時間と被害を測ります。この実験では、Toxiproxy の管理 API で遅延を入れています。

```bash
curl -X POST localhost:8474/proxies/payment-api/toxics \
  -H 'Content-Type: application/json' \
  -d '{"name":"latency","type":"latency","stream":"downstream","attributes":{"latency":5000}}'
```

## 11. まとめ

- 下流が遅くなると W が伸び、λW が上限を超えたところで、共有している資源を通じて関係のない API まで止まる。埋まるまでの時間は「空いている本数 ÷ 到着率」で、計算どおり 1 秒ほどだった
- 守り方は、W・L・λ のどれを小さくするかで決まる。タイムアウトの窓、コネクションを握る範囲、同時実行の枠、流入を、それぞれ計算で決められる
- リトライは逆向きに働く。下流がさばける率の近くまで呼ぶと、きっかけが去っても戻らないことがある
- CPU ではなく「使用中 ÷ 上限」を見る

## 付録

### A. 他にもこんな場面で使える

- **負荷試験の VU の数**：到着率 × タイムアウト（4.1。/orders なら 60 × 5 = 300 VU）
- **コネクションプールの大きさ**：ピーク時の到着率 × 1 件がコネクションを握る平均時間に、ばらつきの余裕を足す
- **非同期のワーカーやコンシューマーの並列数**：処理したい率 × 1 件の処理時間
- **同時実行の枠から通せる率**：枠 ÷ W（7.2。12 ÷ 0.8 = 15 件/秒）

### B. この実験環境の限界

- k6 の constant-arrival-rate はリクエストを等間隔に送るので、本番のトラフィックより、ばらつき（バースト）を小さく見積もります。7.3 で、平常時にバルクヘッドが断った数がほぼ 0 だったのはこのためです
- コンテナ用に約 4GB で動く大きさにするため、到着率やプールの大きさを約 1/5 に縮めています。比率が同じなら、尽きるまでの秒数やタイムアウトの窓は変わりません
- メトリクスは 1 秒ごとの計測なので、「何秒で尽きたか」には 1 秒の幅があります
- HikariCP はプールの統計を 1 秒キャッシュするので、1 秒ごとの計測では、使用中・取得待ちが 1 つ前の計測の値のままのことがあります（スレッドの本数と同じ瞬間の値とは限りません）
- 壊れるシナリオの回復時間は、遅延を外したときに order-api が再起動の途中かどうかで、実行ごとにばらつきます
