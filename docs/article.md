## TL;DR

- スレッドやコネクションを握ったまま（使ったまま返さずに）下流の応答を待つ処理は、下流が遅くなると、1 件がそれを握る時間 W が伸びる。同時に要る数 λW がプールの大きさ（スレッド数やコネクション数）を超えると、そのプールを共有するすべての処理が、空きを待つ待ち行列に並ぶ。止まるのは、遅い下流を呼ぶ処理だけではない
- 尽きるまでの時間は「空いている数 ÷ 到着率」で、遅延の長さによらない。数秒の遅延でも数十秒の遅延でも、同じ速さで尽きる。そのあいだ CPU はむしろ下がるので、見るべきは「使用中 ÷ 上限」
- 守り方は、L = λW のどれを小さくするかで 3 つに分かれる。W を抑える（タイムアウト。トランザクションの外で下流を呼び、コネクションを握らない）、L を区切る（下流を同時に呼ぶ数に上限を付ける。バルクヘッド）、λ を絞る（失敗が続いたら呼ぶのをやめる。サーキットブレーカー）
- タイムアウトには下限と上限がある。下限は「下流の平常時の p99 ＋ 余裕」、上限は「プールの大きさ ÷ ピーク時の到着率」から余裕を引いた値。下限が上限を超えると両方を満たす値がなく、タイムアウトでは守れない。そのときは、下流を待つあいだ握るものを減らすか、同時に呼ぶ数に上限を付ける
- スレッドを握ったまま待つ場所は 1 つではない。下流の応答、コネクションの取得、リトライの待ちのそれぞれで W の上限を確かめ、λW をプールごとに計算する。小さいプールから先に尽きる
- リトライは W と λ を両方増やす。試行回数が下流の処理能力の余裕（さばける率 ÷ 平常時の率）を超えると、きっかけが去っても下流の遅い状態が続く。そのあいだに liveness probe の猶予を使い切ると、再起動を繰り返して戻らなくなる
- 直近の一定時間で失敗率を数えるサーキットブレーカーは、およそ「集計する期間 × しきい値」がたつまで開かない。開くまでのあいだは、同時に呼ぶ数の上限（バルクヘッド）で守る

kind で動かした Spring Boot のサービスで、これらを予測してから壊して確かめました。予測した本数・件/秒・秒数は、実測と合いました（同時に要る数 18 本に対して実測 18.1 本、バルクヘッドを通れる率 15 件/秒に対して 14.9 件/秒など）。

## 1. はじめに

### 1.1 下流が 1 つ遅くなっただけで、関係のない API まで止まる

外部の API が 1 つ遅くなっただけなのに、その API を呼んでいない画面まで開かなくなる。CPU もメモリも余っていて、ログには遅い API のタイムアウトしか出ていない。こうした障害は、スレッドプールやコネクションプールを持つサーバーなら、どこでも起こりえます。

ふり返りでは「スレッドが枯渇したから」と書かれがちです。しかし、それだけでは次の問いに答えられません。

- 下流がどれだけ遅くなったら、何本のスレッドやコネクションが、何秒で尽きるのか
- なぜ、遅い API を呼んでいない処理まで止まるのか
- タイムアウトは何秒にすればよいのか。バルクヘッドで同時に呼ぶ数はいくつまでにするか。リトライは助けになるのか

この記事では、これらをリトルの法則 L = λW で計算して答えます。キャパシティプランニングというと、平常時のピークに耐える台数やプールの大きさを決めることを指しがちです。この記事では、下流の障害時にどのプールが何秒で尽きるかまで計算に入れて、タイムアウトや同時実行数の上限を決めます。

### 1.2 この記事の進め方

小さな注文 API（order-api）を用意し、kind のクラスタで壊します。注文（POST /orders）は外部の決済 API を呼び、商品一覧（GET /products）は DB を読むだけです。決済 API の応答に 5 秒の遅延を入れ、スレッドとコネクションが何秒で尽きるかを先に計算してから、実際に壊して確かめます。そのうえで、防御を 1 つずつ入れて、それぞれが L = λW のどこに効くか（あるいは逆に働くか）を測ります。

結果を先に見せると、防御がない状態では、決済 API を呼ばない /products の成功率まで 1.0% に落ちました。

### 1.3 対象とゴール

Tomcat や HikariCP のように上限のあるプールで動くサーバーを書いている人、運用している人を想定しています。例は Spring Boot ですが、考え方はプールを持つサーバー全般に当てはまります。読み終えたときに、次のことができるようになるのがゴールです。

- 自分のサービスで、下流の障害時にどのプールがいつ尽きるかを計算できる
- タイムアウト・バルクヘッド・サーキットブレーカー・リトライが L = λW のどこに効くかを説明でき、値を計算で決められる

### 1.4 扱わないこと

- **WebFlux・コルーチン・仮想スレッド**：スレッドの数という上限はなくなりますが、コネクションや下流への同時呼び出しといった別の上限が先に当たるだけです。むしろ暗黙の上限がなくなるぶん、バルクヘッドのような明示的な上限が要ります
- **待ち行列理論による遅延の予測**：リトルの法則は平均どうしの関係で、負荷が増えたときに W がどう伸びるかまでは教えてくれません

## 2. リトルの法則

### 2.1 L = λW

$$
L = \lambda W
$$

L = λW は、入って出ていくものを数えられるところなら、どこにでも当てはまります。この記事では、主にサーバーのスレッドプールに当てはめます。

- **L**：中にいる数の平均（スレッドプールなら、使用中のスレッドの数）
- **λ**：1 秒あたりに入る数（スレッドを取ったリクエストの数）。上限がなければ到着率と同じで、落ち着いた状態では出ていく率とも同じ
- **W**：1 件が入ってから出るまでの時間の平均（1 件がスレッドを握っている時間）

1 秒に 60 件届き、1 件が 0.05 秒で返るなら、平均して常に 60 × 0.05 = 3 本のスレッドが使われています。到着の仕方や処理時間の分布によらず、平均どうしでこの関係が成り立つのが強みです。

### 2.2 3 つの向きで使う

3 つの値のうち 2 つが分かれば、残りが決まります。この記事では、次の 3 つの向きで使います（例の数字は、このあとの実験のもの）。

| 知りたいもの | 式 | 例 |
| --- | --- | --- |
| 同時に要る数 | L = λW | 1 秒に 60 件 × 1 件 5.05 秒 ≈ 300 本 |
| さばける率の上限 | λ = L ÷ W | 6 本 ÷ 1 件 0.05 秒 = 120 件/秒 |
| 1 件の平均の時間 | W = L ÷ λ | 平均 3.4 本 ÷ 1 秒に 70 件 ≈ 0.05 秒 |

### 2.3 実測で確かめる

サーバーの使用中のスレッド（L）と、λ × W を同じグラフに描くと、2 本の線は重なります。次は 6 章の実験のグラフです。order-api には 1 秒に 70 件（/orders 60 件、/products 10 件）が届いています。

![実測の L と λ×W](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/littles-law.png)
*緑が使用中のスレッド（実測の L）、黄が λ×W。赤い帯が障害の区間*

平常時は L が 3.4 本、λ×W が 3.1 本です。障害中（決済 API の呼び出しが毎回 0.3 秒でタイムアウトする状態）は、どちらも 18.1 本で、60 件/秒 × 0.3 秒 = 18 本と合います。λ×W は直近 10 秒の平均なので、状態が切り替わった直後だけは遅れて追いつきますが、落ち着けばまた重なります。

以下、設定や計算から出す値を λW、メトリクスから測った値を λ×W と書き分けます。

:::details λ×W をどう測っているか
Spring Boot（Micrometer）は、リクエストごとの処理時間を `http_server_requests_seconds` に記録し、合計（`_sum`）と件数（`_count`）を出します。合計の増え方 `rate(_sum)` は「1 秒に終わった件数 × その平均時間」なので、λ × W そのものです。

```promql
sum(rate(http_server_requests_seconds_sum{job="order-api", uri=~"/orders|/products"}[10s]))
```

L は Tomcat の使用中のスレッド（`tomcat_threads_busy_threads`）です。λ × W は終わったリクエストしか数えないので、終わらないリクエストが溜まると L から離れます（5.4）。
:::

### 2.4 この記事で使う前提

- **平均どうしの関係です。** p99 の W から p99 の L は出ません。この記事の λW も、平均の W を使った値です
- **L と W は同じものについて測ります。** スレッドの L には、スレッドを握っている時間を W に使います。リクエストがスレッドの空きを待って列に並ぶ時間は、スレッドの W には入りません
- **流れが落ち着いた状態の関係です。** 立ち上がりの途中や、上限で頭打ちのあいだは、そのままでは成り立ちません（5.2、5.4）

## 3. 障害を L = λW で読む

### 3.1 障害は W の増加から始まる

下流が遅くなったとき、まず変わるのは W です。λ（届く数）は、クライアントが送り続ける限り変わりません。下流の応答を待つあいだスレッドを握る処理は、下流の応答時間がそのまま W に入ります。下流が 100 倍遅くなれば W もほぼ 100 倍になり、λ が同じなら λW も 100 倍になります。

### 3.2 λW が上限を超えると、共有しているプールを通じて広がる

スレッドを握ったまま下流を待つ処理 A と、下流を呼ばない処理 B が、同じスレッドプールを共有しているとします。上限がなければ、A が同時に握る本数は λW で決まります。下流が遅くなって A の λW がプールの大きさを超えると、プールは A で埋まります。あとから来たリクエストは、A か B かに関係なく、1 本の列に並んで空きを待ちます。

- **B**：下流を呼ばないのに、空きを待つうちにクライアントのタイムアウトを過ぎて失敗する
- **A**：スレッドを取れても下流が返らないので失敗する。クライアントがあきらめたあとも処理は続き、スレッドは握られたまま
- **同じプールで受けているヘルスチェック**：答えられず、コンテナが再起動される

この記事の実験に当てはめたのが、次の図です。A は決済 API を呼ぶ /orders、B は DB を読むだけの /products です。決済 API の応答が 0.05 秒から 5.05 秒（遅延の 5 秒を足した値）になると、/orders の λW は 60 件/秒 × 5.05 秒 ≈ 300 本になり、40 本を大きく超えます（λW は流れが落ち着いたときの本数で、そこに至るまでの動きは 5.2 で追います）。

![障害の広がり方](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/failure-spread.ja.png)
*スレッドだけを描いた単純化。コネクションについては下の本文*

同じことは、A と B が共有するコネクションプールでも起きます。小さいプールほど先に尽きます。A がトランザクションの中で下流を呼んでいれば、A はコネクションも下流の応答まで握ります。コネクションが先に尽きると、スレッドを取れた B も、コネクションの空きを待ってスレッドを握ります。共有している 2 つのプールがどちらも上限を超えるので、片方だけを増やしても B は助かりません。

遅くなったのは下流の 1 つだけです。それでも、共有しているプールを通じて、関係のない処理まで止まります。

### 3.3 守り方は 3 つ：W を抑える・L を区切る・λ を絞る

λW をプールの大きさの内側に収めるには、L・λ・W のどれかに上限を付けます。ここでは L = λW を下流の呼び出しに当てはめます。タイムアウトは W（1 回の呼び出しを待つ時間）、バルクヘッドは L（同時に呼ぶ数）、サーキットブレーカーは λ（1 秒に呼ぶ数）に上限を付けます。どれも結果として、処理がスレッドやコネクションを握る時間を短くします。

- **W を抑える**：下流の応答を待つ時間に上限を付ける（タイムアウト）。下流を待つあいだ握るものを減らす（トランザクションの外で下流を呼べば、コネクションは握らない）
- **L を区切る**：下流を同時に呼ぶ数に上限を付け、あふれた分は待たせずにすぐ断る。下流を待ってスレッドを握るのは、上限の数までになる
- **λ を絞る**：失敗が続いたら、しばらく下流を呼ばずにすぐ失敗を返す
- **リトライは逆に働く**：失敗を取り戻す代わりに、1 件の W と、呼び出しの数 λ を増やす

この記事の実験では、/orders 1 件がスレッド・コネクション・決済 API の呼び出しを握る時間の入れ子に、次の場所で防御を入れます（ラベルは、それを入れるシナリオの名前。値は付録 C）。

## 4. 実験環境

### 4.1 全体の構成

![全体の構成](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/architecture.ja.png)

- order-api は Spring Boot（Tomcat のスレッド 40 本、HikariCP のコネクション 10 本）で、/orders・/products・/livez を同じスレッドで受けます
- 決済 API（payment-api）は、平均 0.05 秒・p99 0.12 秒の対数正規分布で応答を返すモックです。6 本のスレッドなので、1 秒に約 120 件までさばけます
- 決済 API の手前に Toxiproxy を置き、クラスタの外から scenarios/run.sh が遅延を入れたり外したりします
- 負荷は k6 で、応答の速さに関係なく一定の率で送ります（オープンモデル）。k6 は応答を待つ 1 件に 1 VU（仮想ユーザー）を使うので、要る VU の数もリトルの法則で決まります。/orders なら 60 件/秒 × k6 のタイムアウト 5 秒 ＝ 300 で、これに余裕を足した数を最初から用意しています
- Prometheus と Grafana は、手元のブラウザから localhost:9090・localhost:3000 で開けます

:::message
VU の数を固定する負荷試験（クローズドモデル）では、この壊れ方は小さく出るか、再現しません。VU は応答を待つあいだ次のリクエストを送らないので、応答が遅くなると到着率が勝手に下がり、同時に待つ数も VU の数で頭打ちになります（VU がスレッドの数より少なければ、スレッドは尽きません）。
:::

:::details 計測のしかけと、規模の縮め方
- order-api のメトリクスは、業務の 40 本とは別のスレッドで 8081 番から返します。40 本が埋まると readiness にも落ち、業務用の Service からは外れます。メトリクス用の Service は、readiness に落ちた Pod も返す設定（publishNotReadyAddresses）にしてあるので、そのあいだも Prometheus は 1 秒ごとに取りに行けます
- シナリオの設定を当てると、設定が変わったアプリの Pod だけが入れ替わります（payment-api の設定が変わるのは 02a・02b の前後だけ）
- コンテナ用に約 4GB で動くよう、到着率やプールの大きさを、よくある本番の規模（Tomcat の既定のスレッド 200 本など）の約 1/5 に縮めています。比率が同じなら、尽きるまでの秒数やタイムアウトの下限と上限は変わりません
:::

### 4.2 1 回の実験の流れと、被害の測り方

![1 回の実験の流れ](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/scenario-timeline.ja.png)

ウォームアップは、JIT のコンパイルや接続プールが落ち着くまで待つ区間で、何も測りません（0 秒の前にも、設定の適用と Pod の入れ替えに 1 分ほどかかり、全体は約 7 分です）。図の下の括弧が、どの値をどの区間で測るかです。

- **成功率・使用中のスレッド・取得待ち**：障害中の 120 秒で集計する。成功率はエンドポイントごとに区間全体の割合、使用中のスレッドは平均と最大、コネクションの取得待ちは最大
- **スレッドが尽きるまで**：障害から 15 秒のあいだの 1 秒ごとの計測で、初めて 40 本になった時刻。実際にはこれより早く尽きていることがある
- **回復までの時間**：遅延を外してから、両方のエンドポイントの成功率（直近 6 秒）が 99% 以上になり、そのまま 15 秒続いた区間の始まりまで。直近 6 秒で数えるので、すぐに戻っても 6〜7 秒と出る。120 秒のうちにそうならなければ「戻らない」
- **再起動の回数**：負荷をかけている間の全体で数える

## 5. 防御なしで壊す（00）

### 5.1 設定

- 決済 API のタイムアウトは 30 秒
- 決済 API をトランザクションの中で呼ぶ（注文を仮登録 → 決済 API で与信 → 確定、を 1 つのトランザクションで行う、よくある書き方）
- HikariCP の取得待ちの上限は、既定の 30 秒

```kotlin:OrderService.kt（00・01a）
tx.execute {
    val orderId = insertOrder(productId, quantity, "PENDING")
    paymentClient.authorize() // 決済 API を待つあいだも、コネクションを握ったまま
    jdbc.sql("update orders set status = 'CONFIRMED' where id = ?").param(orderId).update()
    orderId
}
```

### 5.2 予測：何秒で、どこまで壊れるか

3.2 の 300 本は、上限がなかった場合に、流れが落ち着いたあとの値です。障害の直後にスレッドがどう埋まるかは、1 件ずつの動きを追うと分かります。到着を等間隔にし、スレッドだけを数えて計算したのが次の図です。

![障害の直後にスレッドが埋まっていく様子（計算）](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/thread-timeline.ja.png)
*計算（実測ではない）。1 行が 1 本のスレッドで、縦に切ったときに交わる棒の数が、その瞬間の L*

障害の前は、0.05 秒の短い棒が上の 3 行を入れ替わりで使っています（/products は 1 ミリ秒足らずで返るので、棒は描いていません）。

- **埋まるまでの時間は、空いている本数と到着率で決まる。** 障害の時点で処理中だった 3 件も応答が遅れるので、空いているのは 37 本です。終わる棒がないまま 1 秒に 60 本ずつ増えるので、約 0.6 秒で埋まります。棒が十分に長ければ、5 秒でも 30 秒でも同じです（どこまで短くすれば埋まらないかは、6.1 で求めます）
- **上限がなくても、300 本にはすぐにはならない。** 1.0 秒の時点では 63 本です。300 本で落ち着くのは、最初の棒が終わり始め、増える棒と終わる棒が釣り合う 5 秒後からです

**L = λW の λ は、そのプールに実際に入る率です。** 上限で頭打ちのあいだは、到着率とは一致しません。

- 0.6〜5 秒：空くスレッドがないので、1 件も入れない
- 5 秒以降：終わった棒の数だけ、入れ替わりに入る。平均 40 ÷ 5.05 ≈ 8 件/秒で、40 本 ≈ 8 件/秒 × 5.05 秒と L = λW が成り立つ

入れなかったリクエストは、図の上の「空きを待つ列」に並び続けます。上限がなければ入る率は到着率の 60 件/秒のままなので、3.2 の 300 本になります。

予測は「障害から約 0.6 秒で 40 本が埋まり、/products は列に並んで k6 の 5 秒でタイムアウトする」です。

:::details 00 では、コネクションの分だけ少し早い（約 0.55 秒）
00 では決済 API をトランザクションの中で呼ぶので、コネクション 10 本が先に (10 − 3) ÷ 60 ≈ 0.12 秒で尽きます。このとき使っているスレッドは、コネクションを握った /orders の 10 本です。そのあとは /products もコネクションの空きを待つあいだ（HikariCP の取得待ちの上限は 30 秒）スレッドを握るので、残りの 30 本は 1 秒に 70 本ずつ埋まり、0.12 + 30 ÷ 70 ≈ 0.55 秒で満杯になります。式にすると、障害から t 秒後のスレッドは 3 ＋ 60t ＋ 10 ×（t − 0.117）本です。

頭打ちのあいだに処理を終えられるのも、コネクションを 5.05 秒ずつ握る /orders の 1 秒に約 2 件（10 ÷ 5.05）だけです。
:::

### 5.3 実測：計算どおり、1 秒足らずで 40 本が埋まる

計測は 1 秒ごとなので、障害の直後の 1〜2 点で、コネクションの分を入れた計算（5.2 の折りたたみ）と比べます。同じ設定で 3 回回しました。

| 実行 | 障害からの時間 | 実測のスレッド | 計算 |
| --- | --- | --- | --- |
| 1 回目 | 0.344 秒 | 27 本 | 26 本 |
| 3 回目 | 0.466 秒 | 35 本 | 34 本 |
| 2 回目 | 0.919 秒 | 40 本 | 40 本（0.55 秒で満杯） |

途中を測れた 2 回は、計算との差が 1 本でした（障害の時点で処理中だった本数が、障害の前の 1 分間で 1〜5 本とぶれるので、その範囲です）。決済 API の遅れの 5 秒を待たずに、計算の線に沿って 1 秒足らずで埋まっています。

![障害の前後 15 秒のスレッド（1 回目の実行）](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/threads-fault.png)
*1 回目の実行。赤い点線が障害の始まり。1 秒ごとの計測なので、0.34 秒後（27 本）と 1.34 秒後（40 本）の点が見える*

:::details コネクションの様子と、測り方
![障害の前後 15 秒の HikariCP（1 回目の実行）](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/hikari-fault.png)
*実線が使用中、点線が取得待ち、薄い破線が上限*

図の 15 秒のあいだは、どの計測でもコネクションは 10 本とも使われていて、握っている 10 本と待っている本数を足すと、スレッドの本数に一致しました（0.34 秒は 10 + 17 = 27、1.34 秒からは 10 + 30 = 40）。0.34 秒の時点で、コネクションはもう尽きていたことになります（計算では 0.12 秒）。取得待ちが 30 で止まっているのは、スレッドが 40 本で頭打ちだからです（コネクションを待てるのは、スレッドを持っているリクエストだけ）。障害の前も約 3 本使っているのは、決済 API をトランザクションの中で呼んでいるからで、60 件/秒 × 0.05 秒と合います。

計測は業務とは別のポートで受けているので、40 本が埋まっても取れます。障害の時刻は、遅延を入れる API を呼ぶ直前と応答を受けた直後に、ミリ秒まで記録しています。3 回の生の値は [runs.md](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/00-no-defense/results/runs.md) にあります。
:::

### 5.4 決済 API を呼ばない /products まで止まり、再起動を繰り返す

障害中の 120 秒の成功率は、/orders が 0.3%、決済 API を呼ばない /products も 1.0% でした（1.2 のグラフ）。/products の失敗のうち 91% が k6 の 5 秒のタイムアウトで、スレッドの空きを待つ列で 5 秒を過ぎています（残りは接続のエラー）。

![00 のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/threads.png)
*40 本の横ばい → 階段状に下がる → 再起動、を繰り返す。線が途切れているのは再起動のあいだ*

order-api は障害中に 3 回、遅延を外したあとにもう 1 回再起動しました。1 回分の流れは次のとおりです。

1. 40 本が埋まると、/livez も列に並んで応答できません。liveness probe（5 秒ごと、1 秒でタイムアウト、3 回続けて失敗したら再起動）が失敗し続け、Kubernetes がコンテナを止めにかかります
2. 止めるとき、Spring Boot は新しいリクエストを受け付けず、処理中のものが終わるのを待ちます（graceful shutdown。Spring Boot 3.4 以降の既定）。障害の約 15 秒後から、スレッドは約 5 秒ごとに 40 → 29 → 17 → 6 本と、11 本ほどずつ減りました。コネクション 10 本を 5.05 秒ずつ握る /orders が 10 件ずつ終わり、そのたびに、コネクションを取れた /products が 1 件ほどすぐに終わるからです。5.2 の折りたたみの「1 秒に約 2 件」が、ここで見えています
3. 新しいコンテナが起動すると、待っていた到着がすぐに入り、1 秒足らずでまた 40 本が埋まります

障害中の再起動は、何も解決しません。起動したとたんに、同じ λW が同じ上限に当たるからです。

:::details 実測の L と λ×W が離れる
障害中の L は平均 28.3 本、λ×W は 19.8 本と、2.3 では重なっていた 2 本の線が離れました。理由は 2 つあります。

- L の平均は、計測できた秒だけの平均です。再起動で計測が途切れた約 16 秒を含みません（途切れた秒を 0 本として 121 秒で割ると 24.5 本）
- λ×W は終わったリクエストしか数えません。遅延を外した時点で、まだ 30 本が処理中でした。再起動の直前に終わったリクエストも、計測が取りに行く前にプロセスが止まると数に入りません

L = λW は、入ったものがいずれ出ていく、流れが落ち着いた状態の関係です。入ったまま終わらないリクエストがあるあいだは、そのままでは成り立ちません。
:::

### 5.5 CPU は下がる

![00 の CPU 使用率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/00-no-defense/results/panels/cpu.png)
*突き出ているのは、再起動したあとの JVM の起動*

障害が始まってから最初の再起動までの約 15 秒、order-api の CPU 使用率は 6% 前後で、平常時の 20% より下がりました（障害中の平均の 16% には、再起動のあとの JVM の起動が入っています）。スレッドは決済 API とコネクションを待っているだけで、計算はしていないからです。CPU を基準にしたオートスケールも、この障害では働きません。

### 5.6 学び

- スレッドやコネクションを握ったまま下流を待つ処理は、下流の遅れを、そのプールを共有するすべての処理に広げる
- 尽きるまでの時間は「空いている数 ÷ 到着率」で、遅延の長さによらない。「プールの大きさ ÷ 到着率」が 1 秒足らずなら、どんな遅延でも 1 秒足らずで尽きる
- 尽きているあいだ、CPU は下がる。再起動しても、同じ λW が同じ上限に当たるだけ

## 6. W を抑える：タイムアウトとトランザクションの境界（01a・01b）

### 6.1 タイムアウトの下限と上限を計算する

W を抑える一番の手段は、決済 API のタイムアウトです。短すぎれば平常時にも失敗し、長すぎれば障害時にスレッドが尽きます。そこで、下限と上限を先に計算します。

![タイムアウトの下限と上限](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/docs/images/timeout-window.ja.png)
*上の段が 01a・01b の決済 API とスレッド。下の 2 段は 6.2・6.3 と 7.1 で使う*

#### 下限：平常時の p99 に余裕を足す

決済 API の平常時の p99 は 120ms です。タイムアウトをこれより短くすると、平常時にも 1% 以上の呼び出しがタイムアウトします。どれだけ足すかは、平常時の分布の裾（p99.9 や、混む時間帯の p99）を見て決めます。ここでは約 200ms にします。

#### 上限：プールの大きさ × 余裕 ÷ ピーク時の到着率

決済 API が完全に返らなくなると、/orders 1 件はタイムアウトまでスレッドを握るので、W はタイムアウトの値そのものになります。λW がスレッドの数に収まるには「タイムアウト ≤ スレッドの数 ÷ ピーク時の到着率」が条件で、40 ÷ 60 ≈ 0.67 秒です。5.2 で見たとおり、W がこれより長いと、W がいくつでも同じ速さで埋まります。

ここから、ほかの API の分と到着のばらつきの分を残します。この記事では 3 割を残して、40 × 0.7 ÷ 60 ≈ 467ms を上限にします。0.7 は計算から出る値ではなく、設計で選ぶ余裕です。到着率には、分単位の平均ではなく、秒単位のピークを使います。また、この上限は、遅くなる下流が 1 つで、ほかの下流は同時には遅くならないことを前提にしています。

この 200〜467ms のあいだから、300ms を選びます。

:::message
上限はもう 1 つあります。上流（クライアント）のタイムアウトです。1 件の W の最大値（タイムアウト × 試行回数 ＋ 待ち）がこれより長いと、誰も待っていない処理にスレッドを使います。00 の障害中、order-api が返した 1 件の処理時間は平均 9.9 秒で、k6 は 5 秒でとうにあきらめていました。
:::

### 6.2 タイムアウトを 300ms にする（01a）

#### 予測

スレッドだけを見れば、λW は 60 件/秒 × 0.3 秒 = 18 本で、40 本に収まります。ところが 01a は、決済 API をトランザクションの中で呼んだままです。コネクションも 0.3 秒握るので、コネクションの λW も 18 本になり、10 本を超えます（6.1 の図の 2 段目）。

コネクション 10 本でさばけるのは 10 ÷ 0.3 ≈ 33 件/秒です。残りの /orders と /products は、スレッドを握ったままコネクションを待ちます。待つ上限は HikariCP の既定の 30 秒で、これがスレッドにとっての新しい W になります。計算すると、障害から約 0.85 秒でスレッドも 40 本が埋まります。

:::details 約 0.85 秒の計算
- 0〜0.12 秒：コネクションが (10 − 3) ÷ 60 ≈ 0.12 秒で尽きる。スレッドは約 10 本
- 0.12〜0.3 秒：最初のタイムアウト（0.3 秒）まで、終わるリクエストはない。/orders と /products の 1 秒 70 件がそのままスレッドを握り、0.3 秒で約 23 本
- 0.3 秒〜：コネクションを握った /orders が 1 秒に約 33 件終わり、列の中で /orders に挟まれた /products も 1 秒に約 5.5 件（33 × 10/60）流れる。スレッドは 1 秒に 70 − 33 − 5.5 ≈ 31 本ずつ増え、残り 17 本が約 0.55 秒で埋まる
:::

#### 実測：予告どおりコネクションで尽き、1 秒足らずでスレッドもほぼ埋まる

![01a の HikariCP](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01a-timeout/results/panels/hikari.png)
*実線が使用中、点線が取得待ち、薄い破線が上限*

コネクションは障害の直後から 10 本とも使われ、取得待ちが 30 前後まで積み上がりました（最大 31）。スレッドは、障害の 0.86 秒後の最初の計測で 39 本、1.86 秒後に 40 本でした（計算は約 0.85 秒で満杯）。障害中の /products の成功率は 12.3%、再起動は 5 回で、タイムアウトを入れても /products は守れていません。

### 6.3 もう 1 つの W：コネクションの取得待ち

タイムアウトは 1 か所ではありません。スレッドを握ったまま待つ場所（下流の応答、コネクションの取得、リトライの待ち）ごとに、W の上限を確かめる必要があります。01a では、決済 API のタイムアウトを 300ms にしても、コネクションの取得待ちの上限（30 秒）がそのまま残り、それがスレッドの W になりました。

6.1 の図の 2 段目のとおり、トランザクションの中で呼ぶ限り、コネクションから見たタイムアウトの上限（10 × 0.7 ÷ 60 ≈ 117ms）は下限の 200ms より短く、両方を満たす値がありません。そこで、タイムアウトの値ではなく、コネクションを握る範囲を変えます。

### 6.4 決済 API をトランザクションの外で呼ぶ（01b）

決済 API を先に呼び、コネクションを握るのは DB に書き込む一瞬だけにします。あわせて、HikariCP の取得待ちを 250ms（設定できる最小値）に縮めます。

```kotlin:OrderService.kt（01b 以降）
paymentClient.authorize() // 決済 API はトランザクションの外で、先に呼ぶ
tx.execute { insertOrder(productId, quantity, "CONFIRMED") }
```

:::message
本番では、整合性の扱いが別に必要です。与信が通ったあとに書き込みが失敗したときの取り消し（補償）に加えて、タイムアウトした与信は「失敗」ではなく「結果が分からない」状態です。リトライするなら、同じ冪等キーで送り直せることが前提です（8 章と 9 章のリトライも同じです）。この記事では、スレッドとコネクションを握る時間の違いだけを見ます。
:::

#### 予測

コネクションを握るのは書き込みの数ミリ秒だけになり、コネクションの λW は 1 本未満です。スレッドの λW は 60 × 0.3 = 18 本で、40 本に収まります。/orders は 0.3 秒でタイムアウトして失敗を返し、/products は影響を受けないはずです。

#### 実測：スレッドは 18 本で横ばい、/products は 100%

![01b のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/threads.png)
*障害中も 18 本前後で横ばい（上限は 40 本）*

![01b の成功率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/01b-tx-boundary/results/panels/success.png)
*/orders（紫）は失敗するが、/products（青緑）は 100% のまま。成功率は直近 10 秒で数えているので、斜めに下がって見える*

障害中のスレッドは平均 18.1 本（最大 22 本）で、計算の 18 本どおりでした。/products の成功率は 100%、再起動は 0 回で、遅延を外してから 7 秒で戻りました（測り方の下限に近い値）。/orders は失敗しますが（成功率 0.5%）、失敗が 0.3 秒で返るので、スレッドを使い切りません。

### 6.5 学び

- タイムアウトは「下流の平常時の p99 ＋ 余裕」と「プールの大きさ × 余裕 ÷ ピーク時の到着率」のあいだに置く。上流のタイムアウトより短くする
- スレッドを握ったまま待つ場所は 1 つではない。下流の応答、コネクションの取得、リトライの待ちのすべてに上限を付け、プールごとに λW を計算する。小さいプールから先に尽きる
- 下限が上限を超えるプールは、タイムアウトの値ではなく、握るものを変える（トランザクションの外で下流を呼ぶ）

## 7. L を区切る：バルクヘッド（02a・02b）

### 7.1 p99 が長い下流では、タイムアウトの下限が上限を超える（02a）

01b でうまくいったのは、決済 API の p99（120ms）が、スレッドから見た上限（467ms）より十分に短かったからです。p99 が長い下流では、下限が上限を超えて、両方を満たす値がありません。外部の決済代行のように p99 が秒単位の下流も珍しくなく、たとえば Tomcat の 200 本で 1 秒に 100 件を受けるなら、上限は 200 × 0.7 ÷ 100 ＝ 1.4 秒です。p99 が 2 秒なら、下限が上限を超えます。

02a では、payment-api を平均 100ms・p99 600ms に遅くし（スレッドは 12 本に増やして、さばける率は 120 件/秒のまま）、タイムアウトを p99 に余裕を足した 800ms にします。決済 API はトランザクションの外で呼びます（01b と同じ）。

#### 予測

6.1 の図の 3 段目のとおり、下限の約 800ms が上限の 467ms を超えていて、両方を満たす値がありません。障害中の λW は 60 × 0.8 = 48 本で 40 本を超えます。平常時の L は実測で約 6.6 本（計算の 60 × 0.1 = 6 に、/products などの分が少し乗る）なので、空いている約 33 本が 1 秒に 60 本ずつ埋まり、約 0.55 秒でスレッドが尽きます。

#### 実測：1 秒ほどで尽き、/products は 25%

障害の 0.48 秒後の最初の計測で 33 本（計算は 35 本）、1.48 秒後に 40 本でした。障害中の /products の成功率は 25.3%、再起動は 5 回です。

平常時の /orders の成功率は 99.4% でした。タイムアウトを p99 ＋ 余裕にしても、p99 より遅い 1% のうち一部（ここでは 0.6%）はタイムアウトします。下限ちょうどにタイムアウトを置いても、平常時にこれだけは払うことになります。

### 7.2 バルクヘッドで同時に呼ぶ数を区切る（02b）

タイムアウトで守れないなら、W ではなく L を直接区切ります。Resilience4j の Bulkhead で、決済 API を同時に呼ぶ数を 12 までにし、空いていなければ待たずに断ります。

```yaml:application.yml
resilience4j:
  bulkhead:
    instances:
      payment:
        max-concurrent-calls: 12
        max-wait-duration: 0ms # 上限に達していたら待たずに断る
```

#### 予測

決済 API を待ってスレッドを握る /orders は、最大 12 本です。そこを通れる率は λ = L ÷ W = 12 ÷ 0.8 = 15 件/秒で、残りの約 45 件/秒はすぐに断られます。スレッドは 12 本と少しで、40 本に収まります。

#### 実測：決済 API に届いたのは 14.9 件/秒、スレッドは最大 13 本、/products は 100%

![02b のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/02b-bulkhead/results/panels/threads.png)
*障害中も 12 本前後で横ばい*

![02b の決済 API の呼び出し](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/02b-bulkhead/results/panels/payment-calls.png)
*緑が成功、黄が失敗（0.8 秒のタイムアウト）。バルクヘッドに断られた分は、決済 API まで届かないので数に入らない*

障害中に決済 API まで届いた呼び出しは 14.9 件/秒で、計算の 15 件/秒どおりでした。/products の成功率は 100%、再起動は 0 回で、遅延を外してから 9 秒で戻りました。

### 7.3 同時実行数は、断ってよい率から決める

バルクヘッドの同時実行数は、小さすぎれば平常時にも断り、大きすぎれば障害時にスレッドを多く握ります。目安の下限は平常時の同時実行数とそのばらつき、上限はほかの API の分を残したスレッドの数（40 × 0.7 ＝ 28）です。12 は、平常時の L（60 件/秒 × 0.1 秒 = 6）の 2 倍で、下限に近い値です。

この環境で平常時に断った呼び出しは、1 分に 1 件ほど（約 3,600 件中）でした。ただしこれは、k6 がリクエストを等間隔に送っているからです。到着がランダム（ポアソン到着）なら、平均 6 に対して、断る率は次のとおりです（アーランの B 式）。

| 同時実行数 | 平常時に断る率 |
| --- | --- |
| 12 | 約 1.1% |
| 14 | 約 0.2% |
| 16 | 約 0.03% |

「平常時の L の 2 倍」という倍率は、規模で意味が変わります。同じ 2 倍でも、平均 30・同時実行数 60 なら、断るのは 100 万件に 1 件以下です。同時実行数は倍率ではなく、断ってよい率から決めます。

### 7.4 学び

- 下流の p99 が長く、タイムアウトの下限が上限を超えるなら、タイムアウトではなく同時実行数で区切る
- バルクヘッドを通れる率は「同時実行数 ÷ W」で決まる。上限を超えた分は待たせずにすぐ断る。待たせると、断るまでの時間が新しい W になる
- 同時実行数は、平常時の同時実行数とばらつきから、断ってよい率で決める。大きくても、ほかの処理の分を残したスレッド数まで

## 8. λ を絞る：リトライとサーキットブレーカー（03a・03b）

### 8.1 リトライで、安全だったはずの 300ms が崩れる（03a）

01b（タイムアウト 300ms、決済 API はトランザクションの外）に、Resilience4j の Retry を足します。最大 3 回試行し、試行の間に 500ms 待ちます（どちらも Retry の既定値）。決済のように副作用のある呼び出しは、冪等キーがない限りリトライしてはいけません（6.4 の注）。ここではスレッドと呼び出しの数の動きだけを見ます。

#### 予測

1 件の W は、最大 3 × 0.3 + 2 × 0.5 = 1.9 秒です。試行の間の待ちも、スレッドを握ったままです。λW は 60 × 1.9 = 114 本で 40 本を超え、(40 − 3) ÷ 60 ≈ 0.6 秒でスレッドが尽きます。01b では安全だった 300ms が、リトライによって安全でなくなります。決済 API への呼び出しも、最大 3 倍に増えます。

#### 実測：1 秒ほどで尽き、/products は 8%

障害の 0.55 秒後の最初の計測で 37 本（計算は 36 本）、1.55 秒後に 40 本でした。同じ設定で 8 回回し、障害中の /products の成功率は 7〜8%、再起動はどの回も 5 回でした。

### 8.2 遅延を外しても、すぐには戻らない

03a は、遅延を外してから戻るまでに 12〜46 秒かかりました（8 回。スレッドが尽きなかった 01b は 7 秒）。負荷のかけ方を直す前に回した 4 回では、2 回が 2 分たっても戻りませんでした（うち 1 回は、直前の実行の再起動の待ちを引き継いでいたので、新しい Pod で始めた 11 回に限ると 1 回）。経緯と 12 回の値は [runs.md](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/03a-retry/results/runs.md) にあります。

![戻らなかった回の成功率](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03a-retry/results/panels/success-not-recovered.png)
*戻らなかった回。遅延を外したあと（赤い帯の右）、一度は 100% まで戻ってから、また 0% に落ちる*

#### 何が起きていたか

どの回でも、遅延を外したあとに再起動した order-api が受け付けを始めると、/orders は 1 秒に 65〜90 件と、到着率の 60 件/秒を超えて処理されました（起動を待つあいだに溜まっていた分が重なったと考えられます）。リトライも加わって、決済 API への呼び出しは 112〜123 件/秒まで膨らみ、payment-api のスレッドは上限の 6 本に 8〜22 秒張り付きました。そのあいだ payment-api の中で列ができ、応答が 300ms を超えてタイムアウトし、リトライで呼び出しがまた増えます。戻らなかった回では、多いときで毎秒約 38 件の呼び出しがタイムアウトし、約 30 件がリトライのすえ成功していました。

payment-api が上限に張り付いているあいだ、order-api のスレッドも 40 本で埋まります。それが liveness probe の猶予（5 秒 × 3 回）より先に解ければ戻り、猶予を使い切れば再起動されて、起動のたびに同じことを繰り返します。Kubernetes は再起動の間隔を延ばしていきます（CrashLoopBackOff）。戻った回でも、再起動のあと 14 秒間はスレッドが 40 本のままで、きわどく間に合っていました。

#### リトルの法則で読むと

payment-api がさばける率は λ = L ÷ W = 6 本 ÷ 0.05 秒 = 120 件/秒で、平常時の 60 件/秒に対して、処理能力の余裕は 2 倍しかありません。最大 3 回のリトライは呼び出しを最大 3 倍にするので、この余裕を超えます。さばける率の近くまで呼ぶと、列ができて W が伸び、タイムアウトしてまたリトライになります。そのうえ再起動のたびに溜まった分が一度に流れ込むので、きっかけ（遅延）を取り除いても、遅い状態が自分を保ってしまいます。このように、きっかけが去っても続く障害は、metastable failure と呼ばれています。

### 8.3 サーキットブレーカーで流入を止める（03b）

03a に Resilience4j の CircuitBreaker を足します。直近 10 秒の呼び出しが 20 回以上あり、その失敗率が 50% 以上なら開きます。開いている 5 秒は決済 API を呼ばずにすぐ失敗を返し、そのあと半開（試しに 10 回だけ呼び、成功すれば閉じて元に戻り、失敗が多ければまた開く状態）に移ります。リトライが一番外側にあるので、試行のたびにブレーカーを通り直し、ブレーカーに断られた呼び出しはリトライしません。

#### 予測

開いているあいだ、決済 API への λ はほぼ 0 になり、/orders はすぐ失敗を返すので、W もほぼ 0 になります。

ただし、すぐには開きません。20 回は失敗率を計算し始めるのに要る呼び出しの数で、平常時の流れですでに満たしています。開く条件は、直近 10 秒の呼び出しの半分以上が失敗であることです。障害の直前の 10 秒に成功した約 550 件が集計に残っていて、成功は 1 秒に約 60 件ずつ集計から抜け、失敗は 0.3 秒後から 1 秒に約 60 件ずつ増えます。60 ×（t − 0.3）＝ 550 − 60t から、開くのは障害から約 4.7 秒後です。おおよそ「集計する期間 × しきい値」です。

#### 実測：開いたのは約 4〜5 秒後、決済 API への呼び出しは 60 件/秒から 4 件/秒に

ブレーカーの状態のメトリクスでは、障害の 3.91 秒後の計測ではまだ閉じていて、4.91 秒後には開いていました。

![03b の決済 API の呼び出し](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03b-circuit-breaker/results/panels/payment-calls.png)
*緑が成功、黄が失敗。開いたあとは、5 秒ごとの半開の試しだけが届く*

障害中に決済 API が受けた呼び出しは平均 4.2 件/秒で、01b の 60 件/秒から大きく減りました。/products の成功率は 100%、再起動は 0 回で、遅延を外してから 11 秒で戻りました。ブレーカーが開いているあいだは決済 API を呼ばないので、遅延が外れても次の半開まで（最大 5 秒）は戻れず、01b の 7 秒より少し遅くなります。

### 8.4 ブレーカーが開くまでの約 5 秒

![03b のスレッド](https://raw.githubusercontent.com/rea9r/littles-law-resilience-lab/main/scenarios/03b-circuit-breaker/results/panels/threads.png)
*障害の直後の約 4 秒、40 本に張り付く（ブレーカーが開くまで）。そのあとの細い山は、5 秒ごとの半開の試し*

開くまでの約 5 秒は、03a と同じことが起きます。/orders は 1 回目の失敗のあとリトライの待ちに入り、スレッドを握ったままです。スレッドは障害の 0.91 秒後から 3.91 秒後までの計測で 40 本のまま、4.91 秒後に 29 本、5.91 秒後に 0 本でした。

/products が 100% のままだったのは、スレッドが上限に張り付いた約 4 秒が、k6 のタイムアウトの 5 秒より短かったからで、紙一重です。上流のタイムアウトが 3 秒なら、一部は失敗していたはずです。そのあと 5 秒ごとに立ち上がる 10 本ほどの山は、半開で試した 10 件が、タイムアウトとリトライの待ちでスレッドを握る分です。

開くまでの時間は、直近の一定時間で数えるなら「集計する期間 × しきい値」で決まり、到着率が高いほど、そのあいだに握られるスレッドが増えます。このあいだを、9 章でバルクヘッドと組み合わせて守ります。

### 8.5 学び

- リトライは、W（試行の間の待ちを含む）と λ（呼び出しの数）の両方を増やす。入れたら、W の上限を「試行回数 × タイムアウト ＋ 待ちの合計」で計算し直す
- 試行回数が下流の処理能力の余裕（さばける率 ÷ 平常時の率）を超えると、きっかけが去っても下流の遅い状態が続く。戻るかどうかは、その状態が解けるまでの時間と、liveness probe の猶予の競争になる。リトライは回数ではなく全体に対する割合（リトライ予算）で絞り、待ちにはジッターを入れる。上流もリトライするなら、回数は掛け算になる
- 直近の一定時間で失敗率を数えるサーキットブレーカーは、およそ「集計する期間 × しきい値」がたつまで開かない。開いているあいだは、下流が直っても戻れない

## 10. 障害時のキャパシティプランニング：自分のサービスを L = λW で点検する

### 10.1 プールと上限を書き出す

リクエストが握ったまま待つもの（スレッド、コネクションなど）と、その上限、共有している処理を書き出します。

- リクエストを処理するスレッド（Tomcat なら `server.tomcat.threads.max`、既定 200）
- DB のコネクション（HikariCP なら `maximum-pool-size`、既定 10）
- HTTP クライアントの接続プール、非同期処理のスレッドプール、バルクヘッドのような同時実行数の上限
- 仮想スレッドを使っているなら、スレッドの上限はありません。下流ごとに同時実行数の上限があるかを確かめます

### 10.2 障害時の W の最大値を足し算する

下流が返らなくなったとき、1 件がスレッドやコネクションを握る最長の時間を、設定から足し算します。

- （接続のタイムアウト ＋ 応答のタイムアウト）× 試行回数 ＋ リトライの待ちの合計
- コネクションの取得待ちの上限（HikariCP の既定は 30 秒）と、HTTP クライアントの接続プールの取得待ち
- トランザクションの中で下流を呼んでいれば、その時間はコネクションの W にも入る

HTTP クライアントには、応答のタイムアウトの既定が無制限のものも多くあります。また「読み取りのタイムアウト」は、バイトが届かない時間の上限で、全体の時間の上限ではないことがあります。最後に、合計が上流のタイムアウトより短いかを確かめます。

### 10.3 λW と上限を比べる

プールごとに次の表を埋め、「ピーク時の到着率 × W の最大値」が「上限 × 余裕」に収まるかを確かめます。下流が複数あるときは、同時に遅くなりうる組み合わせで λW を足します。

| プール | 上限 | 共有している処理 | ピーク時の到着率（秒単位） | 障害時の W の最大 | λW | 上限 × 0.7 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 例：Tomcat | 200 | 注文・一覧 | 250 件/秒 | 1.1 秒 | 275 | 140 | 超える |

超えていれば、そのプールは下流の障害で尽きます。尽きるまでの時間は「空いている数 ÷ 到着率」で、多くの場合 1 秒もかかりません。

:::details 値の取り方（Prometheus と Micrometer の例）
```promql
# ピーク時の到着率（分単位の rate の最大。秒単位のピークはこれより高い）
max_over_time(sum(rate(http_server_requests_seconds_count[1m]))[1d:1m])
# 下流ごとの平常時の p99（percentiles-histogram を有効にしておく）
histogram_quantile(0.99, sum by (le, client_name) (rate(http_client_requests_seconds_bucket[5m])))
# 平常時の L（2.3 と同じく rate(_sum) が λ×W になる）
sum(rate(http_server_requests_seconds_sum[1m]))
```
:::

### 10.4 守り方を選ぶ

| 状況 | 守り方 |
| --- | --- |
| タイムアウトの下限が上限より小さい | W を抑える。タイムアウトを下限と上限のあいだに置く |
| 下流を待つあいだ、小さいプール（コネクションなど）も握っている | 握る範囲を変える。トランザクションの外で下流を呼ぶ |
| タイムアウトの下限が上限を超える | L を区切る。同時実行数に上限を付け、あふれた分はすぐ断る |
| 下流を守りたい、早く失敗させたい | λ を絞る。サーキットブレーカー（開くまでのあいだはバルクヘッドで守る） |
| リトライを入れたい | 冪等であることを確かめ、回数と待ちを控えめにして、W の最大値を計算し直す |

### 10.5 liveness probe を業務と同じスレッドで受けていないか

liveness probe を業務と同じスレッドプールで受けていると、下流の障害でプールが埋まったときに probe も答えられず、コンテナが再起動されます。再起動しても、起動したとたんに同じ λW が同じ上限に当たるので、回復が遅れるだけです。下流を待ってスレッドが埋まった状態は、再起動では直りません。

この記事の実験では、/livez を業務と同じ 8080 番（同じ 40 本）で受けていました。スレッドが尽きたままになった 00・01a・02a・03a は、遅延を外してから戻るまで 37〜43 秒（03a は 12〜46 秒で、戻らない回もあった）かかり、尽きなかった 01b・02b・04 と、尽きたのが 4 秒ほどで済んだ 03b は 7〜11 秒で戻りました。

一方で、Spring Boot のドキュメントは、probe を業務と同じポートでも受ける構成（`management.endpoint.health.probes.add-additional-paths`）を勧めています。業務とは別のポートだけで受けると、業務側が接続を受けられなくなっても probe が成功してしまうからです。liveness probe は「プロセスが壊れていて、再起動で直る」ときだけ失敗させるものです。下流の障害で業務のスレッドが埋まりうるなら、liveness は管理ポートで受けて業務のスレッドに依存させず、業務のポートでは readiness だけを受ける構成が選べます（すべてのレプリカが同時に外れうることは承知のうえで）。業務のスレッドが尽きたことは、再起動ではなく 10.6 の監視で知ります。

### 10.6 「使用中 ÷ 上限」を監視する

```promql
# Pod ごとの「使用中 ÷ 上限」（ラベル名は環境に合わせる）
max by (pod) (tomcat_threads_busy_threads / tomcat_threads_config_max_threads)
max by (pod) (hikaricp_connections_active / hikaricp_connections_max)
max by (pod) (hikaricp_connections_pending)
# 下流ごとの L（同時に待っている呼び出しの数）
sum by (pod, client_name) (rate(http_client_requests_seconds_sum[1m]))
```

- `tomcat_threads_*` は、`server.tomcat.mbeanregistry.enabled=true` にしないと出ません
- メトリクスは業務とは別のポート（`management.server.port`）で出しておけば、業務のスレッドが尽きても測れます
- 尽きるのは 1 秒足らずなので、アラートで防ぐことはできません。役に立つのは、CPU が下がって原因を見誤りそうなときに、どのプールが尽き、どの下流の L が膨らんだかをすぐ示すことです

### 10.7 遅延を注入して確かめる

計算は、前提が合っていて初めて当たります。予測と合格条件（「障害から 2 秒以内にスレッドが上限に達する」「下流を呼ばない処理の成功率が 99% 以上」など）を先に書いてから、下流に遅延を入れ、オープンモデルの負荷をかけて確かめます。遅延は、Toxiproxy のようなプロキシや、サービスメッシュの fault injection で入れられます（この記事の入れ方は [run.sh](https://github.com/rea9r/littles-law-resilience-lab/blob/main/scenarios/run.sh)）。

## 11. まとめ

- スレッドやコネクションを握ったまま下流を待つ処理があると、下流の遅れは、そのプールを共有するすべての処理に広がる。尽きるまでの時間は「空いている数 ÷ 到着率」で、遅延の長さによらず、多くの場合 1 秒足らず
- 守り方は、W・L・λ のどれを小さくするかで決まる。タイムアウトの下限と上限、トランザクションの範囲、同時実行数の上限、流入を、それぞれ計算で決められる
- リトライは逆向きに働き、下流の処理能力の余裕を超えると、きっかけが去っても戻らないことがある
- 見るべきは CPU ではなく「使用中 ÷ 上限」

まず確かめるなら、次の 2 つです。トランザクションの中で外部の API を呼んでいないか。HTTP クライアントに、下限と上限のあいだのタイムアウトが設定されているか。

## 付録

### A. 他にもこんな場面で使える

- **コネクションプールの大きさ**：ピーク時の到着率 × 1 件がコネクションを握る平均時間に、ばらつきの余裕を足す
- **非同期のワーカーやコンシューマーの並列数**：処理したい率 × 1 件の処理時間
- **スケールアウトで守るときの台数**：障害時の λW ÷ 1 台のスレッド数（00 なら 300 ÷ 40 ≈ 8 倍）

### B. この実験環境の限界

- k6 の constant-arrival-rate はリクエストを等間隔に送るので、本番のトラフィックより、ばらつき（バースト）を小さく見積もります
- 障害は、応答の遅延だけです。下流がエラーを返す場合や、接続の段階で詰まる場合は試していません
- Toxiproxy は応答を遅らせるだけなので、障害中の payment-api 自体はほぼ暇です。サーキットブレーカーが下流を守る効果は、障害中には確かめられていません
- order-api のレプリカは 1 つです
- リトライの利点（一時的な失敗を吸収すること）は測っていません
- メトリクスは 1 秒ごとの計測なので、「何秒で尽きたか」には 1 秒の幅があります。HikariCP はプールの統計を 1 秒キャッシュするので、使用中・取得待ちが 1 つ前の計測の値のままのこともあります
- 壊れるシナリオの回復時間は、遅延を外したときに order-api が再起動の途中かどうかで、実行ごとにばらつきます
