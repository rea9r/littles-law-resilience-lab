# 改善の記録

実験環境を作りながら、予測とずれたこと・つまずいたことと、その直し方を残す。

## 2026-10-17

### Grafana が起動しきらない（メモリ上限 320Mi）

- 起きたこと：Grafana 13 の Pod が Running のまま数分たっても応答せず、ノードの CPU を 680% 使い続けた（ほとんどがカーネル時間）
- 原因：メモリ上限 320Mi に対して使用量が 220MB を超え、メモリ不足でページの読み直しを繰り返す状態（スラッシング）になっていた
- 直し方：上限を 512Mi に上げ、CPU を 1 コアに制限した。起動は 12 秒で終わり、CPU 使用率は 2.5% に落ち着いた
- 補足：Docker に割り当てられるメモリは約 4GB なので、各コンポーネントの上限を積み上げて収まるように調整している

### 失敗の理由がメトリクスに出ない

- 起きたこと：`@ExceptionHandler` で 504 や 503 に変換した失敗が、`http_server_requests` の `exception` タグでは `none` になり、理由を区別できなかった
- 直し方：ErrorHandler で `ServerHttpObservationFilter.findObservationContext(request)` から観測のコンテキストを取り、例外を明示的に記録した

### 成功率のグラフが途切れる

- 起きたこと：成功が 1 件もない時間帯に、k6 の成功率のグラフが 0% ではなく「データなし」になった
- 原因：k6 は remote write で値が増えた系列しか送らないので、成功の系列そのものが届かなくなる
- 直し方：`(成功 ÷ 全体) or (0 × 全体)` として、成功の系列がないときは 0 を描くようにした

### 名前を役割の分かるものにした

- api-a / api-b を order-api（注文 API）/ payment-api（決済 API）に改めた。「決済が遅くなっただけで、決済と関係のない商品一覧まで止まる」という話として読めるようにするため

### 01b（短縮版）で予測が当たることを確認

- 平常時：実測の L 3.6、λ×W 3.3（予測 3.6）
- 障害中：スレッドの最大値 19（予測 60 × 0.3 + α ≈ 19）、/products の成功率 100%、回復まで 6 秒
- ウォームアップを 20 秒にした短縮版では、JIT が温まる前の最初の 20 秒ほど、決済 API の呼び出しが 300ms を超えてタイムアウトした。本番の設定ではウォームアップを 60 秒取る

### k6 の Pod を待つスクリプトが競合で止まる

- 起きたこと：Job を作った直後に `kubectl wait pod -l job-name=k6` を呼ぶと、まだ Pod がなく「no matching resources found」で終了した
- 直し方：Pod ができるまで待ってから `kubectl wait` するようにした

### 実験0（1 回目）：予測どおりに壊れた

- 障害中の /products の成功率 0.3%、/orders 0.0%、再起動 3 回、障害中の CPU 平均 22%
- 平常時の実測 L 3.57、λ×W 3.36
- 障害開始から 0.5 秒後の時点でスレッド 29 本・コネクション 10 本（満杯）・取得待ち 19、2.5 秒後にスレッド 40 本で枯渇。予測の約 0.7 秒と矛盾しない
- 「枯渇まで 3 秒」と出たのは、メトリクスの収集間隔が 2 秒だったため。記事で「1 秒足らずで尽きる」を示せるよう、収集間隔を 1 秒にした

### キャプチャが真っ白になる

- 起きたこと：「Powered by Grafana」のバッジを消す処理が、テキストが「Powered by」で始まるパネル全体の親要素まで消していた
- 直し方：テキストがちょうど「Powered by」だけの、いちばん小さな要素（バッジ本体）だけを消すようにした

### Grafana が再びメモリ上限に張り付く

- 起きたこと：起動から 25 分ほどで、Grafana のメモリが上限の 512Mi に達し、1 コアを使い切って応答に 17 秒かかるようになった
- 原因：Go のランタイムはコンテナのメモリ上限を知らないので、ヒープが上限まで膨らむ
- 直し方：`GOMEMLIMIT=448MiB` で GC にメモリの目安を伝え、上限を 640Mi にした

### 設定を変えるたびに実験データが消える

- 起きたこと：収集間隔を変えて Prometheus を入れ替えたら、`emptyDir` に置いていた実験0のデータが消えた。Grafana のアノテーション（障害の時間帯）も、Pod を入れ替えると消える
- 直し方：Prometheus と Grafana のデータを kind の永続ボリューム（local-path）に載せた

### 1 周目：全シナリオを通して実行

障害開始の時刻をミリ秒で記録し、スレッドが尽きるまでの時間を 1 秒ごとの生のサンプルで判定するようにしてから、全 8 シナリオを回した。

- 00：障害開始から 0.4 秒後の計測でスレッド 24 本（予測は平常時の約 3 本 + 60 rps × 0.4 秒 = 27 本）、1.4 秒後に 40 本すべて
- 01a：タイムアウトを 300ms にしても 1.5 秒で尽きた。コネクションの取得待ちが最大 39 件
- 01b：スレッドの最大値 19 本（予測 19 本）、/products 100%
- 02a：1.07 秒で尽きた。平常時の /orders の成功率は 99.7%（予測どおり、p99 を超えた分がタイムアウトする）
- 02b：スレッドの最大値 14 本。平常時の /orders の成功率は 99.4%（02a は 99.7%）。この差は 2 周目で誤差だと分かった（下の「バルクヘッドの平常時の代償」）
- 03a：リトライを足すと、01b では安全だった 300ms でも 1.3 秒で尽きた。障害中は payment-api のスレッドも上限の 6 本に張り付いた（リトライのない 01b では 5 本以下）。リトライが決済 API への λ を増やしている
- 03b：予測と違い、障害開始から 0.7 秒でスレッドが一度 40 本に達し、約 4 秒続いた。サーキットブレーカーが開くには失敗が 20 件たまる必要があり、それまでのリクエストがリトライの待ち（500ms）でスレッドを握るため。/products は 100% で、数秒の待ちで済んだ。予測と合格条件を直した
- 04：スレッドの最大値 14 本、/products 100%、回復まで 9 秒。バルクヘッドが、サーキットブレーカーが開くまでの数秒を守っている

### 障害が終わっても戻らない（02a・03a）

- 起きたこと：02a は回復まで 65 秒、03a は 42 秒かかった。03a では障害の終盤から 1 分近く order-api のメトリクスが途切れていた
- 見立て：liveness probe が業務と同じスレッドプールで受けているので、障害中に再起動を繰り返し（5 回）、CrashLoopBackOff で再起動の間隔が延びた
- 対応：裏付けのため、実行ごとに Pod のイベントを `results/raw/events.txt` に保存するようにした。障害中に決済 API が受けた呼び出し数（決済 API にとっての λ）も記録するようにした

### 2 周目：再現性の確認

同じ設定で全 8 シナリオをもう一度回し、1 周目と比べた。

| シナリオ | 障害中の /products（1 周目 → 2 周目） | スレッドが尽きるまで | 再起動 | 回復まで |
|---|---|---|---|---|
| 00 | 1.6% → 0.8% | 1.4 → 0.48 秒 | 3 → 4 回 | 6 → 49 秒 |
| 01a | 11.5% → 12.4% | 1.54 → 1.62 秒 | 4 → 5 回 | 13 → 18 秒 |
| 01b | 100% → 100% | 尽きない | 0 → 0 回 | 7 → 6 秒 |
| 02a | 29.8% → 33.0% | 1.07 → 1.18 秒 | 5 → 5 回 | 65 → 60 秒 |
| 02b | 100% → 100% | 尽きない | 0 → 0 回 | 7 → 10 秒 |
| 03a | 8.2% → 7.2% | 1.33 → 1.25 秒 | 5 → 6 回 | 42 秒 → 戻らない |
| 03b | 100% → 100% | 0.73 → 1.4 秒（一時的） | 0 → 0 回 | 11 → 10 秒 |
| 04 | 100% → 100% | 尽きない | 0 → 0 回 | 9 → 9 秒 |

- 成功率・スレッド・再起動回数は安定して再現する。ばらつくのは、壊れるシナリオの回復時間だけ
- 障害中に決済 API が受けた呼び出し（2 周目から記録）：01b は 60 件/秒、02b は 14.8 件/秒（予測：枠 12 ÷ 0.8 秒 = 15 件/秒）、03b は 4.6 件/秒、04 は 3.1 件/秒。バルクヘッドの通過量もリトルの法則（λ = L ÷ W）どおりになる

### 回復時間がばらつく理由（00）

- 2 周目の 00 では、障害中の 3 回に加えて、障害が終わった 9 秒後に 4 回目の再起動が起きた
- 障害中に Tomcat の待ち行列にたまったリクエスト（クライアントはタイムアウトで諦め済み）を処理している間、/livez も応答できず、liveness probe が再び失敗したため
- 再起動から復帰までの間隔は 6 秒、6 秒、6 秒と続いたあと 30 秒に延びた（再起動を繰り返すと kubelet が間隔を延ばす）
- 障害がどのタイミングで終わるかで、回復が数秒で済むか 1 分近くかかるかが変わる

### 原因を取り除いても戻らない（03a・2 周目）

- 遅延を外して 26 秒後に order-api が起動したが、直後に決済 API への呼び出しが 107 件/秒に跳ね、payment-api のスレッドが上限の 6 本（処理能力 120 rps）に張り付いた。order-api はまた落ち、回復の観察時間（120 秒）が終わるまで戻らなかった
- order-api から見ると、決済 API の呼び出しは毎秒約 36 件がタイムアウトし、約 30 件はリトライのすえ成功していた。合計で約 110 件/秒が、決済 API の処理能力の手前まで届いていた
- 決済 API のサーバー側の処理時間は 50ms のまま。遅れは待ち行列（Tomcat のキュー）と、起動直後で遅い order-api 側で生じている
- 1 周目の 03a は 42 秒で戻ったので、起きるかどうかはタイミング次第。頻度を確かめるため 03a を追加で 2 回回す

### 03a を 4 回回した

- 遅延を外してから回復まで：42 秒、戻らない、19 秒、戻らない（観察は 120 秒）
- 戻らなかった 2 回は、どちらも Pod のイベントに CrashLoopBackOff が記録されていた。起動 → リトライで決済 API への呼び出しが膨らみ両方のスレッドが埋まる → liveness probe の失敗で再起動 → 再起動の間隔が延びる、の循環
- 詳細は `scenarios/03a-retry/results/runs.md`。リポジトリに残したグラフは 4 回目（戻らなかった回）

### グラフの凡例を分かりやすくした

- 成功率の凡例を `orders` / `products` から「/orders（決済 API を呼ぶ）」「/products（決済 API を呼ばない）」に変えた
- Prometheus と Grafana のデータを永続ボリュームに載せたので、ダッシュボードを変えたあと、全シナリオのキャプチャを再実行なしで撮り直せた

### バルクヘッドの平常時の代償（予測の訂正）

- 予測：同時呼び出しの平均 6 に対して枠 12 なら、到着がランダム（ポアソン分布）だとすると約 2% は断られる
- 実測：2 周目の 02b で、平常時にバルクヘッドが断った件数は 0 件。平常時の失敗はすべてタイムアウト（02a・02b とも 1 分あたり 21〜24 件、約 0.6%）で、1 周目の成功率の差は誤差だった
- 理由：k6 の constant-arrival-rate はリクエストを等間隔に送るので、同時呼び出し数のばらつきが本物のトラフィックよりずっと小さい
- 限界として残す：この環境は、平常時のばらつき（バースト）を本番より小さく見積もる。本番で枠を決めるときは、平均の L に加えて、バーストの分の余裕を見る必要がある
