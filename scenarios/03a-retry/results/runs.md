4 回目は、3 回目が終わった直後に同じ設定で始めたので、Pod が入れ替わらず、3 回目の 5 回の再起動で延びた再起動の待ち（CrashLoopBackOff）を引き継いでいた。障害を入れた時点で order-api は起動から約 5 分しかたっておらず（kubelet が待ちを元に戻すのは、10 分続けて動いたあと）、障害中に落ちたあと、次に起動するまで 2 分半ほどかかった。再起動が 2 回、障害中に決済 API が受けた呼び出しが 14.7 件/秒（ほかの回は 31〜34 件/秒）と少ないのも、落ちていた時間が長いため。新しい Pod で始めた回に限ると、戻らなかったのは 2 回目だけになる。

## 遅延を外したあとに起きていること

12 回のどの実行でも、遅延を外したあとに order-api が起動すると、リトライで決済 API への呼び出しが 112〜123 件/秒（決済 API の処理能力 120 件/秒の付近）まで膨らみ、payment-api のスレッドが上限の 6 本に 8〜22 秒張り付いた。この間に order-api の liveness probe が失敗するかどうかで、数十秒で戻るか、再起動を繰り返して戻らないかが分かれる。戻らなかった 2 回では、どちらも Pod のイベントに CrashLoopBackOff（Back-off restarting failed container）が記録されている。order-api が起動するたびに両方のスレッドが埋まって再起動し、再起動の間隔が延びていく。
